# 스킬 안내

[← README](../README.md)

스킬은 13개입니다. 새 프로젝트는 위에서부터 차례로 쓰고, 이미 있는 프로젝트는 필요한 스킬만 씁니다.
이미 정해진 것은 다시 묻지 않고, 작은 프로젝트는 문서도 작게 만듭니다.

## 새 프로젝트 흐름

| 순서 | 스킬 | 하는 일 | 결과 |
|---|---|---|---|
| 1 | `idea-brainstorm` | 막연한 아이디어의 문제·사용자·가치·범위를 구체화합니다. 이미 명확하면 건너뜁니다 | `docs/IDEA.md` |
| 2 | `prd-generator` | 요구마다 ID와 관찰 가능한 수용 기준을 붙이고, 자율운영 합의(권한·예산·금지·모델·한도 처리)를 적습니다. 화면 제품이면 실제 디자인 미리보기를 보여 주고 사용자가 고르게 합니다 | `docs/PRD.md`, `docs/DESIGN.md` |
| 3 | `trd-generator` | 기존 환경을 조사해 중요한 기술 선택과 근거·검증 수단을 정합니다 | `docs/TRD.md` |
| 4 | `architecture-generator` | 구성·경계·핵심 흐름·데이터와 API 계약을 설계합니다. 앞 문서와 충돌하면 드러냅니다 | `docs/ARCHITECTURE/` |
| 5 | `plan-generator` | 기능 단위 태스크와 작은 phase로 나누고, 상태와 기록 파일을 만듭니다 | `plan_setup/` |
| 6 | `harness-setup` | 수용 기준을 실제로 검사할 수단과 로컬 실행 환경을 준비하고, 직접 돌려 확인합니다 | `harness_setup/` |
| 7 | `loop-setup` | 실행 방식·병렬·검증·복구·재개를 정하고, 승인되면 Loop를 시작해 완료 보고까지 갑니다 | `loop_setup/LOOP.md` |

각 스킬은 끝나면 다음 스킬을 제안합니다. 이후 단계를 미리 승인했으면 이어서 진행합니다. 자세한 규칙은 [진행 방식](workflow.md)에 있습니다.

## 진행 중·완료 뒤

| 스킬 | 이럴 때 | 하는 일 |
|---|---|---|
| `harness-update` | 검사가 낡았다, 테스트가 흔들린다, 새 의존 서비스가 생겼다 | 실패 원인을 코드 결함·검사 불일치·환경·흔들림으로 가르고, 하네스를 필요한 만큼 고쳐 실제로 다시 확인합니다. 통과시키려고 검사를 약화하지는 않습니다 |
| `loop-update` | 실행 방식을 바꾸고 싶다, 같은 곳에서 계속 막힌다, 1.x 루프를 옮기고 싶다 | 기존 합의·이력·남은 예산을 이어받아 LOOP.md를 부분 수정하고, 실행 중이었다면 원래 작업을 끝까지 이어 갑니다 |
| `feature-add` | 기능을 더하거나 요구를 바꾼다 | 영향받는 요구·설계·계획만 고칩니다. 기존 ID와 완료 이력은 보존합니다. 실행 요청이면 구현·검증까지 합니다 |
| `bug-fix` | "xx가 안 돼", "예전엔 됐는데" | 재현 → 실패하는 회귀 검사 → 최소 수정 → 영향 검증 순으로 진행하고 BUG 기록을 남깁니다 |
| `refactor-plan` | 동작은 그대로 두고 코드를 정리한다, 의존성을 올린다, 스택을 바꾼다 | 범위와 검증 계획을 세웁니다. 통과 조건은 "기존 동작 보존 + 구조 조건"입니다 |
| `code-to-docs` | 문서 없이 만든 코드를 이 흐름에 올린다 | 현행 요약 / PRD·TRD / Architecture / 전체 체계 연결 중 고른 범위를 코드 근거로 문서화합니다. 관찰한 사실과 추론을 구분합니다 |

## 어떤 스킬을 부를지 모를 때

말로 요청하면 에이전트가 고릅니다. 다만 스킬을 쓰지 않고 바로 처리할 때가 있으니, 원하는 단계가 분명하면 이름을 적어 주세요.

```text
/harness-loop-fullstack-kor:feature-add 댓글 기능 추가하려는데      # Claude Code
$refactor-plan 라이브러리 버전 올리자                                # Codex
```
