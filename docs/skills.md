# 스킬 안내

[← README](../README.md)

스킬은 레이어 순서로 이어집니다. **각 스킬은 앞 레이어의 파일만 입력으로 받고**, 끝나면 결과를 보고하고 멈춥니다.
모든 스킬은 산출물을 쓴 뒤 프로젝트 루트의 `CLAUDE.md`·`AGENTS.md` 에 자기 레이어의 요약 규칙을 갱신합니다 — 스킬을 읽지 않고 시작하는 세션(직접 연 세션, 루프가 띄운 세션)도 규칙을 알게 하기 위해서입니다.

```
Layer 0  idea-brainstorm        → docs/IDEA.md
Layer 1  prd-generator          → docs/PRD.md
         trd-generator          → docs/TRD.md
Layer 2  architecture-generator → docs/ARCHITECTURE/*.md
Layer 3  plan-generator         → plan_setup/
Layer 4  harness-setup          → harness_setup/          (harness-update 로 갱신)
Layer 5  loop-setup             → loop_setup/             (loop-update 로 갱신)
Layer 6  code-to-docs · refactor-plan · feature-add · bug-fix   (프로젝트 완료 뒤)
```

---

## 문서 만들기 (Layer 0~2)

### `idea-brainstorm` — 모호한 아이디어를 구체화

**언제**: 무엇을 만들지 아직 흐릿할 때. 이미 분명하면 건너뛰고 `prd-generator` 에 바로 설명해도 됩니다.
**하는 일**: 역질문과 선택지로 문제·타깃 사용자·핵심 가치·핵심 흐름·MVP 범위·제약·성공 기준·리스크·미결 사항을 정리합니다.
**산출물**: `docs/IDEA.md`

> 사용자: 프리랜서용 인보이스 앱을 만들고 싶은데 아직 막연해.
> 에이전트: 누가 인보이스를 보내고 누가 받나요? 결제까지 다루나요, 발행까지인가요? … MVP 범위를 A/B/C 중 고르시면 IDEA.md 초안을 쓰겠습니다.

### `prd-generator` — 무엇을 만들 것인가

**하는 일**: 문제·사용자·유저 스토리·기능 요구사항(FR)·비기능 요구사항(NFR)을 쓰고, **요구사항마다 고유 ID 와 관찰 가능한 수용 기준**을 붙입니다. 뒤의 설계·플랜·게이트가 이 ID 를 그대로 참조합니다.
**산출물**: `docs/PRD.md`

> 에이전트: FR-001 인보이스 발행 — 수용 기준: "발행 버튼을 누르면 PDF 가 생성되고 번호가 연속된다". P0/P1 우선순위와 미결 사항(OQ) 표를 함께 만들었습니다.

### `trd-generator` — 어떤 기술로 만들 것인가

**하는 일**: 스택·DB·API·인증·보안·테스트·배포를 **결정 단위(TD)** 로 확정하고, 각 결정에 근거 요구사항·검증 방법·되돌리기 비용을 붙입니다. 테스트 절의 **필수 커버 영역 표**와 로컬 개발 환경 절의 **구성 요소 표**는 하네스가 그대로 받습니다.
**산출물**: `docs/TRD.md`

### `architecture-generator` — 구조를 고정

**하는 일**: `overview.md` 에 시스템 구성·경계·핵심 흐름을, 영역별 문서(frontend·backend·database·auth·security 등)에 세부 설계를 씁니다. **PRD·TRD 와 충돌하는 설계는 봉합하지 않고 충돌(CF)로 드러냅니다.**
**산출물**: `docs/ARCHITECTURE/*.md`

## 계획과 검증 (Layer 3~4)

### `plan-generator` — 마스터 플랜

**하는 일**: 프로젝트를 **phase(검증 가능한 단계) → task(파일 몇 개를 고치는 작업 단위)** 로 쪼개고, PRD 추적표에 담당 태스크를 채웁니다.
미결·충돌에 걸린 태스크는 `blocked` 로 표시하고, 사용자가 미결을 풀면 루프가 `pending` 으로 엽니다.
루프가 "수용 기준을 다시 써야 한다"고 돌려보내면 이 스킬의 부분 갱신이 처리합니다.

```
plan_setup/
├── PLAN.md                    전체 지도 — phase 구성, 태스크 색인, 차단 목록, 요구사항→태스크 추적
├── phase-01/
│   ├── phase-01-<이름>.md     phase 의 목표·수용 기준·태스크 목록
│   └── phase-01-tasks/
│       └── phase-01-task-01.md
├── STATE.md                   지금 어디인가
└── LOG.md                     무슨 일이 있었는가 (append-only)
```

태스크 문서의 frontmatter 가 뒤의 모든 자동화의 재료입니다.

```yaml
id: phase-02-task-03
title: 인보이스 번호 채번
priority: P0
depends_on: [phase-01-task-09, phase-02-task-01]   # DAG 의 간선
files: [src/data/invoice-number.ts, src/data/invoice-number.test.ts]   # 병렬 충돌 검사의 재료
architecture: [database.md §3.2, backend.md §3.5]
acceptance_criteria: [...]
status: pending          # pending / in_progress / blocked / failed / completed
verification: [lint, unit, e2e, task_validation]   # 통과해야 할 게이트
blocked_by: []
```

### `harness-setup` — 검증 하네스

**하는 일**: 문서와 플랜을 읽고 **게이트 4개의 정의서**(무엇을 검사하고, 어떤 명령으로 돌고, 무엇이 통과이며, 언제부터 활성인가)와 **로컬 개발 환경 스크립트**(`local-dev`)를 만듭니다. 자세한 내용은 [검증 하네스](harness.md).
**산출물**: `harness_setup/HARNESS.md`, `quality_gates/{lint,unit,e2e,task_validation}.md`, `scripts/local-dev.*`

### `harness-update` — 하네스 갱신

**언제**: 게이트가 활성 시점에 도달했을 때, 차단이 풀렸을 때, 새 의존 서비스가 생겼을 때, 같은 검사가 여러 태스크에서 실패할 때. 보통은 루프가 스스로 부릅니다.
**하는 일**: 미활성 게이트를 활성으로 올리고, 대기 중이던 e2e 흐름을 켜고, `local-dev` 에 구성 요소를 더하고, 흔들리던 테스트를 안정화하며 그 원인을 규칙 표에 남깁니다.
갱신은 **상태 반영 / 범위 확대 / 약화** 세 등급으로 나뉘고, 검증을 약하게 만드는 변경은 사용자 확인 없이는 적용하지 않습니다.

> 사용자: Redis 붙였으니 local-dev 고쳐줘.
> 에이전트: 구성 요소 표에 Redis 행을 더하고 `local-dev.ps1` 에 준비 판정 블록을 넣었습니다(범위 확대). `LOG.md` 에 한 줄 남겼습니다.

## 개발 루프 (Layer 5)

### `loop-setup` — 개발 루프 세팅

**하는 일**: 앞으로 모든 세션이 따를 실행 규칙을 `LOOP.md` 한 문서로 고정합니다 — 다음 태스크를 어떻게 고르고, 게이트를 어떤 순서로 돌리고, 실패를 어떻게 분류하고, 언제 멈춰 묻고, 기록을 언제 쓰고, 세션을 누가 여는지.
태스크 DAG 를 스크립트로 그려(`DAG.md`) 병렬 폭과 자원 충돌을 미리 검사하고, 세션을 여는 **구동 스크립트**(`loop-drive`)를 써서 시험 실행까지 합니다. 자세한 내용은 [개발 루프](loop.md).
**세팅 때 묻는 것**: 병렬 여부(기본 예), 동시 에이전트 수, 슬롯 간 DB·포트 격리 방식(테스트가 DB 를 쓰면 슬롯별 DB 추천), 역할별 모델(모르면 "추천대로"), 미활성 게이트를 단 채 완료를 허용할지.
**산출물**: `loop_setup/LOOP.md`·`DAG.md`, `harness_setup/scripts/dag-render.*`·`loop-drive.*`, `STATE.md` 에 재시도·승인·배정 절 추가

이 스킬은 루프를 **세우기만** 하고 돌리지 않습니다. 문서를 다 쓴 뒤 "첫 사이클을 시작할까요?"라고 묻습니다.

### `loop-update` — 루프 갱신

**언제**: 태스크가 추가되어 DAG 가 달라졌을 때, 동시 수·격리 방식·모델을 바꿀 때, 루프가 같은 자리에서 반복해 멈출 때, 이전 버전이 만든 `LOOP.md` 를 새 구조로 옮길 때.
**하는 일**: `LOOP.md` 를 부분 수정합니다. 재시도 3회·분리 검증·게이트 4개 같은 고정 규칙은 건드리지 않고, 멈춤 규칙을 줄이는 갱신은 사용자 확인을 받습니다.
**게이트가 실패한 것은 이 스킬을 부를 이유가 아닙니다** — 그건 루프가 실패 분류로 처리합니다.

## 프로젝트 완료 뒤 (Layer 6)

넷 다 **기존 문서를 다시 쓰지 않습니다.** 문서 뒤에 절(`## 추가 N`, `## 리팩토링 N`)을 붙이고, 플랜에는 끝번호 phase 를 더하며, 필요한 앞 스킬을 부분 갱신 모드로 부릅니다.
루프가 도는 중(`STATE.md` 에 `in_progress` 인 phase 가 있을 때)에는 시작하지 않습니다.

### `code-to-docs` — 문서 없는 코드를 올린다

**언제**: 바이브 코딩으로 만든 코드처럼 문서가 없는 프로젝트를 이 흐름으로 이어 가고 싶을 때.
**하는 일**: 코드를 읽고 "이렇게 만들자"가 아니라 **"지금 이렇게 되어 있다"** 로 PRD·TRD·아키텍처를 씁니다. 코드만으로 알 수 없는 것과 버그로 보이는 동작은 판단 없이 미결로 남깁니다.
그다음 현재 동작을 붙잡는 테스트만 쓰는 phase-01 과 하네스·루프를 세웁니다. phase-01 을 끝내면 이 플러그인으로 만든 완료 프로젝트와 같은 상태가 됩니다.

### `refactor-plan` — 리팩토링 계획

**언제**: "코드 정리하자", "라이브러리 올리자", "프레임워크 바꾸자".
**하는 일**: 범위(언어·프레임워크 교체 / 라이브러리 최신화 / 코드 정리)를 묻고 코드를 읽어 고칠 목록을 만듭니다. 통과 조건은 새 기능이 아니라 **기존 게이트 전부 통과(동작 보존)** 와 구조 조건입니다.

### `feature-add` — 기능 추가

**언제**: "xx 기능 추가하려는데".
**하는 일**: 요청이 모호하면 `idea-brainstorm` 부터, 명확하면 `prd-generator` 부터 부르되 각 문서에 `## 추가 N` 절만 붙입니다. 기존 요구사항이 바뀌면 "FR-003 수용 기준 2 를 다음으로 대체"처럼 적고 번호는 유지합니다. 끝에 기능 phase 를 더하고 하네스·루프를 갱신합니다.

### `bug-fix` — 버그 수정

**언제**: 다 만든 앱을 **쓰다가** "xx 가 안 돼"를 발견했을 때. 개발 중 게이트 실패는 루프의 일입니다.
**하는 일**: 먼저 버그인지 요구 변경인지 가립니다(고친 뒤의 동작을 새 결정 없이 한 줄로 쓸 수 없으면 `feature-add` 로). 버그면 재현 절차를 `LOG.md` 에 **고치기 전에** 적고, 고치기 전에 실패하는 회귀 검사를 게이트에 넣고, 고치고, 게이트 4개를 통과시킨 뒤 커밋합니다. 게이트가 하나라도 못 돌면 커밋하지 않고 멈춥니다.

> 사용자: '안 끝난 것만' 체크하면 목록이 싹 비어 버려.
> 에이전트: BUG-01 로 적었습니다. 원인은 `routes/tasks.js` 21행의 문자열·불리언 비교이고, 회귀 검사가 고치기 전에 2건 실패하는 것을 확인한 뒤 고쳤습니다. 게이트 4개 통과 후 커밋했습니다.

## 환경별 차이

스킬 본문(절차·판단 기준·산출물 형식)은 두 환경에서 같고, 환경마다 다른 것만 각 스킬의 `references/` 에 있습니다.

| | 클로드 코드 | 코덱스 |
|---|---|---|
| 선택지 묻기 | AskUserQuestion | 평문 번호 목록 |
| 분리 검증 세션 | `claude -p` | `codex exec` |
| 병렬 구동 | Orca 있으면 Orca 워커, 없으면 스크립트가 슬롯마다 `claude -p` | Orca 있으면 Orca 워커, 없으면 스크립트가 슬롯마다 `codex exec` |
| 다음 스킬 연결 | 자동 호출 | 다음 단계를 텍스트로 안내 |
