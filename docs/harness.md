# 검증 하네스

[← README](../README.md)

태스크 하나는 `verification` 에 적힌 게이트를 **`lint → unit → e2e → task_validation` 순서로** 통과해야 완료입니다. 앞이 실패하면 뒤를 돌리지 않습니다.
하네스는 "도구를 잘 골랐는가"가 아니라 세 가지로 판정됩니다.

1. **명령 한 줄로 돌고 종료 코드로 성패가 갈리는가** — 사람이 로그를 읽어야 판정되는 게이트는 게이트가 아닙니다
2. **구현한 쪽이 스스로 통과 판정을 내릴 수 없는가** — 마지막 게이트가 다른 세션에서 도는 이유입니다
3. **아직 못 도는 게이트가 '통과'로 보이지 않는가** — 테스트 0건 실행은 초록불이 되고, 초록불은 아무도 다시 안 봅니다

## 게이트 4개

| 순서 | 게이트 | 누가 판정 | 무엇을 보나 | 통과 |
|---|---|---|---|---|
| 1 | `lint` | 도구 | 문법·타입·아키텍처 규칙(계층 경계·의존 방향) | 종료 코드 0 |
| 2 | `unit` | 도구 | 단위·통합 테스트. TRD 의 필수 커버 영역 | 종료 코드 0 + 커버 조건 |
| 3 | `e2e` | 도구 | 브라우저에서 사용자 흐름(FLOW-xx). PRD 유저 스토리에서 뽑음 | 종료 코드 0 |
| 4 | `task_validation` | **다른 세션의 에이전트** | 태스크의 수용 기준이 **실행 중인 앱에서 실제로 관찰되는가** | 판정 `RESULT: PASS` |

각 게이트는 `harness_setup/quality_gates/<이름>.md` 정의서 하나입니다. 앞 셋은 정의서의 `## 명령` 을 돌려 종료 코드로 판정하고,
`task_validation` 에는 명령이 없습니다 — 그건 명령이 아니라 **새 세션을 여는 것**입니다.

## 활성 시점 — 미활성은 통과가 아니다

하네스는 코드가 0줄일 때 세워지므로 처음에는 거의 모든 게이트가 돌 수 없습니다. 그래서 게이트마다 **활성 시점**(어느 태스크가 끝나야 실제로 도는가)을 적고,
그전에는 결과가 무엇이든 `미활성` 으로 읽습니다. 0건 실행의 초록불도, 도구가 없어서 나는 빨간불도 판정에 쓰지 않습니다.

미활성 게이트를 단 채 태스크를 완료시킬지는 **사람이 정합니다.** 루프 세팅 때 한 번 물어 `STATE.md` 에 "그 게이트가 활성될 때까지"라는 기한과 함께 적고,
게이트가 활성되면 그 승인은 만료되어 루프가 스스로 지웁니다. 무기한 승인은 만들지 않습니다.

상태 어휘는 넷입니다 — `활성` / `부분 활성`(게이트 안 일부가 더 늦게 열릴 때) / `미활성` / `대기`(차단된 태스크에 걸린 흐름).

## task_validation — 왜 다른 세션인가

구현한 세션은 자기가 무엇을 **의도했는지** 압니다. 그래서 화면이 실제로 그렇게 동작하지 않아도 그렇게 보이고, 애매한 수용 기준을 자기 구현에 맞는 쪽으로 읽습니다.
나쁜 의도가 아니라 정보의 문제입니다. 그래서 코드 작성과 검증을 떼어 놓습니다.

- **주는 것**: 태스크 문서, 실행 중인 앱, `task_validation.md`(절차와 판정 형식), 필요하면 태스크가 가리키는 설계 절
- **주지 않는 것**: 구현 세션의 대화·요약·"무엇을 했는지", 통과 보고, 원인 추정, 커밋 메시지·최근 변경 파일 — **이 목록이 이 게이트의 실질입니다**

검증자는 앱을 실제로 조작해 수용 기준 한 줄마다 관찰한 증거를 적습니다. 코드를 읽고 PASS 를 주지 않고, 고치지 않고, 원인을 추정하지 않습니다.

```
TASK: phase-02-task-03
GATE: task_validation
관찰 수단: 1 | 2 | 3          (1 브라우저 조작 도구 / 2 e2e 도구로 일회성 스크립트 / 3 HTTP·DB)
RESULT: PASS | FAIL | 판정 불가 | 환경 문제
- [1] PASS — 발행 버튼을 누르자 INV-0007 이 생성되고 직전 번호와 연속됨
- [2] FAIL — 계정 B 로 A 의 인보이스 URL 을 열었더니 200 과 본문이 보임
END
```

- `환경 문제` — 앱이 안 떠서 관찰 자체를 못 했다. FAIL 이 아닙니다 (안 뜬 화면을 FAIL 로 적으면 멀쩡한 코드를 고치게 됩니다)
- `판정 불가` — 수용 기준이 관찰 가능하게 쓰이지 않았다. 태스크 문서로 돌아갑니다
- 마지막 줄 `END` 는 잘린 판정을 알아보는 표식입니다

## e2e 흔들림 규칙

같은 코드로 돌릴 때마다 결과가 다른 테스트는 꺼진 게이트와 같습니다. `e2e.md` 에 흔들림을 줄이는 규칙 표를 두고, **흔들림을 고칠 때마다 원인 패턴을 한 줄씩 더합니다.**
세팅 때 들어가는 규칙은 역할·이름 기반 선택자, 실행마다 고유한 데이터, 인증 상태 재사용, 외부 값은 실제 경로에서 읽기, 조건이 될 때까지 기다리는 단언, 전환·로드가 끝난 뒤 측정, 목록의 순서를 가정하지 않기입니다.

## 로컬 개발 환경 — `local-dev`

`harness_setup/scripts/local-dev.ps1`(Windows) 또는 `.sh` 하나로 DB·메일 캡처·앱 서버 같은 의존 서비스를 **한 명령으로 준비**합니다. TRD 의 구성 요소 표와 1:1 로 관리됩니다.

- 옵션: 초기화 `-Reset`, 상태 `-Status`, 로그 `-Logs`, 내리기 `-Down`
- **종료 코드가 실패한 단계를 구별합니다** — 0 성공 / 전제(런타임·컨테이너 엔진 없음) / 환경변수 / 의존 서비스 / 스키마·시드 / 앱. 0이 아니면 그 자체가 환경 문제이고 루프는 추측하지 않습니다
- 앱 서버는 스크립트를 부른 셸과 **분리된 프로세스**로 떠서 세션이 끝나도 살아 있습니다
- 포트·DB 이름은 환경변수에서 읽습니다. 병렬 슬롯마다 다른 값을 줄 수 있게 하기 위해서입니다

## `HARNESS.md`

하네스의 현재 상태 요약입니다 — 게이트 개요 표(정의서·명령·활성 시점·현재 상태), 로컬 개발 환경(명령·종료 코드·구성 요소 표·**공유 DB 를 쓰는 게이트**·슬롯 변수),
하네스 밖(게이트로 못 덮는 요구사항과 대신 확인하는 방법), 하네스 결정(TRD 가 비워 둔 자리를 하네스가 채운 것).
