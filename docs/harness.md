# 검증 하네스

[← README](../README.md)

하네스는 "다 됐다"를 말이 아니라 실행 결과로 판정하기 위한 장치입니다. `harness-setup`이 만들고 `harness-update`가 고칩니다.

## 네 게이트

제품 Loop는 아래 순서로 완료를 판정합니다. 앞 게이트가 실패하면 고치기 전에는 뒤로 넘어가지 않습니다.

| 게이트 | 보는 것 |
|---|---|
| `lint` | 정적 오류 |
| `unit` | 기능과 계약 |
| `e2e` | 실제 실행에서의 성공·실패 흐름(화면은 브라우저, 비화면은 CLI·HTTP·저장값 등) |
| `task_validation` | 수용 기준을 독립 세션이 직접 관찰 |

정의는 `harness_setup/quality_gates/`에 있고, 각 태스크의 `verification`이 이를 가리킵니다.
명령과 도구는 프로젝트 스택에 맞춰 에이전트가 정합니다. 코드·설정·데이터 조건이 같다는 근거가 있으면 이미 통과한 결과를 재사용하고, 같은 코드 상태의 태스크는 묶어서 검사할 수 있습니다.

## 통과로 세지 않는 것

- 종료 코드 0, 테스트 0건, 전부 skip, 서비스가 안 떠 있는 상태
- 아직 활성화되지 않은 검사(준비만 된 상태)
- 구현한 쪽의 보고나 코드 리뷰만으로 내린 판정

판정 중에 제품 코드·수용 기준·통과 단언을 고치지 않습니다(`--fix`, 스냅샷 갱신 등 포함). 실패를 넘기려고 단언을 지우거나, 검사 대상을 줄이거나, 재시도를 늘리지 않습니다.

## 독립 검증 (task_validation)

마지막 판정은 **그 변경을 구현하지 않은 별도 세션**이 맡습니다. 같은 모델이어도 되지만, 구현 대화를 이어받은 세션이나 같은 세션의 역할만 바꾼 것은 독립 검증이 아닙니다.

- 검증자에게는 요구·수용 기준·필요한 설계·실행 방법·대상 코드를 줍니다. 코드와 diff는 볼 수 있습니다.
- 구현자의 추론과 자체 판정이 담긴 기록 전체는 넘기지 않습니다.
- 검증자는 제품이나 기준을 고치지 않고, 기준별 PASS/FAIL과 재현 증거를 돌려줍니다.
- 수정이 생기면 이전 판정은 무효입니다. 다른 검증자가 다시 판정합니다.

## 다른 OS

요구에 다른 OS 동작이 있으면, 그 OS에서 실제로 실행할 수단을 직접 확인합니다(Windows라면 `wsl -l -v`로 WSL 배포판 확인 등).
수단이 있으면 게이트와 독립 검증에 넣고, 없을 때만 "미검증"으로 남깁니다. WSL로 확인한 결과는 실제 Linux 컴퓨터와 다를 수 있다는 한계도 기록합니다.

## 로컬 실행 환경

기존 실행·테스트 명령을 먼저 씁니다. 기존 명령으로 안 되는 준비만 `harness_setup/scripts/`에 스크립트로 둡니다.

- 공유 DB는 초기화·마이그레이션 명령과 실제 접속 대상을 확인합니다.
- "포트가 열렸다"만으로 준비됐다고 보지 않고 실제 요청으로 확인합니다.
- 프로세스는 직접 띄운 것만, 신원을 확인한 뒤 종료합니다.
