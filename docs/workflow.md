# 진행 방식

[← README](../README.md)

## 큰 흐름

IDEA → PRD → TRD → Architecture → Plan → Harness → Loop.

이 순서는 생각을 구체화하는 순서입니다. 모든 요청이 모든 문서를 새로 써야 한다는 뜻은 아닙니다.
문서만 원하거나 작은 수정이면 그 범위에서 끝냅니다.

## 시작 전 합의

에이전트는 먼저 사실(OS, 런타임, 설치된 도구, 현재 권한, 기존 코드와 문서)을 조사합니다. 그다음 **사용자만 정할 수 있는 것만** 한 번에 묻습니다.

- 목적과 범위, 제외할 것
- 허용할 변경과 금지 사항(외부 전송, 유료 서비스, 커밋·푸시 등)
- 시간·사용량 예산
- 역할별 기본 모델, 사용량 한도에 걸렸을 때의 처리(기다렸다 재개 / 허용한 다른 모델 / 중단)
- 실행 환경(Orca / 일반 / 그 밖의 도구)

합의는 `docs/PRD.md`의 `## 자율운영 합의`에 남고, 이후 세션도 같은 합의를 이어받습니다. 이미 정한 것은 다시 묻지 않습니다.

## 단계 승인

- 기본은 **단계마다 결과와 다음 스킬을 제안하고, 승인을 받은 뒤 이어 가는 것**입니다.
- 요청이나 합의에서 이후 단계를 권한·예산과 함께 밝혔다면 그 범위는 연속으로 진행합니다. 예: "루프까지 묻지 말고 진행해, 예산 1시간"
- "만들어줘"만 했거나, 아무 말이 없었거나, 에이전트가 스스로 채운 합의는 다음 단계 승인으로 보지 않습니다.
- **Loop가 시작된 뒤에는 질문하지 않습니다.** 합의 밖의 새 결정이 필요해지면 그 일에 영향받는 작업만 멈추고 나머지를 끝낸 뒤, 결정할 내용을 최종 보고에 남깁니다.

## 화면 제품의 디자인 선택

화면이 있는 제품은 PRD 다음, 본격적인 화면 구현 전에 **실제로 렌더링된 디자인 미리보기**를 보여 주고 사용자가 최종 방향을 고릅니다.
현재 환경에서 가능한 수단(아티팩트, 로컬 페이지, 이미지 등)을 쓰며, 말로 된 설명만으로 대신하지 않습니다.

- 선택한 방향·버전·범위·시각 품질 기준은 `docs/DESIGN.md`에 남습니다.
- 승인 전에는 임시 디자인으로 화면을 완료 처리하지 않습니다.
- 이미 승인한 디자인을 유지하는 수정이나 화면 없는 작업에는 새 승인을 요구하지 않습니다.
- 디자인 승인은 기능 검증을 대신하지 않습니다. 구현 결과는 승인된 방향과 실제 화면으로 대조합니다.

## 뒤 단계에서 결정이 바뀔 때

설계나 구현 중에 앞의 결정이 바뀌면, 영향받는 앞 문서(IDEA 포함)의 해당 부분만 고치고 근거를 남깁니다.
범위·수용 기준·사용자 제약이 바뀌는 일은 사용자에게 묻습니다. Loop 중이라면 그 부분만 멈추고 최종 보고에서 묻습니다.
