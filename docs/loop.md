# 개발 루프

[← README](../README.md)

`loop_setup/LOOP.md` 는 개발 프로세스의 **헌법**입니다. 독자는 사람이 아니라 다음 세션의 에이전트이고, 세션은 계속 끊깁니다.
모든 세션은 `LOOP.md` → `STATE.md` 를 읽고 시작합니다.

## 한 태스크는 세 토막, 토막마다 세션이 다르다

| 토막 | 하는 일 |
|---|---|
| **구현** | 배정받은 태스크 → 시작 전 하네스 점검 → 구현 → `local-dev` → `lint`·`unit`·`e2e` → 결과를 넘기고 종료 |
| **검증** | 새 세션이 `task_validation` 만 돌려 판정을 내고 종료 |
| **반영** | 판정을 기록 → PASS 면 병합·완료·커밋·phase 판정 / FAIL 이면 원인 분류 → 같은 자리에서 다시 수정 |

검증이 별도 세션이면 검증 앞과 뒤도 같은 세션일 수 없어서 토막이 셋입니다. 태스크가 끝나면 세션을 닫습니다 — 이어서 다음 태스크를 하면 다음 검증이 오염된 채로 시작합니다.

## 실패 처리 — 분류가 먼저, 코드 수정은 3회

| 분류 | 알아보는 법 | 고칠 곳 | 재실행 |
|---|---|---|---|
| 진짜 결함 | 같은 순서를 수동으로 밟아도 같은 결과 | 코드 | 최대 3회, 처음부터 |
| 낡은 스펙 | 화면·규약이 의도적으로 바뀜 | 테스트·흐름 정의 | 1회, 실패한 게이트부터 |
| 환경 문제 | `local-dev` 가 0 이 아닌 코드로 끝남 | 환경 재준비 | 1회 |
| 흔들림 | 같은 코드인데 결과가 다름 | 그 테스트 | 1회 |
| 판정 불가 | 수용 기준이 관찰 가능하지 않음 | 태스크 문서 | 즉시 중단 |

3회는 **코드를 고치는 예산**이라 진짜 결함만 셉니다. 소진하면 멈추고 사람에게 묻습니다("이어서" 또는 "건너뛰라"). 3회는 원본 설계가 못 박은 값이라 루프가 조정하지 않습니다 —
세 번이 부족하게 느껴지면 대개 환경 문제나 흔들림이 예산을 먹은 것이고, 답은 분류를 제대로 하는 것입니다.

**여러 태스크에 걸친 같은 실패도 셉니다.** 실패는 `LOG.md` 에 `- 실패: <태스크> / <게이트> / <검사 ID> / <분류>` 형식으로 남고,
같은 검사가 서로 다른 두 태스크 이상에서 실패하면 루프가 하네스를 고치거나(스스로 할 수 있는 범위), 할 수 없으면 새 배정을 멈추고 묻습니다.
태스크마다 카운터가 리셋되는 구조에서 같은 낭비가 계속 반복되는 것을 막기 위해서입니다.

## 기록 — `STATE.md` 와 `LOG.md`

- 기록은 완료 시점만이 아니라 **시작·전이·완료 세 번**입니다. 세션은 구현 중에 가장 많이 끊기기 때문입니다
- 쓰는 순서는 태스크 문서 `status` → `STATE.md` → `LOG.md` → 커밋이고, 어긋나면 태스크 문서가 이깁니다
- `STATE.md` 는 "지금 어디인가", `LOG.md` 는 "무슨 일이 있었는가"(append-only). 새 상태 파일은 만들지 않습니다

## 구동기 — 세션을 누가 여는가

"한 태스크에 한 세션"은 누군가 세션을 계속 열어 줘야 성립합니다. 루프 세팅이 **구동 스크립트**(`harness_setup/scripts/loop-drive.*`)를 만들고, 그 스크립트가 세션을 엽니다.
스크립트는 판단하지 않습니다 — 띄우고 기다릴 뿐이고, 판단(결과 반영·실패 분류·다음 배정)은 매 라운드 새로 여는 **코디네이터** 세션이 합니다.

| 모드 | 워커를 띄우는 수단 | 언제 |
|---|---|---|
| ① 스크립트 구동 | 스크립트가 `claude -p` / `codex exec` 를 슬롯마다 띄움 | Orca 가 없을 때의 기본 |
| ② Orca 스크립트 구동 | Orca 터미널 안의 스크립트가 `orca orchestration worker-start` 로 띄우고 결과를 기다림. 워커의 질문은 별도 세션이 문서를 보고 답하거나 사람에게 올림 | Orca 가 있을 때의 기본 |
| ③ 서브에이전트 | 상위 세션이 Agent 도구로 띄움 | 클로드 코드 전용 대안 |

코디네이터를 대화 세션으로 계속 살려 두지 않는 이유는 비용입니다. 기다리는 동안 상태를 확인할 때마다 커진 대화 전체를 다시 읽게 되고, 실사용 프로젝트에서는 이것이 전체 토큰의 약 30%였습니다.
phase 가 바뀌어도 스크립트는 그냥 이어 가고, 코디네이터는 매 라운드 빈 컨텍스트로 시작합니다.

자식 세션은 사람에게 물을 수 없으므로 물을 일이 생기면 `STATE.md` 에 `질문:` 을 남기고 끝납니다. 권한은 허용 목록으로 주고 토막마다 다릅니다 — 검증 세션에는 쓰기와 git 을 주지 않습니다.
(단, Orca 워커에는 허용 목록을 줄 수 없어 사용자의 에이전트 권한 설정을 따릅니다. 루프 세팅이 무엇을 허용해야 하는지 안내합니다.)

## 병렬 운용

태스크가 파일 단위로 잘려 있고 `depends_on`·`files` 가 다 적혀 있으므로 **기본은 병렬**입니다. 병렬은 **현재 phase 안의 태스크들** 사이이고 phase 사이는 순서대로입니다.

- **DAG**: `dag-render` 스크립트가 태스크 frontmatter 로 `loop_setup/DAG.md` 를 만듭니다 — 머메이드 그래프, 구간별 병렬 폭(동시에 열 수 있는 태스크 수), 순환·잘못된 참조 확인, 파일이 겹치는 태스크 쌍. 이 그림으로 실행 순서를 검토합니다
- **자원 충돌 사전 검사**: 같은 파일을 고치는 태스크, 마이그레이션·설정처럼 공유되는 자원을 쓰는 태스크를 세팅 때 검사해 동시에 돌리지 않을 쌍을 표로 남깁니다
- **배정**: 워커는 스스로 태스크를 고르지 않습니다. 코디네이터가 열 수 있고 충돌 없는 태스크를 빈 자리(슬롯)만큼 나눠 줍니다. 문서(`STATE.md`·`LOG.md`·태스크 문서)는 코디네이터만 씁니다
- **작업 자리**: 기본 브랜치(`main`)에서는 아무도 작업하지 않습니다. 코디네이터와 첫 워커는 코디네이터 워크트리에서, 동시에 코드를 쓰는 둘째 워커부터는 각자 워크트리에서 돕니다.
  검증을 통과한 태스크만 병합되어 `main` 에 들어오므로 `main` 은 언제나 '검증된 최신'이고, 사용자가 중간에 살펴봐도 됩니다
- **격리**: 슬롯마다 앱 포트와 DB 를 환경변수로 나눕니다(방식 셋 중 세팅 때 선택). 테스트가 DB 를 쓰면 슬롯별 DB 를 추천합니다 — 격리 없이 앱 쓰는 게이트만 순서대로 돌리는 방식에서도 unit 테스트는 병렬로 돌아 공유 DB 에서 서로의 데이터를 건드리기 때문입니다
- **에이전트 혼용**: Orca 는 워커마다 에이전트를 고를 수 있어 구현은 Claude, 검증은 Codex 처럼 섞을 수 있습니다. 검증을 다른 에이전트로 두면 분리가 한 겹 더 강해집니다

병렬을 끄면 단일 모드로 돌고, 폭이 1인 구간은 병렬이 켜져 있어도 단일과 같습니다.

## phase 완료와 사람을 부르는 곳

phase 는 **태스크 전부 완료 + phase 수용 기준 충족 + phase 완료 묶음**(느려서 매 태스크에서 빼 둔 e2e 흐름) 통과, 셋 다여야 완료입니다.
현재 phase 가 완료되기 전에는 다음 phase 의 태스크를 열지 않습니다.

루프가 사람을 부르는 것은 `STATE.md` 의 `질문:` 하나로 모입니다.

- 코드 수정 3회 소진, 판정 불가, 미활성 게이트 승인, 차단 대기, phase 완료 묶음 실패
- 여러 태스크에 걸친 같은 실패를 스스로 고칠 수 없을 때
- **phase 를 열 때**: 처리되지 않고 기한이 지난 `알림:`(루프가 다른 담당에게 넘긴 메모)과 판단 시점이 온 미결 사항을 한 번에 모아 묻습니다

그 밖에는 멈추지 않습니다. 모든 phase 가 끝나면 구동 스크립트가 멈추고, 그 뒤의 기능 추가·버그 수정·리팩토링은 [완료 뒤 스킬](skills.md#프로젝트-완료-뒤-layer-6)이 이어 갑니다.
