# Claude Code 환경 보조 지침 (trd-generator)

## 프로젝트 여건은 AskUserQuestion 으로

2단계의 여건 확인(인원·기간·익숙한 스택·운영 인력·예산·기존 자산·배포 대상·OS)은 `AskUserQuestion` 으로 묻는다.
평문으로 나열하면 사용자가 앞의 두세 개만 답하는데, 여건 하나가 빠지면 그 위에서 고른 스택이 통째로 어긋난다.

- 한 번의 호출에 최대 4개까지 묶되, **앞의 답에 따라 뒤 질문의 선택지가 달라지는 것은 묶지 않는다.**
  (운영 인력의 답이 배포 방식 선택지를 바꾸므로 이 둘은 같은 호출에 넣지 않는다)
- `option.description` 에는 그 선택이 **어느 영역의 결정을 좁히는지** 적는다.
  ("운영 인력이 없으면 직접 관리하는 인프라 후보가 전부 탈락하고 관리형 서비스만 남습니다.")
- **여건은 객관식으로 물어도 안전하다.** 사용자가 아는 사실이기 때문이다.
  반대로 8단계 미결 중 '확인'·'실험'·'유예'는 객관식으로 묻지 않는다 — 모르는 것을 찍게 만들고, 그 답이 확정된 합의로 문서에 박힌다.
- 예산과 기간에는 **범위를 좁히는 선택지를 항상 하나 포함한다.** 여건을 넉넉히 잡으면 스택이 부풀고, 부푼 스택은 Layer 3에서 태스크로 돌아온다.

## PRD 읽기와 기존 코드베이스 확인

`docs/PRD.md` 는 Read 로 전문을 읽는다. 특히 5절(NFR), 8절(가정과 미결), 9절(추적표)은 TRD의 뼈대가 되므로 요약하지 말고 그대로 본다.

기존 코드베이스가 있으면 Glob·Grep으로 실제 스택을 확인한 뒤 쓴다. 패키지 매니페스트, 락 파일, 설정 파일, CI 설정, 컨테이너 정의가
가장 빠른 단서다. 서브에이전트를 쓸 수 있으면 Explore 에이전트에게 "현재 사용 중인 언어·프레임워크·저장소·배포 방식과 그 근거 파일"을
조사시키고, 그 결과를 1.3절 '기존 자산'으로 삼는다. 이 확인 없이 쓴 TRD는 이미 쓰고 있는 것을 바꾸자고 제안하게 된다.

## 스파이크가 필요한 결정

8단계에서 '실험'으로 분류한 미결은 서브에이전트에게 실제로 재 보게 할 수 있다.
다만 **여기서 성급히 구현하지 않는다.** TRD 단계의 스파이크는 "그 숫자가 나오는지"만 확인하는 최소 코드이고,
결과는 TRD 12절에 판정과 함께 적는다. 코드 자체는 남기지 않거나 별도 경로에 둔다 — 아직 태스크가 아니기 때문이다.

## 파일 작성과 검토 요청

`docs/TRD.md` 는 Write 도구로 만든다. 이미 있으면 덮어쓰기 전에 읽고, 버전을 올릴지 새로 쓸지 확인한다.

작성 후 7단계 보고에서 **되돌리기 비용이 큰 결정 3개**를 먼저 보여 주고, 사용자가 그중 바꾸고 싶은 것이 있는지
`AskUserQuestion` 으로 한 번 묶어 확인하는 것이 좋다. 이 결정들이 아키텍처의 전제가 되므로 여기서 미루면 다음 스킬이 다시 멈춘다.
