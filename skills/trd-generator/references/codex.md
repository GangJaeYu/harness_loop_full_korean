# Codex 환경 보조 지침 (trd-generator)

## 프로젝트 여건은 번호 목록으로 한 번에

선택지 UI가 없으므로, 2단계의 여건 확인은 **표 하나로 모아서** 제시하고 한 번에 답을 받는다.
질문을 여러 턴에 흩뿌리면 답이 누락되고, 누락된 여건 위에서 스택을 고르게 된다.

```
아래만 알려주시면 TRD를 쓸 수 있습니다. ("1-B, 2: 파이썬/리액트, 3-A, ..." 형태로 답해 주셔도 됩니다.)

1. 개발 인원과 기간은?
   A) 1인 · 3개월 이내   → 관리형 서비스 위주. 직접 운영하는 구성 요소를 최소화
   B) 2~3인 · 6개월      → 선택지가 넓어짐
2. 팀이 이미 잘 다루는 언어·프레임워크는? (자유 서술)
3. 운영할 사람이 따로 있나요?
   A) 없다 (개발자가 겸함)  → 직접 관리하는 인프라 후보 전부 탈락
   B) 있다
...
```

각 선택지에는 반드시 **그 선택이 어느 영역의 후보를 좁히는지**를 붙인다. 영향 감각 없이 고르면 팀이 감당 못 하는 스택이 나온다.

목록에는 사용자가 **아는 사실**만 올린다. 8단계 미결 중 '확인'·'실험'·'유예'는 객관식으로 묻지 않는다 —
사용자는 모르는 것을 찍게 되고 그 답이 확정된 합의가 된다. 이 셋은 미결 표에 해소 경로를 적고 넘어간다.

## PRD 읽기와 기존 코드베이스 확인

`docs/PRD.md` 는 전문을 읽는다. 5절(NFR), 8절(가정과 미결), 9절(추적표)은 TRD의 뼈대이므로 요약본으로 대체하지 않는다.

기존 프로젝트라면 셸에서 패키지 매니페스트, 락 파일, CI 설정, 컨테이너 정의를 먼저 확인하고 현재 스택을 파악한다.
추측으로 현재 상태를 적지 않는다. 기존 프로젝트의 TRD는 "무엇을 고를까"가 아니라 "무엇이 이미 정해져 있고 무엇을 바꿀 것인가"다.

## 파일 작성

`docs/TRD.md` 는 파일 쓰기 도구나 heredoc으로 만든다. 표가 많으므로 마크다운 표 정렬이 깨지지 않는지 작성 후 확인한다.
승인 모드에 따라 쓰기 권한 요청이 필요할 수 있으니, 작성 직전에 경로를 알린다.

스파이크가 필요한 결정은 여기서 구현하지 않는다. 무엇을 만들어 무엇을 재면 판정되는지만 12절에 적고,
실제 실행은 Layer 3의 검증 태스크로 넘긴다.
