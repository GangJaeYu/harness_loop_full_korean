# 개발 루프 갱신 (Layer 5)

## 이 스킬의 목적

`LOOP.md` 는 원본 사양이 **개발 프로세스의 헌법**이라고 부른 문서다.
그런데 헌법도 한 번 쓰고 끝나지 않는다 — **미결이 닫히고, 운용 방식이 바뀌고, 규칙이 현실과 어긋난다.**
원본 사양이 "필요한 경우 적극적으로 LOOP.md는 업데이트되어야 한다"고 적은 것이 이 자리다.

**그런데 이 스킬에는 다른 갱신 스킬에 없는 위험이 하나 있다.**

```
LOOP.md 에 적힌 규칙의 절반은 루프를 '멈추게 하는' 것이다
   재시도 3회 · 분리된 검증 세션 · 미활성은 통과가 아니다 · 범위를 넘지 않는다
그리고 그 규칙에 걸리는 쪽과 그 규칙을 고칠 수 있는 쪽이 같다
   → 막혔을 때 가장 빠른 해결은 언제나 자기를 멈춘 규칙을 지우는 것이다
```

**그래서 이 스킬의 절반은 무엇을 고쳐도 되는지가 아니라 무엇을 고치면 안 되는지에 대한 것이다.**
하네스가 조용히 죽는 방식이 "기준을 낮추는 것"이라면, 루프가 조용히 죽는 방식은
**"멈추게 하는 규칙을 하나씩 지우는 것"**이다. 둘 다 기록에는 통과율이 올라간 것으로만 남는다.

### 여기서 하는 일과 하지 않는 일

| 하지 않는 것 | 어디서 하는가 |
|---|---|
| 루프를 처음 세우는 것 | `loop-setup` — `loop_setup/LOOP.md` 가 없으면 그쪽이다 |
| 게이트가 무엇을 검사하고 어떤 명령으로 도는지 고치는 것 | `harness-update` |
| 활성 시점·E2E 흐름 목록·`local-dev` 스크립트를 고치는 것 | `harness-update` |
| 태스크·phase·수용 기준·`verification` 을 고치는 것 | Layer 3 (`plan-generator` 10단계 부분 갱신) |
| 태스크 코드를 고치는 것 | 루프를 **도는** 세션 |
| `STATE.md` 의 **값**을 고치는 것 | 루프를 도는 세션. 여기서는 **절의 형식**을 넓힌다 (5단계) |
| 만료된 승인을 정기적으로 정리하는 것 | 루프가 매 사이클 스스로 한다. 여기는 **놓쳤을 때의 안전망**이다 |
| 실패한 게이트에 대응하는 것 | 루프를 도는 일이다. `LOOP.md` 의 실패 분류가 이미 정해 두었다 |

**형식은 새로 정하지 않는다.** 사이클 단계, 분류 표의 열, `Retry` 절의 필드, 미결 표의 모양은
`loop-setup` 의 산출물 템플릿에 이미 있다. 여기서 다시 정하면 두 스킬이 다른 형식을 만들고,
갱신을 한 번 돌릴 때마다 문서가 조금씩 달라진다. **기존 파일의 형식을 그대로 따라 쓴다.**

## 0단계. 언제 이 스킬을 부르는가

### 부르는 자리

| 언제 | 무엇을 고치나 |
|---|---|
| **세팅 때 병렬을 껐다가 켤 때** | 격리 미결을 닫고 슬롯·배정·필자 규칙을 켠다. **`loop-setup` 이 그 경우에만 미결을 남긴다**(기본은 병렬이라 보통 이미 켜져 있다) |
| 병렬을 끌 때 | 병렬 전용 규칙을 되돌리고 구동기를 ①-단일로 |
| 동시 에이전트 수 상한·슬롯 규칙·격리 방식이 바뀜 | 8절의 폭 표·슬롯 표·환경변수 표 |
| `local-dev` 가 슬롯 변수를 읽게 됨 (`harness-update` 완료) | 9절의 "격리 적용 대기"를 지우고 폭 1 제한을 푼다 |
| **미결(OQ)이 닫힐 때** | 그 미결에 걸려 있던 잠정 규칙을 확정 규칙으로 |
| 만료된 승인이 남아 있을 때 | 지운다. **다만 이건 루프가 매 사이클 스스로 하는 일이고, 여기는 놓쳤을 때의 안전망이다** |
| `local-dev` 의 명령·옵션이 바뀜 | `LOOP.md` 에 실제 값으로 적힌 곳 |
| `task_validation` 의 분리 수단이 바뀜 | 세션 경계 절과 호출 지시문 |
| 구동기 모드가 바뀜 (스크립트 ↔ 오르카 ↔ 서브에이전트) | 세션 경계 절의 구동기 블록 — 지시문·허용 목록·판정 블록 수집 경로 |
| 역할별 모델이 바뀜 (모델 은퇴·요금제 한도·품질 문제·"이어서" 재배정으로 한 급 올림) | 8절 "에이전트·모델 배치" 표 한 곳. 지시문·스크립트에 이름이 박혀 있으면 표 참조로 바꾼다 |
| 태스크가 추가·삭제됨 | `dag-render` 를 다시 돌려 `loop_setup/DAG.md` 를 갱신하고, **자원 충돌 표**·**구간별 병렬 폭** 요약을 다시 만든다 |
| **②가 상주 코디네이터 구조다** — 대화형 코디네이터가 phase 내내 살아 있거나, phase 마다 코디네이터를 새 터미널로 띄우는 교체 명령·시작 프롬프트가 8절에 있다(2026-09-23 이전 `loop-setup` 산출물), 또는 phase 마다 사람이 코디네이터를 연다 | ②를 **구동 스크립트 + 라운드별 판단 자식** 구조로 옮긴다 — 아래 "1.10.0 이전 `LOOP.md` 를 옮길 때" |
| **트리거가 알림으로만 쌓인다** — `Next Action` 에 `알림:` 이 여러 phase 에 걸쳐 쌓여 있고, 그중 조건이 이미 충족된 것(반복 흔들림·판단 시점이 지난 미결)이 있다 | 반복 판정·`알림(<주체>, ~<만료>)` 형식·phase 를 열 때의 확인(0절 7번)을 넣고, 쌓인 알림을 분류한다 — 같은 절 |
| **격리 3인데 DB·앱을 쓰는 테스트가 여러 태스크에 걸쳐 흔들린다** | 격리 부족이다. 격리를 1·2로 올린다(8절 슬롯 표·환경변수 표, `e2e 대기` 토막 제거). `local-dev` 가 슬롯 변수를 읽게 하는 것은 `harness-update` 의 일이라 함께 부른다 |
| `harness-update` 가 게이트 구성을 바꿈 | 루프가 읽는 자리(정의서 이름, 활성 시점 출처)가 달라졌는지 |
| **같은 자리에서 반복해 멈춘다** | 규칙이 현실과 어긋난 곳. **아래를 먼저 읽는다** |

### 부르지 않는 자리

- **게이트가 실패했을 때** — 그건 루프를 도는 일이다. `LOOP.md` 의 분류가 코드·하네스·태스크 문서 중
  어디로 갈지 이미 정해 두었고, 그중 어디에도 "`LOOP.md` 를 고친다"는 없다
- **태스크가 어려울 때** — 규칙이 아니라 그 태스크의 문제다
- **재시도 3회를 다 썼을 때** — 그때 할 일은 **사용자에게 보고**하는 것이다.
  여기서 이 스킬을 부르면 한도를 늘리는 갱신으로 끝나고, 그건 정확히 3회 상한이 막으려던 것이다

**"규칙이 나를 멈춰 세웠다"는 갱신의 이유가 아니다.** 그건 규칙이 제 일을 하고 있다는 뜻이다.

### 같은 자리에서 반복해 멈추는 것은 다르다

한 번 걸린 것은 규칙이 작동한 것이지만, **여러 태스크에서 같은 규칙에 같은 방식으로 걸리면**
규칙이 현실과 어긋났을 가능성이 있다. 구별하는 방법은 **무엇을 바꾸면 안 걸리는가**를 보는 것이다.

| 상황 | 무엇이 문제인가 |
|---|---|
| 태스크마다 `files` 밖의 설정 파일을 고쳐야 통과한다 | **플랜의 문제.** 그 파일이 어느 태스크의 `files` 에도 없다 → Layer 3 |
| 매번 같은 흐름이 흔들려 멈춘다 | **하네스의 문제** → `harness-update`. **단 격리 3에서 DB·앱을 쓰는 테스트라면 루프의 문제**(격리 부족) → 여기서 격리를 올리고 `harness-update` 를 함께 |
| 같은 태스크가 3회 소진을 반복하는데 분류는 매번 `진짜 결함` 이다 | 플랜·하네스가 아니면 **워커 급의 문제일 수 있다.** 그 태스크만 구현 워커를 한 급 올려 재배정한다(8절 표의 "올리는 조건"). 전체를 올리지 않는다 |
| 미활성 승인을 태스크마다 다시 묻고 있다 | **루프의 문제.** `Standing Decisions` 의 범위가 너무 좁다 → 여기 |
| 병렬 중 `Retry` 절이 서로 덮어써진다 | **루프의 문제.** 절 형식과 필자 규칙이 단일 에이전트 전제다 → 여기 (5단계) |

**앞 둘은 이 스킬이 아니다.** 여기서 고치면 다른 레이어의 결함을 루프 규칙으로 덮는 것이 되고,
덮인 결함은 다음 phase 에서 더 크게 돌아온다.

## 1단계. 무엇이 바뀌었는지부터 읽는다

**고칠 곳을 정하기 전에 지금 상태를 읽는다.** 루프 규칙은 진행 상황을 전제로 쓰였다.

| 읽을 것 | 무엇을 얻는가 |
|---|---|
| `loop_setup/LOOP.md` | 지금 규칙. **미결 절에 무엇이 열려 있는가** |
| `plan_setup/STATE.md` | 지금 어느 phase·태스크인가. `Retry` 와 `Standing Decisions` 의 현재 내용 |
| `plan_setup/LOG.md` | **반복되는 실패와 반복되는 중단이 여기 쌓여 있다.** 갱신의 근거는 대개 여기 있다 |
| `harness_setup/HARNESS.md` | 게이트별 **현재 활성 상태** — 만료시킬 승인이 있는지 |
| `harness_setup/quality_gates/*.md` | 게이트 구성이 바뀌었는지 (정의서 이름, 활성 시점 절의 유무) |
| `harness_setup/scripts/` | `local-dev` 의 실제 명령·옵션이 `LOOP.md` 에 적힌 것과 같은지 |
| 태스크 문서 frontmatter | 태스크가 늘었으면 **DAG 와 폭을 다시 잰다** |

**`loop_setup/LOOP.md` 가 없으면 이 스킬을 쓰지 않는다.** 갱신할 대상이 없다. `loop-setup` 을 제안한다.

## 2단계. 갱신을 세 등급으로 나눈다

| 등급 | 무엇인가 | 어떻게 하는가 |
|---|---|---|
| **① 상태 반영** | 이미 일어난 사실을 규칙에 맞추는 것 — 만료된 승인 정리, 바뀐 옵션 반영, 다시 잰 폭 | **그냥 한다.** 보고에 한 줄 |
| **② 규칙 추가** | 규칙을 늘리거나 조이는 것 — 격리 규칙 확정, 병렬 운용 규칙, 절 형식 확장 | 한다. **매 사이클에 얼마나 붙는지**를 보고한다 |
| **③ 완화** | 루프를 멈추게 하는 것을 줄이거나 늦추는 것 | **사용자 승인 없이는 하지 않는다** |

①이 갱신의 대부분이다. **①을 미루면 규칙이 실제와 어긋나고, 어긋난 규칙은 다음 세션이 무시하기 시작한다** —
한 줄이 틀린 것을 알면 나머지도 의심하게 되기 때문이다. 망설일 이유가 없다.

### 무엇이 ③ 완화인가

| 완화 | 왜 완화인가 |
|---|---|
| 코드가 아닌 갈래의 재실행을 1회보다 늘린다 | 아무것도 검증하지 않는 실행이 늘어난다 |
| 미활성 승인의 범위를 **무기한**으로 넓힌다 | 그 게이트가 활성돼도 아무도 다시 보지 않는다 |
| 태스크 간 반복 감지(`LOG.md` 흐름 ID)를 끈다 | 같은 낭비가 태스크마다 반복되는 것을 못 잡는다 |
| 반복 판정을 지시문에서 빼거나, 걸렸을 때 `질문:` 대신 `알림:` 으로 넘기게 한다 | 규칙은 남아도 아무도 실행하지 않는다 — 실전에서 이렇게 여섯 phase 를 흔들림 위에서 돌았다 |
| `알림:` 의 만료나 phase 를 열 때의 확인(0절 7번)을 뺀다 | 충족된 트리거가 사람 눈에 안 띄는 목록으로 쌓인다 |
| 기록 시점을 시작·전이·완료에서 줄인다 | **세션이 끊겼을 때 복구가 안 된다.** 가장 눈에 안 띈다 |
| 불일치 복구 규칙을 뺀다 | 위와 같다 |
| 태스크 선택에서 `depends_on`·`blocked` 확인을 뺀다 | 열리지 않은 태스크를 구현하게 된다 |
| 범위 확장 금지(`files`·`architecture`)를 푼다 | 검증받지 않은 변경이 커밋에 섞인다 |
| 커밋을 게이트 통과 전으로 옮긴다 | 검증받지 않은 상태가 기본선이 된다 |
| phase 완료 묶음 실패를 통과로 읽게 한다 | 그 흐름들은 영원히 안 돈다 |
| 병렬 폭 측정을 생략한다 | 병렬 결정의 근거가 사라진다 |

**③은 거절이 아니라 확인이다.** 사용자가 직접 요청한 경우에도 마찬가지다 —
**결과를 제시하고 확인받은 뒤 적용한다.** "기록을 완료 시점 하나로 줄인다"와
"세션이 중간에 끊기면 그 태스크를 처음부터 다시 한다"가 같은 말인데 앞쪽으로만 들리기 때문이다.
확인 뒤에는 그대로 하고, 무엇을 왜 줄였는지를 기록에 남긴다.
대화할 수 없는 상황이면 적용하지 말고 결과와 대안을 적어 사용자에게 넘긴다.

**"지금 자꾸 걸려서"는 완화의 이유가 아니다.** 정당한 경우는 **그 규칙이 더 이상 유효하지 않을 때**뿐이다 —
운용 방식이 실제로 바뀌었거나(단일 → 병렬), 그 규칙이 전제하던 것이 사라진 경우.

## 3단계. 고칠 수 없는 것

**완화 승인을 받아도 이 스킬이 고치지 못하는 것이 있다.** 다른 곳에서 정해져 내려온 것들이다.

| 고정된 것 | 누가 정했나 | 바꾸려면 |
|---|---|---|
| **재수정 사이클 최대 3회** | 원본 사양이 문장으로 못 박음 | 원본 사양을 고치는 결정. 사용자에게 그렇게 보고한다 |
| **한 태스크에 한 세션** | 원본 사양 | 위와 같다 |
| **`task_validation` 은 분리된 세션에서** | 원본 사양 + Layer 4 | 위와 같다 |
| **멀티 에이전트 시 DAG 구현** | 원본 사양 | 위와 같다 |
| 게이트 넷과 그 이름·순서 | Layer 4 | `harness-update` 도 못 바꾼다. 원본 사양이다 |
| 상태 어휘 넷 (`활성`·`부분 활성`·`미활성`·`대기`) | Layer 4 | 새 이름을 만들지 않는다 |
| 기록처는 `STATE.md`·`LOG.md` 둘뿐 | Layer 4 | 셋째를 만들지 않는다 |

**"3회를 늘려 달라"는 요청은 여기로 온다.** 상한을 지우는 대신 답할 것이 있다 —
세 번이 부족했던 이유는 대개 그중 몇 번이 **환경 문제나 흔들림에 소모된 것**이고,
그 답은 상한 제거가 아니라 분류를 제대로 하는 것이다. `LOG.md` 를 보면 실제로 그런지 알 수 있고,
**그렇지 않다면 그건 원본 사양을 다시 볼 문제**이지 루프 문서에서 조용히 바꿀 일이 아니다.

**미결을 닫을 때가 가장 실수하기 쉽다.** 미결 표의 행을 지우고 끝내면 결정이 어디에도 안 남는다.
**결정은 본문의 규칙이 되어야 하고, 미결 표에서는 사라져야 한다.** 둘 다 해야 한 번 닫힌 것이다.

## 5단계. 병렬로 켤 때 `STATE.md` 를 꼬이지 않게 하는 두 규칙

**멀티 에이전트를 켜는 갱신에서 이 둘을 빼면 기록이 반드시 깨진다.** 서로 다른 문제이고 해법도 다르다.

### (가) 칸이 모자란다 — 형식을 넓힌다

`Current Task` 는 값 하나, `Last Verification` 은 "지금 상태 한 줄", `Retry` 는 태스크 하나를 담는다.
넷이 동시에 돌면 **넣을 자리가 없다.** 태스크별 블록이나 목록으로 넓힌다.

**넓힐 때 기존 값을 새 형식으로 옮긴다.** 지우고 새로 만들면 **진행 중인 태스크의 재시도 이력이 사라지고**,
그 태스크는 다음 세션에서 앞의 시도를 처음부터 반복한다. 넓히는 것이 목적이지 초기화가 아니다.

**`Current Task`·`Last Verification` 은 Layer 3이 만든 절이다.** 병렬에는 정말 필요하므로 넓히되,
**Layer 3이 초기화한 형식을 바꾸는 일이므로 ②로 분류해 보고에 올린다.** 조용히 바꾸면
`plan-generator` 의 형식 규칙과 실제 파일이 갈라지고, 다음에 누가 맞는지 아무도 모른다.

### (나) 동시에 쓰다가 서로 덮어쓴다 — 필자를 하나로 줄인다

칸을 나눠 줘도 **파일 쓰기는 통째로** 일어나므로 "각자 자기 줄만 고친다"로는 여전히 잃는다.
**잠금으로 풀지 않는다** — 잠근 채로 죽은 에이전트가 전체를 세우고, 그건 병렬의 이득을 통째로 지운다.

| 무엇 | 병렬에서 누가 쓰나 |
|---|---|
| 태스크 문서의 `status` | **코디네이터만 자기 트리에서.** 슬롯 브랜치가 문서를 고치면 `failed`·"이어서" 경로에서 병합 충돌이 난다 — 슬롯은 코드만 바꾼다 |
| 하네스 문서 (`harness-update`) | **코디네이터만 자기 트리에서.** 워커는 `하네스 부족` 으로 돌려보낸다 |
| `STATE.md` | **orchestration 만** |
| `LOG.md` | **orchestration 만.** 에이전트는 판정 블록을 넘기고 병합 순서대로 append 된다 |

**이 분업이 맞는 이유는 루프가 이미 갖고 있다** — "어긋나면 태스크 문서가 이긴다".
태스크 문서가 원본이고 `STATE.md` 는 요약이므로, **원본만 각자 쓰고 요약은 한 명이 만들면
충돌이 구조적으로 사라진다.** 에이전트가 중간에 죽어도 `status` 가 남아 있어 orchestration 이 다시 만든다 —
세션이 끊겨도 이어지게 만든 장치가 여기서 그대로 쓰인다.

`STATE.md` 가 실시간이 아니게 되는 것은 감수한다. **실시간인데 틀린 요약보다 조금 늦고 맞는 요약이 낫고**,
지금 무엇이 도는지가 급하면 태스크 문서를 보면 된다.

### 병렬을 끌 때

형식은 되돌리지 않아도 되지만 **필자 규칙은 되돌린다** — 단일 에이전트인데 orchestration 을 기다리면
아무도 `STATE.md` 를 쓰지 않게 된다. 그리고 **격리 미결을 다시 열어 둔다.**

## 6단계. 고친다

**병렬 운용 중이면 라운드 사이에 고친다.** 구동기가 자식들을 띄운 채로 `LOOP.md`·`STATE.md` 형식을 바꾸면 도는 워커는 옛 규칙으로 끝나고
코디네이터는 새 규칙으로 읽어 기록이 어긋난다. `Assignments` 의 행이 전부 끝나 코디네이터가 종료한 뒤(또는 사람이 구동기를 멈춘 뒤) 고치고,
고친 뒤에 구동기를 다시 돌린다. 하네스 갱신(`harness-update` ②③)도 같은 타이밍이다.
**②의 상주 코디네이터를 옮길 때는** 돌던 워커가 끝나기를 기다려 그 코디네이터 세션을 종료한 뒤 고친다 — 옛 코디네이터가 살아 있는 채로 구동 스크립트를 띄우면 코디네이터가 둘이 된다.

**기존 파일을 부분 수정한다. 통째로 다시 쓰지 않는다.**
`LOOP.md` 에는 그동안 쌓인 것이 들어 있다 — 이 프로젝트의 실제 값, 원본 예시에서 조정한 항목과 그 이유,
닫힌 미결의 흔적, 실측한 DAG 결과. 다시 쓰면 그게 조용히 사라지고, 사라진 것은 아무도 눈치채지 못한다.

지킬 것 넷.

- **파일은 하나 그대로다.** 규칙이 늘었다고 쪼개지 않는다 — 매 세션이 시작할 때 읽는 문서라,
  흩어지면 일부만 읽고 시작한다. 정말 길어지면 **조건부로만 필요한 절**(멀티 에이전트 등)을 빼는 것이 먼저다
- **새 기록처를 만들지 않는다.** 갱신 이력은 `LOG.md` 한 줄이고, `LOOP.md` 는 **현재 규칙**만 보여준다
- **`STATE.md` 는 절의 형식과 만료된 승인만 건드린다.** 값은 루프를 도는 세션의 것이다 (형식 규칙은 5단계)
- **하네스에서 읽어 오는 것을 여기 베껴 적지 않는다.** 게이트 명령은 여전히 정의서에서 꺼낸다.
  `local-dev` 경로·옵션처럼 원래 실제 값으로 적기로 한 것만 실제 값을 유지한다

### 갱신을 기록에 남긴다

`LOG.md` 에 한 줄 남긴다. 형식은 그 파일의 기존 형식을 따른다.
**멀티 에이전트로 운용 중이면 직접 쓰지 않고 그 한 줄을 orchestration 에 넘긴다** — 병렬에서 `LOG.md` 의 필자는 하나다(5단계).

**완화(③)와 미결을 닫은 것은 이유를 함께 남긴다.** "무엇을 왜 바꿨고 사용자가 무엇에 동의했는지",
미결이면 "무엇을 근거로 그 선택지를 골랐는지". **루프가 헐거워진 이력은 루프 자체보다 중요하다** —
지금 아무도 안 멈추는 자리가 원래 무엇을 막던 것인지가 거기 있다.

### `CLAUDE.md` · `AGENTS.md` 갱신

`LOOP.md` 를 고친 뒤 프로젝트 루트의 `CLAUDE.md` 와 `AGENTS.md` 를 **같은 내용으로** 갱신한다. 사용자가 직접 연 세션과 루프의 자식 세션은 이 스킬을 읽지 않고 시작하는데,
그때 자동으로 읽히는 파일은 Claude Code 는 `CLAUDE.md`, Codex 는 `AGENTS.md` 뿐이다. 그래서 **지금 어느 호스트에서 돌든 둘 다 쓴다** —
한쪽만 쓰면 다른 호스트의 세션이 규칙을 모른 채 시작한다. 내용은 **어느 세션에서든 반드시 지킬 것**만 두고 세부 규칙은 문서를 가리킨다 —
규칙을 옮겨 적으면 두 곳이 곧 어긋나고, 어긋나면 세션은 짧은 쪽을 믿는다.

- 둘 다 없으면 아래 뼈대로 만든다. 있으면 **`## 루프 (loop_setup/LOOP.md)` 절의 바뀐 값만** 고친다. `현재 단계` 줄은 건드리지 않는다 — 루프 중간의 갱신이지 단계가 바뀐 것이 아니다. 다른 절과 사용자가 손으로 적은 내용은 건드리지 않는다
- 두 파일이 서로 다르면 지금 호스트의 파일을 기준으로 다른 쪽을 맞춘다. 손으로 적은 줄은 양쪽에 남긴다
- 파일은 있는데 `## 문서 지도`·`## 공통 규칙` 이 없으면(예: `/init` 이 만든 파일) 기존 내용 **아래에** 뼈대 두 절을 더한다. 기존 내용은 손대지 않는다
- 절이 없으면 `공통 규칙` 뒤에 제품·기술·구조·플랜·하네스·루프 순서의 자리에 더한다
- 전체 **100줄 안팎, 200줄을 넘기지 않는다.** 넘치면 규칙을 문서 쪽으로 돌려보내고 가리키는 줄만 남긴다

```markdown
# <프로젝트 이름>

> harness-loop-fullstack 스킬이 만들고 갱신하는 파일이다. 각 절은 그 레이어의 스킬만 고친다.
> `CLAUDE.md` 와 `AGENTS.md` 는 같은 내용이다. 한쪽을 손으로 고치면 다른 쪽도 같이 고친다.
> 세부 규칙은 각 문서에 있다 — 여기에는 어느 세션에서든 반드시 지킬 것만 둔다. 200줄을 넘기지 않는다.

## 문서 지도

- 현재 단계: <마지막으로 끝낸 스킬> → 다음: <다음 스킬>

```

`## 루프 (loop_setup/LOOP.md)` 절에서 **바뀐 값만** 고친다 — `구동` 줄(모드·동시 수·격리 방식)과, 병렬을 켜면서 STATE.md 절 형식이 넓어졌다면 그 사실 한 줄.
문장 규칙(3회·분리 세션·슬롯 밖 수정 금지)은 바뀌지 않으므로 손대지 않는다. 절 형식은 `loop-setup` 이 만든 것 그대로다.

```markdown
## 루프 (loop_setup/LOOP.md)
- 세션을 열면 `loop_setup/LOOP.md` 0절부터 따른다. 이 절은 요약이 아니다 — LOOP.md 가 규칙이다
- 완료는 네 게이트를 통과한 뒤다. 코드가 끝난 것은 완료가 아니다
- 실패→수정→재검증은 3회까지. 소진하면 STATE.md `Next Action` 에 `질문:` 을 적고 멈춘다
- 커밋은 네 게이트 통과 뒤. 시점과 횟수는 LOOP.md 5절. 검증 세션은 STATE.md·LOG.md 를 쓰지 않는다
- 병렬이면 자기 슬롯 워크트리 밖을 고치지 않고, 워커는 STATE.md·LOG.md·태스크 문서·하네스 문서를 쓰지 않는다(출력 블록으로 넘긴다). merge 는 코디네이터 몫
- 구동: <스크립트 / 오르카 / 서브에이전트> · 동시 <N> · 격리 <방식> · 모델 코디 <급> / 구현 <급> / 검증 <급> ← loop-update 가 갱신
```

| 승인 기한 | 남은 승인에 **범위나 기한**이 있음 (무기한 0건) | 기한을 붙인다 |

막고 있는 동안에는 아무 일도 안 일어나는 것이 규칙이 일하고 있다는 증거이고,
그래서 **잘 작동하는 규칙일수록 지워도 될 것처럼 보인다.**

## 8단계. 보고

1. **③ 완화가 있었으면 맨 앞에.** 무엇이 더 이상 루프를 멈추지 않는지
2. **무엇을 왜 고쳤는가** — 등급(①②③)과 함께. ①은 묶어서 한 줄씩
3. **닫은 미결** — 무엇을 근거로 그 선택지를 골랐고, 되돌리기 비용은 얼마인지
4. **멀티 에이전트를 켰다면** — 격리 방식, 구간별 폭과 권장 에이전트 수,
   **넷을 띄워도 노는 구간이 어디인지.** 병렬의 이득을 부풀리지 않는다
5. **② 규칙 추가의 비용** — 매 사이클에 얼마나 붙는가
6. **다른 레이어로 가야 하는 것** — 루프가 반복해 멈추는 원인이 플랜(`files` 에 없는 파일)이나
   하네스(흔들리는 흐름)에 있으면 여기서 덮지 않고 그쪽으로 넘긴다
7. **아직 열려 있는 미결** — 무엇이 언제 닫히는지
8. **옛 구조를 옮겼다면** — 구동기를 어떻게 바꿨고 스모크 테스트가 어떻게 돌았는지, 쌓여 있던 알림을 몇 개 처리·전환·질문으로 올렸는지

**루프가 헐거워졌으면 그 사실이 보고의 맨 앞이다.** 진행이 빨라진 것을 성과로 적지 않는다 —
멈춤 규칙을 지워서 빨라진 것은 아무것도 뜻하지 않고, 그걸 성과로 읽으면 다음에도 같은 방식으로 빨라진다.

## 자주 만나는 갱신 네 가지

### 격리 미결을 닫을 때 (세팅 때 껐던 병렬을 켠다)

기본이 병렬이라 보통은 `loop-setup` 이 세팅 때 격리를 이미 정했다. 이 절은 **사용자가 세팅 때 병렬을 꺼서** 미결이 남은 경우다. 닫을 때 필요한 것은 셋이다.

1. **실제 동시 에이전트 수** — 구간별 폭을 다시 재서 넷이 실제로 차는 구간이 있는지 본다.
   폭이 2인데 넷을 띄우면 격리 비용만 치르고 이득이 없다
2. **공유해야 하는 것이 실재하는지** — DB를 공유해야만 하는 태스크가 실제로 있는가
3. **선택지 중 하나를 고르고 되돌리기 비용을 적는다** — 환경 통째 분리 / DB 하나에 워크트리별 계정·권한 /
   공유 자원을 쓰는 게이트만 직렬화

**첫 번째 선택지는 `local-dev` 수정이 필요할 수 있고, 그건 `harness-update` 의 일이다.**
루프가 스크립트를 고치지 않는다.

그리고 **미결을 닫으면 표에서 지우고 결정을 본문 규칙으로 옮긴다.**
표에 "이렇게 하기로 했다"고만 남기면 사이클을 도는 세션이 그것을 읽지 않는다.

### 게이트가 활성돼 승인이 만료될 때

`Standing Decisions` 의 미활성 승인은 **"그 게이트가 활성될 때까지"** 로 발급됐다.
게이트가 활성되면 그 항목은 **지워야 한다.**

**빠뜨리기 쉽다.** 활성은 하네스 문서에서 일어나는데 승인은 `STATE.md` 에 있어서,
둘을 잇는 것이 사람의 기억밖에 없기 때문이다. `HARNESS.md` 의 게이트 표를 보고
`미활성` 이 아니게 된 게이트를 `Standing Decisions` 에서 검색하는 것이 확실하다.

남기면 무슨 일이 생기냐면 — **이제 실제로 도는 게이트를 루프가 "승인받았으니 건너뛴다"로 읽는다.**
가장 조용한 종류의 구멍이고, 통과율은 오히려 좋아 보인다.

### 루프가 같은 자리에서 반복해 멈출 때

먼저 0단계로 **어느 레이어의 문제인지 가른다.** `LOG.md` 에 쌓인 중단 기록이 근거다.

그리고 **루프의 문제라는 결론이 나와도, 멈춤을 줄이는 방향인지 확인한다.**
같은 중단을 없애는 방법이 보통 둘 있다 — **원인을 없애는 것**과 **멈추지 않게 하는 것**.
앞쪽이 먼저다. 승인 범위가 좁아 매번 묻는 것이면 범위를 게이트 단위로 넓히면 되고(기한은 유지),
`Retry` 절이 병렬에서 덮어써지는 것이면 형식을 넓히면 된다.
**뒤쪽(멈추지 않게 하기)이 답인 경우는 드물고, 그때는 ③이라 승인이 필요하다.**

### 1.10.0 이전 `LOOP.md` 를 옮길 때 (상주 코디네이터·쌓이는 알림)

2026-09-23 이전 `loop-setup` 이 만든 `LOOP.md` 에는 두 구조가 있다. ②에서 **대화형 코디네이터가 phase 내내 상주**하고(또는 phase 마다 새 터미널로 교체되고),
"두 태스크에 걸친 같은 실패"·미결의 판단 시점 같은 트리거가 **설명으로만** 있어 코디네이터가 `알림:` 한 줄로 쌓고 지나간다.
실전(ERP)에서 앞쪽은 전체 토큰의 30%를, 뒤쪽은 여섯 phase 동안 같은 흔들림을 만들었다. 옮기는 순서는 이렇다.

1. **라운드 사이를 잡는다** — 돌던 워커가 끝나고 상주 코디네이터가 종료된 뒤. 살아 있는 코디네이터 옆에 구동 스크립트를 띄우지 않는다
2. **4절 ② 블록을 `loop-setup` 템플릿의 "② 오르카 스크립트 구동"으로 바꾼다** — 코디네이터 지시문에서 교체 단계(다음 코디네이터를 띄우는 줄)를 지우고,
   반복 판정 2.5)·질문 답변 지시문·② 워커 덧붙임을 넣는다. 이 프로젝트가 고쳐 둔 지시문 문장은 살린다 — 통째로 붙여 넣지 않는다
3. **8절** — 코디네이터 수명·교체 명령·시작 프롬프트를 지우고 구동 스크립트·구동 시작 명령·대기 길이·스모크 테스트 칸을 넣는다. 배정표가 오르카 Run·Task 였다면 `STATE.md` 에 `Assignments` 절을 더한다
4. **`harness_setup/scripts/loop-drive.*` 를 쓰고 스모크 테스트를 돌린다**(`loop-setup` 12단계와 같다). 오르카 터미널 안에서, 가벼운 모델의 시험 워커 하나로
5. **트리거를 넣는다** — 3절 실패 줄 형식과 반복 판정, 0절 7번, 9절 `언제` 를 `phase-NN 진입 전` 같은 확인 가능한 시점으로
6. **쌓인 알림을 분류한다.** 새 형식으로 바꾸기만 하면 같은 목록이 다시 자란다
   - 루프가 ①로 할 수 있는 것(`harness-update` ① 후보 등) → 이번에 처리하고 지운다
   - 조건이 이미 충족된 트리거(두 태스크 이상 반복된 흔들림, 판단 시점이 지난 미결) → `질문:` 으로 모아 올린다. 격리 3에서 DB 테스트가 흔들렸다면 선택지에 격리 1·2를 넣는다
   - 다른 레이어의 일(문서 표기 보정, `files` 보완) → `알림(<주체>, ~다음 phase 전)` 형식으로 바꾼다
   - LOG.md 의 과거 실패 줄은 형식이 달라도 고치지 않는다 — append-only 다. 반복 판정은 옮긴 뒤의 새 형식 줄부터 센다(처음 판정 때 옛 기록에서 확인한 반복은 위 `질문:` 으로 이미 올렸다)
7. `CLAUDE.md`·`AGENTS.md` 의 `구동:` 줄을 고치고 `LOG.md` 에 한 줄 — 무엇을 옮겼고 알림을 몇 개 처리·전환·질문했는지

**이 갱신은 멈춤을 줄이지 않는다** — 정지 조건(`질문:`·전부 `completed`)과 멈춤 규칙은 그대로이고, 트리거가 실행되면서 멈추는 자리는 오히려 는다(②).
대신 사람이 불리는 곳이 phase 경계로 모인다 — 알림은 phase 안에서 묶였다가 경계에서 한 번 묻는다.
