# Codex 환경 보조 지침 (loop-update)

## 무엇이 바뀌었는지 찾기

`loop_setup/LOOP.md` 를 전문 읽는다. 파일 하나이고, 고칠 곳을 정하려면 규칙 전체를 알아야 한다.
`plan_setup/STATE.md` 와 `harness_setup/HARNESS.md` 도 읽는다 — **갱신의 근거는 대개 이 둘의 차이에 있다.**

**만료시킬 승인이 가장 잘 빠진다.** 게이트가 활성됐는데 `Standing Decisions` 에 그 게이트의
미활성 승인이 남아 있으면, 루프가 **실제로 도는 게이트를 "승인받았으니 건너뛴다"로 읽는다.**
활성은 하네스 문서에서 일어나고 승인은 `STATE.md` 에 있어서, 둘을 잇는 것이 사람의 기억밖에 없다.

```
grep -n '미활성' harness_setup/HARNESS.md
grep -n -A5 'Standing Decisions' plan_setup/STATE.md
```

## 반복되는 중단 찾기

```
grep -n 'failed\|중단\|흔들림\|환경 문제' plan_setup/LOG.md
```

**세는 것만으로는 어느 레이어의 문제인지 안 나온다.** 중단마다 "무엇을 바꾸면 안 걸렸겠는가"를 본다 —
`files` 밖의 파일을 고쳐야 했으면 Layer 3, 같은 흐름이 흔들렸으면 `harness-update`,
승인을 매번 다시 물었으면 여기다. **앞 둘을 여기서 고치면 다른 레이어의 결함을 루프 규칙으로 덮는 것이다.**

## DAG 와 폭을 다시 재기

태스크가 추가·삭제됐거나 차단이 풀렸으면 **다시 잰다.** 눈으로 세지 않는다.

```
grep -H '^id:\|^status:\|^depends_on:\|^files:' plan_setup/phase-*/phase-*-tasks/*.md
```

순환·미존재 참조·`files` 겹침을 확인하고 층별로 나눠 **구간별 폭**을 낸다.
`loop-setup` 이 처음 잰 숫자는 그때의 태스크 목록 기준이다 — 태스크가 바뀌었는데 그대로 두면
**"넷으로 돌리자"는 결정이 근거 없이 유지된다.**

## 고치는 방법

**부분 수정한다. 파일을 통째로 다시 쓰지 않는다.** `LOOP.md` 에는 이 프로젝트의 실제 값,
원본 예시에서 조정한 항목과 그 이유, 닫힌 미결의 흔적, 실측한 DAG 결과가 쌓여 있다.
다시 쓰면 그게 조용히 사라지고 아무도 눈치채지 못한다.

heredoc 으로 문서를 다시 만들 때는 구분자를 따옴표로 감싼다(`<<'EOF'`) — 안 그러면 `$` 로 시작하는
환경변수 예시와 경로가 빈 문자열이 된다. **다만 전체 재작성 자체를 피하는 것이 먼저다.**

`STATE.md` 의 절 형식을 넓힐 때(병렬에서 `Retry` 를 태스크별 블록으로 등)는
**기존 값을 새 형식으로 옮긴 뒤** 형식을 바꾼다. 넓히면서 지우면 진행 중인 재시도 이력이 없어지고,
그 태스크는 앞의 시도를 처음부터 반복한다.

**`STATE.md` 의 값은 건드리지 않는다.** 여기서 만지는 것은 **절의 형식과 만료된 승인** 둘뿐이다.

승인 모드에 따라 쓰기 권한 요청이 필요하니, 작성 직전에 고칠 파일과 고칠 절을 알린다.

## 사용자에게 묻는 지점

선택지 UI가 없으므로 **표 하나로 모아** 제시하고 한 번에 답을 받는다.

```
루프를 고치기 전에 확인할 것이 있습니다.
("1: A" 형태로 답해 주셔도 됩니다.)

1) 워크트리 간 격리 방식 — 지금 닫아야 합니다
   (다시 잰 폭: 구간 B 만 4, 나머지는 1~3. 넷이 실제로 차는 구간은 한 곳뿐입니다)
   A) 워크트리별 환경 통째 분리   → 완전 격리. local-dev 수정 필요(harness-update 몫)
   B) DB 하나 + 워크트리별 계정   → 가볍다. 권한 발급 단계가 local-dev 에 추가된다
   C) 공유 자원 게이트만 직렬화   → 새로 만들 것 거의 없음. 병렬 이득이 앞 두 게이트까지

2) (완화가 필요한 경우에만) 아래를 적용할까요?
   기록 시점을 줄입니다 → 세션이 중간에 끊기면 그 태스크를 처음부터 다시 하게 됩니다
```

**완화는 결과로 적는다.** "기록을 줄인다"가 아니라 **"끊기면 처음부터 다시 한다"** 로 적어야
사용자가 실제로 무엇에 동의하는지 안다.

**재시도 3회·분리 세션·게이트 구성은 묻지 않는다.** 원본 사양과 Layer 4가 정했고 이 스킬이 못 바꾼다.
늘려 달라는 요청을 받으면 **묻는 대신 `LOG.md` 를 확인해** 그 3회가 실제로 무엇에 소모됐는지를 답으로 준다.

## 다음 단계

Codex에서는 다음 단계를 명시적으로 남긴다.
예: `다음 단계: loop_setup/LOOP.md 와 plan_setup/STATE.md 를 읽고 <태스크 ID> 부터 사이클을 이어 갑니다.`

`Standing Decisions` 를 지웠다면 **다음 태스크에서 그 게이트에 대해 다시 묻게 된다** —
그게 정상이고, 그러라고 만료시킨 것이다. 그 사실을 다음 단계 안내에 함께 적는다.

## `AGENTS.md` 는 `CLAUDE.md` 를 가리키는 한 줄

Codex 는 프로젝트 루트의 `AGENTS.md` 를 자동으로 읽고 `CLAUDE.md` 는 읽지 않는다. 본문을 두 파일에 두면 곧 어긋나므로
본문은 SKILL.md 의 "`CLAUDE.md` 갱신" 절대로 `CLAUDE.md` 에만 쓰고, `AGENTS.md` 에는 아래 한 줄만 둔다.
없으면 만들고, 이미 다른 내용이 있으면 그 줄을 맨 위에 더한다.

```
CLAUDE.md 를 읽고 따른다.
```
