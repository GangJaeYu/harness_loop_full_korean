# Claude Code 환경 보조 지침 (harness-setup)

## 다섯 입력을 읽는 방법

`docs/PRD.md`, `docs/TRD.md`, `docs/ARCHITECTURE/*.md`, `plan_setup/PLAN.md`, 그리고 태스크 문서들을 읽는다.
태스크는 수십 개가 되므로 전부 통독하지 않아도 되지만, **아래는 요약으로 대체하지 않는다.**

| 문서 | 절 | 왜 |
|---|---|---|
| PRD | 유저 스토리, P0 기능 요구사항, NFR | E2E 흐름 목록을 여기서 뽑는다. 원본 사양이 하네스에 넘긴 판단이다 |
| TRD | 테스트 절의 도구(TD)와 **필수 커버 영역 표**, 로컬 개발 환경 절의 **구성 요소 표** | unit 게이트의 목표와 `local-dev` 가 준비할 것이 그대로 여기 있다 |
| PLAN.md | **`Layer 4로 넘기는 검증` 절** | 이 절 때문에 하네스가 있다. 항목 단위로 배치한다 |
| ARCHITECTURE | 계층 경계·의존 방향, 각 절의 검증 기준 | lint 로 강제할 구조 규칙과 게이트가 볼 것 |

태스크 문서는 **frontmatter 만 기계로 훑는 편이 정확하다.** Bash 로 `verification`·`status`·`files`·`architecture` 를
뽑아 목록을 만들면 게이트가 무엇에 걸리는지, `blocked` 가 몇 개인지, 활성 시점으로 삼을 태스크가 어느 것인지가 한 번에 나온다.
사람이 눈으로 세는 것보다 정확하고, 여기서 세는 것이 틀리면 활성 시점이 없는 태스크를 가리키게 된다.

Explore 서브에이전트에게 **"모든 태스크 문서의 frontmatter 를 표로 뽑아라"** 를 시켜도 된다.
다만 게이트 설계 판단(무엇을 어느 게이트에 넣을지)은 직접 한다.

## task_validation 의 관찰 수단 확인

검증자가 브라우저를 무엇으로 조작할지를 **하네스를 세울 때** 확인해 `HARNESS.md` 에 적는다.
이 세션에 브라우저 자동화 MCP 도구가 붙어 있는지 도구 목록에서 본다(있으면 그것이 1순위 수단이다).
없으면 TRD가 고른 e2e 도구가 설치돼 있는지 확인하고, "없음 — e2e 도구로 일회성 스크립트"로 적는다.
둘 다 없으면 화면 기준은 `판정 불가` 가 되므로 그 사실을 보고에 올린다 — 사용자가 도구를 붙일지 정한다.

## 사용자 OS 확인

시스템 정보로 현재 OS 를 확인하고 그것을 `local-dev` 의 기본으로 삼는다.
TRD가 개발자 OS 를 미결로 남겨 두었는데 여기서 확인됐으면, **그 사실을 보고에 올린다** —
미결 하나가 실제로 해소된 것이므로 TRD 쪽에서 지울 수 있다.

## 기존 코드베이스가 있으면

Glob·Grep 으로 이미 있는 설정 파일을 먼저 확인한다. 린터 설정이나 테스트 스크립트가 이미 있으면
**새로 만들지 말고 그것을 게이트 명령으로 가리킨다.** 두 벌이 생기면 어느 쪽이 판정한 것인지 알 수 없다.

패키지 매니저 스크립트(`package.json` 의 `scripts` 등)가 있으면 게이트 명령을 거기에 맞춘다 —
게이트가 도구를 직접 부르고 프로젝트는 스크립트를 부르면, 둘이 다른 설정으로 도는 일이 생긴다.

## task_validation 을 분리된 세션으로 돌리는 방법

**분리 수단은 새 세션이다.** 구현 세션이 닫힌 뒤 **컨텍스트가 없는 새 세션**이 판정한다 —
구현 세션이 무엇을 했는지 모르는 상태여야 이 게이트가 원하는 조건이 된다.

이 환경에서 그 새 세션을 여는 **기본은 헤드리스 자식 세션 `claude -p "<검증 지시문>"`** 이다(Layer 5 구동기 ①).
헤드리스 실행은 이 저장소에서 실제로 확인됐고, 검증 세션의 권한을 `--allowedTools` 로 **읽기·`local-dev`·관찰 수단만**으로 좁힐 수 있다
(쓰기와 git 은 주지 않는다). 상위 세션이 Agent 도구로 띄우는 **서브에이전트는 대안(구동기 ③)**이다 — 새 컨텍스트로 시작하긴 하지만
상위 세션의 권한을 그대로 물려받아 토막별 제한이 안 되고, 상위 세션이 태스크를 거듭 돌리며 컨텍스트를 쌓는 구조라 기본으로 두지 않는다.
**어느 방식으로 세션을 여는지는 하네스가 아니라 `loop_setup/LOOP.md` 의 구동기가 정한다.** 하네스는 그 세션에 **무엇을 주고 무엇을 주지 않는지**만 고정한다.
`task_validation.md`·`HARNESS.md` 에 "서브에이전트"를 분리 수단으로 단정해 적지 않는다.

지시문에 넣을 것은 **네 가지뿐**이다.

1. 태스크 문서 경로
2. `harness_setup/quality_gates/task_validation.md` 경로
3. 애플리케이션이 실행 중이라는 사실과 접속 주소
4. 판정 블록을 그대로 출력하라는 지시

**넣지 않을 것이 더 중요하다** — 구현 세션이 무엇을 고쳤는지, 어떤 파일을 건드렸는지, 무엇이 의도였는지.
"참고하라"고 붙이는 한 줄 요약이 가장 흔한 누수이고, 그 한 줄이 바로 구현 중에 형성된 판단이다.
검증 세션에는 **"이 두 문서, 태스크 문서의 `architecture` 가 가리키는 설계 절, 실행 중인 앱 외의 정보를 찾지 말라"**를 명시한다.
설계 절을 허용하는 이유는 수용 기준이 그 절을 인용하는 일이 흔하고, Layer 2가 쓴 것이라 구현 판단이 새지 않기 때문이다.

`task_validation.md` 에 **그대로 복사해 새 세션에 건넬 수 있는 지시문**을 적어 둔다. 매번 다르게 쓰면 매번 다른 것이 새어 나간다.

```
다음 태스크의 수용 기준을 실행 중인 애플리케이션에서 관찰해 판정하세요.
- 태스크 문서: plan_setup/phase-NN/phase-NN-tasks/phase-NN-task-MM.md
- 절차와 판정 형식: harness_setup/quality_gates/task_validation.md
- 애플리케이션: (접속 주소). scripts/local-dev… 로 준비돼 있습니다
- 이 두 문서, 태스크 문서의 architecture 가 가리키는 설계 절, 실행 중인 앱 외의 정보는 찾지 마세요.
  최근 커밋·변경 파일·작업 메모를 포함해 구현 과정에 대한 설명을 참고하지 말고, 코드를 고치지 말고, 원인 추정을 하지 마세요.
```

**한 세션 안에서 구현하고 같은 세션이 판정하는 것은 이 게이트를 돌린 것이 아니다.**
그렇게 돌 수밖에 없는 상황이면 통과로 기록하지 말고 사용자에게 알린다.

## 파일 작성

디렉터리를 만들고 Write 로 쓴다. 순서는 이게 낫다.

1. `quality_gates/lint.md`·`unit.md`·`e2e.md`·`task_validation.md`
2. `scripts/local-dev.*` 와 `scripts/.env.example`
3. `HARNESS.md` (게이트 표와 구성 요소 표가 확정된 뒤)

스크립트는 쓰고 나서 **실제로 한 번 돌려 본다.** 돌지 않는 스크립트는 하네스가 아니라 문서이고,
안 돌아 본 스크립트를 분리된 검증 세션에 건네면 그 세션은 환경 문제를 구현 문제로 보고한다.
전제(런타임·컨테이너 엔진)가 이 컴퓨터에 없어서 못 돌리면, **못 돌려 봤다는 사실을 보고에 적는다.**

이미 `harness_setup/` 이 있으면 읽고 나서 판단한다. `harness-update` 가 갱신해 둔 활성 시점·커버 영역·흐름 상태는
초기값으로 덮으면 사라진다. 갱신이 목적이면 이 스킬이 아니라 `harness-update` 다.

## 사용자에게 묻는 지점

AskUserQuestion 을 쓰는 자리는 둘이다. **한 번씩만 묻는다.**

**도구가 비어 있을 때 (도입부의 "도구를 새로 고르지 않는 이유"와 9단계 '근거 없는 기준').** TRD가 정하지 않은 도구가 게이트에 필요하면 묻는다.
선택지에 **되돌리기 비용**을 적는다 — 나중에 바꾸면 무엇을 다시 써야 하는지.

**하네스에 더 넣을 것 (10단계).** 성능 목표를 회귀로 지키는 측정 묶음, 브라우저 여러 종 실행 구성,
접근성 검사(PRD에 근거가 있을 때만) 같은 것들이다. **게이트 실행 순서·재시도·하네스 갱신 판단은 묻지 않는다** —
원본 사양이 Layer 5 루프의 일로 정해 두었다.
`option.description` 에 **그것이 모든 태스크에 얼마나 붙는지**를 적는다.
관문에 세운 것은 앞으로 모든 세션이 매번 치르는 비용이라, 그 감각 없이 고르면 나중에 사람이 게이트를 끈다.

## 다음 스킬 연결

사용자가 검토를 마치고 동의하면 Skill 도구로 `loop-setup` 을 호출한다. **동의 전에는 호출하지 않는다.**
게이트가 확정되지 않은 채로 루프를 세우면, 루프가 부를 명령이 없는 게이트를 순서대로 부르게 된다.
