# Codex 환경 보조 지침 (harness-setup)

## 다섯 입력을 읽는 방법

`docs/PRD.md`, `docs/TRD.md`, `docs/ARCHITECTURE/` 전부, `plan_setup/PLAN.md`, 그리고 태스크 문서들을 읽는다.
요약본으로 대체하면 안 되는 곳은 PRD의 유저 스토리·P0 요구사항·NFR(E2E 흐름의 재료),
TRD의 **필수 커버 영역 표**와 **로컬 개발 환경 구성 요소 표**, PLAN.md의 **`Layer 4로 넘기는 검증` 절**이다.
마지막 절 때문에 하네스가 존재한다 — 항목 하나하나를 어느 게이트가 받을지 정한다.

태스크는 수십 개이므로 셸로 frontmatter 만 훑는 편이 정확하다.

```
grep -H -A1 '^status:' plan_setup/phase-*/phase-*-tasks/*.md
grep -H '^verification:' plan_setup/phase-*/phase-*-tasks/*.md
```

`blocked` 가 몇 개인지, 게이트를 줄인 태스크가 있는지, 활성 시점으로 삼을 태스크가 어느 것인지가 여기서 나온다.
**존재하지 않는 태스크 ID를 활성 시점으로 적으면** 루프가 영원히 미활성인 게이트를 들고 돌게 된다.

## task_validation 의 관찰 수단 확인

검증자가 브라우저를 무엇으로 조작할지를 **하네스를 세울 때** 확인해 `HARNESS.md` 에 적는다.
코덱스 세션에 브라우저 조작 도구(MCP 등)가 붙어 있으면 그것이 1순위이고, 없으면 TRD가 고른 e2e 도구가
설치돼 있는지 셸로 확인해 "없음 — e2e 도구로 일회성 스크립트"로 적는다.
둘 다 없으면 화면 기준은 `판정 불가` 가 되므로 보고에 올린다 — 사용자가 도구를 붙일지 정한다.

## 사용자 OS 확인

셸에서 현재 OS 를 확인하고 그것을 `local-dev` 의 기본으로 삼는다(`uname` 또는 그에 준하는 확인).
Windows 면 `local-dev.ps1`, 그 외에는 `local-dev.sh` 를 주 스크립트로 만든다.
TRD가 개발자 OS 를 미결로 남겨 두었는데 여기서 확인됐으면 보고에 올린다 — 미결 하나가 실제로 해소된 것이다.

## 기존 설정이 있으면

셸로 이미 있는 린터·테스트 설정과 패키지 매니저 스크립트를 먼저 확인한다.
있으면 새로 만들지 말고 **게이트 명령이 그것을 가리키게** 한다. 두 벌이 생기면 어느 쪽이 판정한 것인지 알 수 없다.

## task_validation 을 분리된 세션으로 돌리는 방법

**이 환경에서는 자동 분리를 기대하지 않는다.** 분리는 **새 세션을 여는 것**으로 이룬다.
그래서 `task_validation.md` 에 **그대로 복사해 새 세션에 붙여 넣을 수 있는 지시문**을 만들어 둔다.
매번 손으로 다시 쓰면 매번 다른 것이 새어 나가기 때문이다.

지시문에 들어갈 것은 넷뿐이다.

```
다음 태스크의 수용 기준을 실행 중인 애플리케이션에서 관찰해 판정하세요.
- 태스크 문서: plan_setup/phase-NN/phase-NN-tasks/phase-NN-task-MM.md
- 절차와 판정 형식: harness_setup/quality_gates/task_validation.md
- 애플리케이션: (접속 주소). scripts/local-dev… 로 준비돼 있습니다
- 이 두 문서, 태스크 문서의 architecture 가 가리키는 설계 절, 실행 중인 앱 외의 정보는 찾지 마세요.
  최근 커밋·변경 파일·작업 메모를 포함해 구현 과정에 대한 설명을 참고하지 말고, 코드를 고치지 말고, 원인 추정을 하지 마세요.
```

**구현 세션의 요약을 붙이지 않는다.** "참고하라"고 붙인 한 줄이 바로 구현 중에 형성된 판단이고,
그게 들어가는 순간 분리한 의미가 없어진다.

**같은 세션에서 구현하고 판정하는 것은 이 게이트를 돌린 것이 아니다.** 그렇게 할 수밖에 없으면
통과로 기록하지 말고 사용자에게 알린다. 분리된 척하는 검증은 통과 기록만 남기고 실제로는 아무것도 막지 않는다.

## 파일 작성

`harness_setup/` 아래에 디렉터리를 만들고 파일 쓰기 도구나 heredoc 으로 만든다. 순서는 이게 낫다.

1. `quality_gates/` 의 네 정의서 → 2. `scripts/local-dev.*` 와 `.env.example` → 3. `HARNESS.md`

스크립트를 heredoc 으로 쓸 때는 **셸이 변수를 미리 치환하지 않도록** 구분자를 따옴표로 감싼다
(`<<'EOF'`). 안 그러면 `$` 로 시작하는 변수와 경로가 빈 문자열이 되어, 겉보기에 멀쩡한 스크립트가 아무것도 안 한다.
PowerShell 스크립트를 만들 때도 마찬가지다.

**쓰고 나서 실제로 한 번 돌려 본다.** 돌지 않는 스크립트는 하네스가 아니라 문서다.
전제(런타임·컨테이너 엔진)가 없어서 못 돌리면 **못 돌려 봤다는 사실을 보고에 적는다.**

승인 모드에 따라 쓰기·실행 권한 요청이 필요하니, 작성 직전에 만들 디렉터리와 파일 목록을 알린다.

이미 `harness_setup/` 이 있으면 통째로 덮어쓰지 않는다. 활성 시점·커버 영역·흐름 상태는
`harness-update` 가 진행에 맞춰 갱신해 둔 것이라, 초기값으로 덮으면 어디까지 활성화됐는지가 사라진다.

## 사용자에게 묻는 지점

선택지 UI가 없으므로 **표 하나로 모아** 제시하고 한 번에 답을 받는다.
묻는 자리는 둘이고, 같은 목록에 넣어 함께 묻는다.

```
하네스를 세우기 전에 정할 것이 있습니다.
("1: A, 2: B" 형태로 답해 주셔도 됩니다.)

1) 포매터 규칙 — TRD가 정하지 않았습니다
   A) 도구 기본값 그대로       → 되돌리기 비용 없음
   B) 규칙을 따로 정한다       → 나중에 바꾸면 전 파일이 한 번 바뀝니다

2) 하네스에 더 넣을 것 (전부 선택 가능, 안 넣어도 됩니다)
   A) 성능 목표를 회귀로 지키는 측정 묶음  → phase 완료 시에만 돌면 태스크당 비용 0
   B) 브라우저 여러 종 실행 구성           → phase 완료 묶음에 둡니다
   C) 접근성 검사                          → PRD에 근거 요구사항이 없으면 통과선을 만들 수 없습니다
```

**게이트 실행 순서·재시도·하네스 갱신 판단은 묻지 않는다.** 원본 사양이 Layer 5 루프의 일로 정해 두었다.

각 선택지에 **그것이 앞으로 모든 태스크에 얼마나 붙는지**를 적는다.
관문에 세운 것은 매 세션이 치르는 비용이고, 그 감각 없이 고르면 나중에 사람이 게이트를 꺼 버린다.

## 다음 스킬 연결

Codex에서는 스킬 자동 호출을 기대하지 말고 다음 단계를 명시적으로 남긴다.
예: `다음 단계: loop-setup 스킬(SKILL.md)을 읽고 plan_setup/ 과 harness_setup/quality_gates/ 를 입력으로 loop_setup/LOOP.md 를 만듭니다.`

미활성 게이트가 남아 있으면 그 목록과 활성 시점을 함께 남긴다.
루프가 미활성 게이트를 통과로 읽지 않게 해야 한다.
