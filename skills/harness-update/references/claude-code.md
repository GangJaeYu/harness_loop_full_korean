# Claude Code 환경 보조 지침 (harness-update)

## 무엇이 바뀌었는지 찾기

Read 로 `harness_setup/` 전체와 `plan_setup/STATE.md`·`LOG.md` 를 읽는다. 하네스 문서는 길지 않아 전문 읽어도 된다.

**태스크 상태는 눈으로 세지 말고 뽑는다.** 완료된 태스크와 차단이 풀린 태스크를 Bash 로 훑으면
활성화해야 할 것이 한 번에 나온다.

```
grep -H '^status:' plan_setup/phase-*/phase-*-tasks/*.md
grep -H '^blocked_by:' plan_setup/phase-*/phase-*-tasks/*.md
```

**차단이 풀린 경우가 가장 잘 빠진다.** `blocked_by` 에 있던 OQ·CF ID로 하네스 문서 전체를 Grep 해서
그 ID가 언급된 곳을 전부 찾는다 — `대기` 표시는 흐름 목록·커버 영역 표·`HARNESS.md` 여러 곳에 흩어져 있다.

```
grep -rn 'OQ-007\|CF-006' harness_setup/
```

## 반복되는 실패 찾기

`LOG.md` 를 Grep 해서 같은 흐름·검사 ID가 어느 태스크들에서 실패했는지 센다.
**두 태스크에 걸쳐 나왔으면 코드가 아니라 하네스를 의심한다** — 흔들리는 선택자, 남은 테스트 데이터, 준비 판정 누락.
그때는 코드를 또 고치지 말고 이 스킬로 넘어온 것이 맞다.

## 고치는 방법

**Write 가 아니라 Edit 을 쓴다.** 하네스 문서에는 활성 시점, 커버 영역의 담당 태스크,
'하네스 결정'·'하네스 밖' 목록처럼 그동안 쌓인 것이 들어 있고, Write 로 다시 쓰면 조용히 사라진다.
사라진 줄은 아무도 눈치채지 못한다 — 그게 없어졌다는 것을 알려 줄 것이 없기 때문이다.

고친 스크립트는 **실제로 돌려 본다.** 최소한 상태 확인 경로는 돌아가야 한다.
컨테이너를 실제로 띄우는 것이 곤란하면 그 사실을 보고에 적는다.
안 돌려 본 스크립트를 넘기면, 분리된 검증 세션이 그 실패를 구현 문제로 보고한다.

**STATE.md 와 태스크 문서는 고치지 않는다.** 읽기만 한다. 그건 Layer 3·5의 것이다.

## 사용자에게 묻는 지점

AskUserQuestion 을 쓰는 자리는 **③ 약화 하나뿐이다.** 상태 반영(①)까지 확인을 구하면
갱신이 대화가 되고, 그러면 사람이 하네스를 대신 관리하게 된다.

약화를 물을 때는 `option.description` 에 **그래서 지금부터 무엇이 확인되지 않는지**를 적는다.
"E2E 흐름 하나를 뺍니다"가 아니라 "공유 링크 폐기가 즉시 반영되는지를 앞으로 아무도 확인하지 않습니다".
전자는 정리로 들리고 후자는 결정으로 들리는데, 실제로는 후자다.

선택지에 **약화하지 않는 대안을 먼저** 둔다 — 흔들림의 원인을 없애는 쪽(고유 테스트 데이터, 인증 재사용,
준비 판정 보강)을 다 해 보고도 안 될 때만 기준을 낮추는 것이 순서다.

## 갱신 후

`LOG.md` 에 한 줄 남긴다. Edit 으로 **끝에 덧붙인다** — append-only 파일이라 중간을 고치지 않는다.
약화가 있었으면 이유를 함께 적는다.

루프가 이 스킬을 부른 경우, 갱신이 끝났으면 **무엇이 다시 실행 가능해졌는지**를 명확히 돌려준다.
게이트가 지금 활성인지 미활성인지가 루프의 다음 판단에 그대로 쓰인다.
