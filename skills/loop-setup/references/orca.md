# 오르카 구동(②) 참고 — loop-setup

구동기가 **②(오르카 스크립트 구동)** 일 때만 읽는다 — 7단계에서 ②를 고를 때, 12단계에서 `LOOP.md` 와 `loop-drive`·`loop-watch`·`loop-status`·`loop-answer` 를 쓸 때, 13단계 점검, `loop-update` 가 ② 산출물을 고칠 때.
①·③ 이면 읽지 않는다. ②도 판단하는 쪽(코디네이터 자식)·지시문·기록 규칙은 본문 그대로이고, 여기 있는 것은 **오르카로 워커를 띄우고 기다리고 지켜보는 방법**뿐이다.
오르카 CLI 는 판마다 표면(명령·필드·상태 이름)이 바뀐다 — 여기 적힌 것은 실측한 판의 것이니 세팅 때 스모크(이 파일 4절)로 다시 확인한다.
그냥 "N절" 은 `LOOP.md` 의 절이고(그 4절 ② 블록은 이 파일 2절, 8절 ② 값은 이 파일 3절), 이 파일의 절은 "이 파일 N절" 이라 쓴다. "N단계" 는 본문(SKILL.md)의 단계다.

## 1. ②의 원리

**②의 모양 — 코디네이터를 상주시키지 않는다.** ②는 ①-병렬과 **판단하는 쪽이 같고 워커를 띄우는 수단만 다르다.**
처음 설계는 대화형 코디네이터 하나가 phase 내내 살아서 워커를 띄우고 기다렸는데, 실전(ERP, 2026-09)에서 그 세션 10개가 전체 토큰의 30%를 썼다 —
기다리는 동안의 폴링(`check`·`worker-list`·대기)이 한 phase 에 수백 번이고, 그때마다 수십만 토큰으로 자란 컨텍스트를 통째로 다시 읽었다.
기다리기는 판단이 아니므로 **스크립트가 한다.** 판단(반영·분류·배정)은 라운드마다 **새로 여는 코디네이터 자식**이 하므로 컨텍스트가 쌓이지 않는다.

스크립트는 **판단하지 않는다** — 띄우고, 기다리고, 받은 질문을 판단 자식에게 넘기고, 결과 파일을 확인할 뿐이다. `STATE.md` 의 필자는 코디네이터 자식이다(질문 답변 자식은 `Next Action` 에 `질문:` 한 줄만 쓰고, 답하기 탭은 사람이 입력한 `답:` 한 줄만 쓴다).
**phase 경계를 그냥 지난다** — ①-병렬과 같다. 다음 phase 코디네이터를 새 터미널로 띄울 필요가 없고(실전에서 그 터미널 생성이 수십 번 시간 초과로 실패했다),
그래도 "phase 마다 새 컨텍스트"는 더 강하게 지켜진다 — 판단 자식이 라운드마다 새로 열리기 때문이다.
사람이 스크립트를 여는 것은 처음 시작할 때와 `질문:` 에 답한 뒤 재개할 때뿐이다.
이 모양은 세팅 때 실제로 돌려 확인한다(12단계 — 이 파일 4절의 스모크 테스트) — 오르카 CLI 는 버전마다 표면이 바뀐다.

**②의 정지 감시 — 일하는 워커는 건드리지 않고, 진행할 수 있는데 멈춘 상태만 잡는다.** 구동 스크립트가 늘 `check --wait` 로 기다리므로 "코디네이터가 턴을 끝내 못 봄" 은 구조적으로 없다.
그래도 남는 정지가 있다(ERP 실측·실험, 2026-09~10) — 백그라운드 완료 알림이나 끊긴 `ask` 뒤 잠든 워커, 사람만 풀 수 있는 프롬프트, 시작하다 만 워커, 한도·과부하로 실패한 자식,
PC·오르카 재시작 뒤 끊긴 워커, 죽거나 한 단계에 묶인 스크립트. 감시는 이것을 **두 자리**에서 본다 — 스크립트 안(대기 뒤·자식 뒤·시작 때 판정하고, 정해진 조치만 한다:
깨우기 1회·초안 제출 1회·시작 재시도 1회·한도 쉼·자식 재시도·사유를 남기고 멈춤·도는 dispatch 0 이면 첫 줄로·이중 기동 거부·죽은 워커 정리 — stop, 안 되면 abandon·터미널 닫기)과 **스크립트 밖의 작은 감시**(파일과 읽기 전용 명령만 보고 알림만 —
스크립트 자신이 죽은 것은 스크립트가 알릴 수 없다). 나머지는 모두 알림이고, 같은 상태는 한 번만 알린다(답 없는 `질문:` 과 사람이 세우지 않은 루프 정지·죽음은 30분·2시간·8시간에 다시 — 아래 "②의 답하기", 4절 [정지 재알림]). 감시는 `STATE.md` 를 쓰지 않는다 — 필자는 그대로다.
워커를 멈추거나 다시 띄우는 근거는 오르카의 양성 증거(`worker-start` 실패 영수증, `exited`)이고, 무언가가 없다는 것(전사 없음·응답 없음) **하나만으로는** 알림의 근거일 뿐이다.
예외는 하나 — 오르카가 생존을 확인하지 못하고(`unverifiable`·`missing`) **그리고** 그 워커가 20분 동안 전사에도 터미널에도 아무것도 내지 않았으면, 없음이 둘 겹친 것이라 죽은 것으로 보고 정리한다
(4절 [워커 정리] → END 없는 결과 파일 → 코디네이터가 중단으로 세어 같은 슬롯에서 다시, 두 번째면 `질문:`). 일하는 워커는 도구가 오래 돌아도 터미널에 진행 표시(경과 시간)를 계속 그리므로 둘이 함께 멈추지 않는다.
**먼저 죽지 않게 한다** — 그날 워커를 죽인 것은 에이전트가 아니라 다른 슬롯의 게이트 실행기였다: `cargo test --workspace` 의 자손 PID 를 15분 모아 두었다가 끝날 때 전부 껐는데,
그사이 끝난 자손의 PID 를 막 뜬 codex 검증 워커가 다시 받아 함께 꺼졌다(Windows 는 PID 를 곧바로 재사용한다. codex 기록은 오류 없이 09:44:05 에서 끊기고, 그 게이트의 다음 검사는 09:44:08 에 시작했다).
그래서 병렬이면 하네스 스크립트의 프로세스 정리가 `harness-setup` 7단계 "자기가 띄운 것만, 같은 프로세스인지 확인하고 끈다" 를 지키는지 세팅 때 확인한다(13단계) — 아래 정리는 그래도 죽었을 때의 안전망이다.
실전(2026-10-13, 동시 3)에서 그 codex 검증 워커가 죽었는데 생존 판정이 `unverifiable` 로 굳어 알림만 남았고(그 판정은 "증거가 아니다"였다), 생존 확인은 "빈 대기 15분" 에만 돌았는데
다른 슬롯이 5~10분마다 끝나 대기가 빌 틈이 없었다 — 그 슬롯이 1시간 반 동안 서 있었다. 그래서 생존 확인은 **도는 워커가 있는 동안 5분마다** 하고(`worker-list` 는 읽기 명령이라 워커를 건드리지 않는다),
워커 한 토막의 상한(구현 90분·검증 45분, 잠정)을 넘으면 살아 있어도 알린다 — 정리하지는 않는다.
깨우기는 `send --to dispatch:<ID>` 다 — 쉬는 워커에 오르카가 "You have 1 orchestration message" 를 입력으로 넣어 깨운다(2026-10-01 실험). 답은 늘 `reply` 로 보내고 `send` 는 깨우기에만 쓴다.
세부(항목 11개·기준값)는 4절 ② 블록·"밖의 감시" 와 8절(이 파일 2·3절)에 있다.

**②의 상태판 — 감시는 멈춘 것을 알리고, 상태판은 도는 것을 보여 준다.** 구동 스크립트는 터미널 밖으로 분리되고 판단 자식은 화면 없는 `claude -p` 라,
오르카 사이드바에는 워커 카드만 보인다 — 그 워커 줄도 `worker-task_<내부 ID>` 라 어느 태스크인지 모르고, 코디네이터는 어디에도 없다.
실전(2026-10-12)에서 사람이 "놀고 있는 것 같다·코디네이터는 어디냐" 를 거듭 물었고, 실제로는 판단 자식이 돌고 있었는데 그것을 가리려면 에이전트가 로그·프로세스·`worker-list` 를 뒤져야 했다.
그래서 **읽기만 하는 상태판** `loop-status.*` 를 둔다 — 구동 스크립트·감시가 이미 쓰는 임시 폴더 파일과 `STATE.md`, `worker-list` 만 읽어 한 화면에 다시 그린다.
아무것도 쓰지 않으므로 필자도 감시도 그대로이고, 아무 터미널에서나 띄우고 닫아도 된다. 구동 시작 명령은 분리한 뒤 그 터미널에 상태판을 그린다(로그만 흘러가던 자리).
오르카 카드 댓글(`worktree set --comment`)에 상태를 쓰는 길은 실측에서 버렸다 — 사이드바에 글자로 나오지 않고 CLI 로 지울 수도 없다(1.4.222).

**②의 답하기 — 질문을 오르카에 띄우고 그 자리에서 답을 받는다.** 루프가 사람을 부르는 길은 `STATE.md` 의 `질문:` 한 줄인데, 1.14 까지 그것을 사람에게 전하는 수단은
기록 파일 한 줄과 OS 토스트 한 번이었다(같은 알림은 한 번만). 다시 알리는 규칙은 워커의 `ask` 에만 있었고 코디네이터가 적은 `질문:` 은 다시 알리지 않았다.
실전(2026-10-13)에서 태스크 질문 하나가 토스트 한 번 뒤 1시간 반 동안 답을 기다렸다 — 사람은 오르카 화면을 보고 있었고 거기에는 아무것도 뜨지 않았다. 그래서 둘을 더한다.
- **다시 알린다** — 밖의 감시가 답 없는 `질문:` 줄마다 처음 본 시각을 적어 두고 30분·2시간·8시간에 `질문재알림` 을 낸다(요약에 그 단계 이름을 넣어 래치가 단계마다 한 번씩만 통과한다)
- **오르카에 답하기 탭을 띄운다** — 새 `질문:` 을 보면 감시가 `orca terminal create --worktree path:<코디네이터 트리> --title "질문 <n>건 — 답하기" --command "<답하기 명령>" --focus` 로 탭을 연다.
  `ORCA_*` 없이 불러도 탭이 뜨고, 그 탭은 오르카 터미널이라 `ORCA_TERMINAL_HANDLE` 을 가진다(2026-10-13 확인) — 그래서 구동 스크립트가 질문 대기로 멈춰 있으면 **그 탭에서 바로 다시 띄울 수 있다.**
  답하기가 이미 떠 있으면(`loop-answer.pid` 의 프로세스가 살아 있으면) 새로 열지 않고 그 탭을 앞으로 가져온다(`orca terminal switch --terminal <핸들>` — 실패하면 새로 연다).
  떠 있지 않으면(처음이거나 사람이 탭을 닫았다) 새로 연다. 새 질문이 생길 때와 다시 알릴 때 이렇게 한다. 탭 띄우기가 실패해도 토스트와 기록 줄은 남는다(오르카 터미널 생성은 시간 초과가 잦았다 — 2026-09 ERP)
- **답하기 스크립트** `loop-answer.*` — 답 없는 `질문:` 을 번호와 함께 보여 주고(태스크 질문이면 "그 행만 서 있다", 전역이면 "새로 띄우기가 멈춰 있다"), 답을 받아 코디네이터 트리 `STATE.md` 의
  그 질문 바로 아래에 `답: <질문 머리> — <답>` 한 줄을 적는다. **판단 자식이 도는 동안은 쓰지 않고 기다린다**(`loop-stage.txt` 가 코디네이터 자식·답변 자식) — 자식이 `STATE.md` 를 통째로 다시 쓰면
  둘 중 하나가 사라진다. 그 밖의 줄은 건드리지 않는다. 다 적은 뒤 구동 스크립트가 없으면(종료 사유 "질문 대기" 등) 다시 띄울지 묻고 구동 시작 명령을 그 탭에서 돌린다
  (분리된 뒤 그 탭은 상태판이 된다). 다시 띄우지 않으면 **탭에 머문다** — 끝나지 않고 STATE.md 를 다시 읽으며 새 질문이 생기면 다시 묻는다. 끝나 버리면 탭은 빈 셸로 남고
  감시는 "탭이 있다" 로 보아 다음 질문이 화면에 뜨지 않는다. 떠 있는 동안 `loop-answer.pid` 를 둬서 감시가 그것으로 가른다.
  사람이 손으로 `답:` 을 적거나 대화형 세션에 말하는 길은 그대로다 — 답하기 탭은 그 길을 화면 앞으로 가져온 것이다.
병렬에서 사람이 답을 적는 곳은 **코디네이터 트리의 `STATE.md`** 다 — `main` 의 것은 다음 fast-forward 에 덮이고, 코디네이터 자식은 자기 트리만 읽는다.

### 병렬 운용에서 ② 가 다른 것 (본문 11단계에서 이어짐)

- **구동 스크립트는 오르카 터미널에서 띄우고, 터미널 프로세스 밖으로 분리해 돈다** — 오르카 CLI 는 호출한 터미널을 Run 의 코디네이터로 묶는다(밖에서 띄우면 `no_active_sender_terminal`).
  띄운 뒤에는 자신을 터미널 밖에서 다시 띄우고 `ORCA_*` 는 orca 호출에만 붙여, 터미널을 닫아도 그 바인딩으로 계속 돈다(4절 ②, 8절 "분리 실행 방식").
  Run ID 는 `(임시)/loop-run.txt` 에 두고, 스크립트가 죽었다 다시 뜨면 `run-use --id <Run>` 으로 같은 Run 을 이어받는다 — 돌던 워커와 그 우편함을 잃지 않는다
- **②에서 워커의 에이전트는 워커마다 고른다** — `worker-start --agent claude|codex` 가 워커 단위라 구현은 클로드, 검증은 코덱스처럼 섞을 수 있다.
  검증을 구현과 다른 에이전트로 두면 분리가 한 겹 더 강해진다. 8절 "에이전트·모델 배치"에 적는다. 두 CLI 와 플러그인이 둘 다 설치되어 있어야 한다.
  모델도 같은 표에서 — 워커가 뜰 때 8절 표의 모델·추론 강도를 플래그로 받는다(①③도 같다. 11단계 "역할별 모델")
- **②의 워커는 `ask` 를 포그라운드로 돌린다** — 백그라운드로 걸고 턴을 끝내면 답이 와도 완료 알림을 놓친 채 잠들 수 있다
  (실전 ERP: reply 1초 뒤 도착한 백그라운드 완료 알림이 20분 가까이 처리되지 않았고, 코디네이터가 `send` 로 건드린 뒤에야 풀렸다). Claude Code 는 600초를 넘긴 명령을 백그라운드로 옮기므로
  Bash 도구 timeout 은 상한 600000, `ask --timeout-ms` 는 그보다 짧은 540000 으로 둔다. **시간 초과는 실패가 아니다** — `ask --resume <같은 메시지 ID>` 로 이어 간다
  (오르카: "Timeout leaves the question pending; resume with the original message ID"). 안 적으면 워커는 대기 창 몇 번 만에 `failed` 로 보고하려 한다.
  **연결이 끊겨 끝난 ask 도 실패가 아니다** — 오르카가 재시작되면 포그라운드 `ask` 가 "runtime closed the connection"·`runtime_unavailable` 로 끝나는데, 질문은 남아 있고 답도 그대로 받을 수 있다.
  안 적으면 워커는 `--resume` 없이 턴을 끝내 잠들고(살아 있음·`activity: done`), 답이 와도 깨어나지 않는다(2026-10-01 실험). 30초 뒤 같은 ID 로 `ask --resume`, 세 번 연속 연결이 안 되면 `failed`
  프리앰블은 `check --wait`·`ask` 안에서 막혀 있는 동안 heartbeat 를 건너뛰는 것을 허용하므로 포그라운드 대기가 heartbeat 규칙과 부딪히지 않는다. 지시문은 ② 워커 덧붙임(4절)에 있다
- **대기는 Run 단위다** — 구동 스크립트가 워커마다 기다리지 않고 `check --wait` 를 Run 에 걸고, `worker_done` 이 하나라도 오면 다음 라운드(판단 자식)로 넘어간다.
  ①-병렬처럼 전부 끝나기를 기다리지 않는 이유는 오르카가 워커마다 끝을 알려 주기 때문이다 — 빨리 끝난 슬롯이 놀지 않는다.
  판정 파일은 태스크 ID 로 파생된 경로라 셋이 동시에 검증해도 겹치지 않는다.
  **도는 dispatch 가 0개면 기다리지 않는다** — `check --wait` 를 깨우는 것은 `worker_done` 뿐인데 도는 워커가 없으면 그것이 오지 않는다. 실전(ERP phase-12)에서
  격리 3 의 e2e 가 실패해 행이 `수정` 이 된 순간 도는 워커가 없었고, 다음 라운드는 영원히 열리지 않았다. 반복의 첫 줄로 돌아가 코디네이터 자식이 그 행을 다시 배정하게 하되,
  그 한 바퀴에서도 새 dispatch·행 변화가 없으면 멈춘다 — 안 그러면 진전 없는 코디네이터 자식이 끝없이 불린다.
  대기 한 번은 60초, 생존 확인은 도는 워커가 있는 동안 **5분마다**다. 처음에는 "빈 대기 15분" 이었는데(오르카 가이드의 "빈 대기 세 번" 을 15분 대기 기준으로 읽은 것 — 60초 대기에 횟수로 세면 3분 만에 생존을 의심한다),
  동시 3 이면 다른 슬롯이 5~10분마다 끝나 대기가 빌 틈이 없어 사실상 돌지 않았다(실전 2026-10-13 — 이 파일 1절 "②의 정지 감시"). 생존 확인은 판정을 읽기만 하므로 자주 해도 워커를 건드리지 않는다 — 의심의 문턱은 횟수가 아니라 아래 시간들이다.
  생존 판정이 `exited` 인데 `worker_done` 이 없으면 결과 파일이 없을 때만 END 없는 줄을 적는다 — 코디네이터가 중단으로 세어 두 번째에 `질문:` 을 올리게 하는 것이다.
  `unverifiable`·`missing` 이고 그 워커의 전사와 터미널 출력이 둘 다 20분째 그대로면 [워커 정리](4절 — stop, 안 되면 abandon·터미널 닫기) 뒤 같은 줄을 적는다. 하나라도 움직이면 알림(`생존확인불가`)만 하고 기다린다.
  결과 파일 없이 dispatch 파일만 지우면 같은 행이 새 Task 로 다시 떠 오르카의 연속 실패 차단도 우회하며 끝없이 돈다.
  **결과 파일은 `worker_done` 뒤에 반영한다** — 워커는 결과 파일을 쓰고 나서 `worker_done` 을 보내는데, 그 사이에 다른 워커의 `worker_done` 으로 열린 코디네이터 자식이 그 파일을 먼저 반영하고 지우면,
  늦게 온 `worker_done` 을 받은 스크립트가 "결과 파일 없음" 으로 END 없는 사본을 다시 만들어 이미 끝난 행이 중단으로 세어진다(실전 2026-10-13). 그래서 코디네이터는 dispatch 파일이 남은 행의 결과 파일을 건드리지 않고,
  스크립트는 dispatch 파일이 없는 `worker_done`(재생된 배달)으로 결과 파일을 만들지 않는다

②에서는 슬롯 1 의 워커가 `--worktree path:<코디네이터 트리>`, 슬롯 2 이상이 `--worktree path:<worker-N 워크트리>` 다 — `current` 는 쓰지 않는다. 스크립트의 위치가 아니라 **그 오르카 터미널이 속한 워크트리**로 풀려, 메인 트리의 터미널에서 띄우면 슬롯 1 워커가 `main` 에 뜬다(2026-10-01 실험). `main` 에서는 띄우지 않는다. 카드 이름은 `coordinator`·`worker-N` 으로 둔다(`orca worktree set --display-name`). **워커 이름은 태스크를 만들 때 정한다** — `task-create --display-name "worker<N>_<태스크 ID>"`(검증 워커는 끝에 `_검증`) 뒤 `worker-start --task` 로 띄운다. 그 이름이 오르카의 워커 기록(`worktree ps` 의 에이전트 `displayName`)에 남는다. `worker-start --spec` 한 번으로 띄우면 기록에도 이름이 없다. (`worker-start --display-name` 은 새 워크트리를 만들 때의 워크트리 이름이라 기존 워크트리에서는 거부된다. 터미널 탭 제목은 에이전트가 덮어쓴다.)
다만 **사이드바 카드의 워커 줄은 이 이름과 무관하게 `worker-task_<내부 ID>` 로 보인다**(오르카 1.4.222, 2026-10-12 — 이름을 붙인 실전 루프에서 확인). 어느 슬롯이 어느 태스크를 하는지는 상태판(4절 ②, 8절)에서 본다.

## 3. `LOOP.md` 8절 ② 값

본문 템플릿 8절 "슬롯과 워크트리" 의 `(②면 references/orca.md 3절 …)` 줄 자리에 넣는다.

**상태판 명령**(②): (실제 명령 — 예: `node harness_setup/scripts/loop-status.mjs`, 한 번만이면 `--once`). 읽기만 하므로 아무 터미널(`main` 포함)에서 띄우고 닫아도 된다. 다시 그리는 간격 10초 · `worker-list` 30초.
**답하기 명령**(②): (실제 명령 — 예: `node harness_setup/scripts/loop-answer.mjs`. 기본은 탭에 머물며 새 질문을 기다린다. 한 바퀴만 묻고 끝내려면 `--once`). 밖의 감시가 질문이 생기면 이것을 오르카 탭으로 띄운다. 쓰는 것은 코디네이터 트리 `STATE.md` 의 사람의 `답:` 한 줄뿐이다.
오르카 사이드바로는 루프를 볼 수 없다 — 카드는 워크트리 단위라 판단 자식(`claude -p`)과 구동 스크립트는 나오지 않고, 워커 줄은 `--display-name` 과 무관하게 `worker-task_<내부 ID>` 로 보이며, 카드 댓글(`worktree set --comment`)은 글자로 보이지 않는다(오르카 1.4.222, 2026-10-12). "살아 있나·누가 무엇을 하나" 는 상태판에서 본다.
**분리 실행 방식**(②): (실제 값 — Windows: WMI `Win32_Process.Create`, 창 숨김 / macOS·Linux: `setsid nohup`). `Start-Process`·`&` 처럼 터미널 셸의 자손이면 터미널을 닫을 때 함께 죽고,
자기 환경에 `ORCA_*` 를 가진 프로세스는 트리 밖이어도 오르카가 정리한다 — 스크립트는 띄우기 때 적은 `(임시)/loop-env.json` 에서 `ORCA_*` 를 뺀 값을 자기 환경으로 쓰고 `ORCA_*` 는 orca 호출에만 붙인다(2026-10-01 탐침. macOS·Linux 는 스모크에서 확인).
**알림 수단**(②): `(임시)/loop-alerts.log` 한 줄 + OS 알림 + 답 없는 `질문:` 이면 오르카 답하기 탭(스모크에서 띄워 본 결과 — 안 뜨면 "답하기 탭 없음") — (OS 알림의 실제 값. Windows: 모듈 없이 Windows PowerShell 5.1 의 토스트 `[Windows.UI.Notifications.ToastNotificationManager]` / macOS: `osascript -e 'display notification …'` / Linux: `notify-send`). OS 알림이 실패해도 기록 줄은 남는다.
알림은 문제일 때와 **태스크·phase 가 완료될 때** 온다. 완료 알림이 태스크 하나의 보통 소요보다 오래 없으면 상태판을 본다 — 구동 스크립트와 밖의 감시가 둘 다 죽으면(재부팅·강제 종료) 알려 줄 쪽이 없다.
**감시 기준값**(②, 잠정 — 실측으로 조정): 단계 상한 — 앱 전환 5분 · 태스크 e2e 15분 · 오르카 명령 5분 · 코디네이터 자식 60분 · phase 묶음 120분(본문 8절 "phase 묶음 상한" 과 같은 값) · 답변 자식 10분 · 재시도 대기 그 회차 간격+2분 · 한도 대기 재설정 시각+15분(모르면 17분).

모델 오류 화면 — 같은 5분마다 화면 12줄을 보고, 계속을 입력한 뒤 5분에도 그대로면 정리 · 시작 때 초안이면 1회(에이전트 쪽은 Enter, 오르카 쪽은 draft 글을 다시 보냄) 뒤 30초 · 멈춘 루프(질문 대기 밖)·죽은 스크립트 재알림 30분·2시간·8시간.
**모델 오류 문구**(②, [감시 11-가] — 아는 것만 막는다): `at capacity` · `try a different model`(codex, 실측 2026-10-13). 일하는 중 표시 `esc to interrupt`. 새로 본 문구는 여기에 더한다 — 사용량 한도 문구(`usage limit`·`continuing automatically at`)는 넣지 않는다(한도는 기다리는 것이라 워커한도화면 알림만).
**임시 폴더의 구동 파일**(②): `loop-run.txt`(Run) · `loop-drive.pid`·`loop-env.json`·`loop-stage.txt`·`loop-alive.txt`·`loop-exit.txt`(종료 사유) · `loop-watch.pid`·`loop-watch.alive` · `loop-alerts.log`·`loop-latch-<실행 ID>.txt` · `answered.txt` · `dispatch-<ID>.txt`·`done-`·`verdict-`·`e2e-<ID>.txt` · `bundle-phase-NN.txt`·`.log`·`.pid`(phase 완료 묶음 — 결과·출력·도는 묶음 프로세스) · `nudged.txt`(구동기가 직접 입력한 워커 터미널 핸들 — release 뒤 이것만 닫는다) · `loop-drive.log` · `loop-watch-questions.json`(질문을 처음 본 시각)·`loop-answer-tab.txt`(답하기 탭 핸들)·`loop-answer.pid`(답하기가 떠 있는 동안).
이것은 기록이 아니라 구동 상태다(기록처는 `STATE.md`·`LOG.md` 둘뿐) — 커밋하지 않고, 지울 때는 스크립트가 멈춘 뒤에 지운다.
구동 스크립트와 밖의 감시가 서로 읽는 파일의 모양은 고정이다 — `loop-drive.pid`·`loop-watch.pid` = JSON `{"pid": <숫자>, "start": "<시작 시각 읽기 명령의 출력>", "run": "<실행 ID>"}` · `loop-stage.txt` = JSON `{"stage": "<단계>", "at": "<ISO 시각>", "until": "<ISO — 쉬는 단계에서 끝날 시각을 알 때만. 한도 재설정 시각을 모르면 쓰지 않는다 — 감시는 17분으로 잰다>", "run": "<실행 ID>"}`
(단계 이름: 시작 · 대기 · 코디네이터 자식 · 답변 자식 · 오르카 명령 · 앱 전환 · 태스크 e2e · phase 묶음 · 재시도 대기 · 한도 대기) · `loop-alive.txt` = ISO 시각 한 줄 · `loop-exit.txt` = 종료 사유 한 줄 · `loop-latch-<실행 ID>.txt` = 줄마다 `<종류>|<대상>|<요약>`.
**구동 터미널은 구동 전용이다**(②) — 오르카는 Run 에 읽지 않은 메시지가 남아 있으면 `You have N orchestration message. Run \`orca orchestration check …\`` 를 그 터미널의 **입력으로** 넣는다.
셸이면 명령으로 실행하려다 오류 한 줄을 내고 끝난다(무시한다 — 메시지는 스크립트가 받는다). 그 터미널에서 대화형 에이전트가 돌면 이 문구가 사람 말로 섞여, 그 세션이 지시대로 `check` 를 불러 스크립트가 처리할 배달을 가져갈 수 있다 —
그 터미널에서 대화형 에이전트를 열지 않는다. 스크립트는 자식(`claude -p`·`orca`)에게 터미널 입력을 물려주지 않는다(표준 입력 `ignore`).
분리 뒤 그 터미널에 그리는 상태판은 입력을 읽지 않으므로 이 문구에 반응하지 않는다(상태판을 끄면 셸이 받아 오류 한 줄을 낸다 — 무시한다).
**대기 한 번의 길이**(②): `60000`ms(60초). 기다리는 것은 스크립트라 짧아도 토큰이 들지 않고, 짧아야 대기 뒤의 확인을 제때 한다. 빈 대기는 체크포인트다. 생존은 대기가 비든 아니든 **도는 워커가 있는 동안 5분마다** `worker-list` 로 본다([감시 11] — 동시 3 에서는 대기가 15분씩 비지 않는다).

## 4. 12단계 — 오르카 응답 모양과 스모크 테스트

오르카 `--json` 응답은 **들여쓴 여러 줄 JSON 봉투** `{"id", "ok", "result"}` 다(거부는 `"ok": false` + `error.code` + 종료 코드 1, 연결이 끊긴 호출 실패는 JSON 이 없다). 출력 전체를 한 번에 읽는다 —
한 줄만 읽던 스크립트가 실전 첫 호출(`run-create` 성공)을 실패로 읽고 멈췄다(2026-10-01). 결과 모양도 지어내지 않는다 — `run-create` 는 `result.run.id`, `task-create` 는 `result.task.id`,
`worker-start` 는 `result.dispatchId`, `check` 는 `result.deliveryId`·`messages[]`·`replayed`(메시지의 `payload` 는 JSON **문자열**이고 `dispatchId` 는 그 안에 있다), `worker-list` 는 `result.workers[]`(각 `dispatchId`·`projection.liveness.verdict`(`live`·`exited` …)·`projection.stage.activity`(`working`·`done`·`unknown` …)). 없는 Run 을 물어도 실패가 아니라 빈 `workers` 다.

- **②는 스모크 테스트** — 오르카 터미널에서 Run 을 하나 만들고 **가벼운 모델의 시험 워커 하나**에 "파일을 고치지 말고, ask 로 한 번 묻고, 받은 답을 결과 파일에 END 까지 쓰고 worker_done --report-path 로 끝내라"를 준다.
  스크립트가 질문을 받아 `claude -p` 로 답하고, `worker_done` 과 결과 파일을 받고, `worker-release` 까지 돌면 통과다(실측 1분 안쪽).
  스모크도 실제와 같이 **분리해서** 띄우고, 도는 동안 그 터미널을 닫아 본다 — 스크립트가 살아서 끝까지 가고(생존 파일이 계속 갱신된다), 밖의 감시가 떠서 알림 수단으로 시험 알림 하나를 보내면 통과다.
  macOS·Linux 의 분리 방식(`setsid nohup`)은 아직 실측이 없다 — 여기서 확인한 결과를 8절에 적는다. 닫기를 살아남지 못하면 "터미널을 닫지 마라" 를 8절에 적는다
  **상태판도 스모크 안에서 확인한다** — 시험 워커가 도는 동안 다른 터미널에서 `loop-status --once` 를 돌려 "● 돌고 있음"·시험 워커 행·단계가 나오고,
  스모크가 끝난 뒤 다시 돌려 "○ 멈춤 — <종료 사유>" 가 나오면 통과다. 상태판이 돈 뒤 임시 폴더의 파일 목록·수정 시각이 그대로인지도 본다(읽기만 해야 한다)
  **답하기 탭도 스모크 안에서 띄워 본다** — 감시가 쓰는 것과 같은 `orca terminal create … --command "<답하기 명령> --once"` 를 `ORCA_*` 없이 불러 오르카에 탭이 뜨고 "답 없는 질문 없음" 이 나오면 통과(그 탭은 닫는다).
  `--once` 는 한 바퀴만 묻고 끝나는 옵션이다(질문이 없으면 그 한 줄을 내고 끝난다). 탭이 뜨지 않으면 8절 알림 수단에 "답하기 탭 없음 — 토스트·기록 줄만" 을 적는다
  **시험 워커의 시작 화면도 본다** — `worker-start` 가 `outcome_unknown` 이면 `orca terminal read --terminal <핸들> --screen --limit 12 --json` 으로 지시문이 어디 남았는지 보고 —
  에이전트 입력 줄(`› [Pasted Content N chars]` 등)인지 오르카 쪽 `draft` 값뿐인지 — 4절 [감시 5] 의 두 갈래에 걸리는지 확인한다. 다른 모양이면 그 모양을 더하고 8절 "스모크 테스트"에 적는다(에이전트 CLI 판마다 바뀐다).
  `[워커 정리]` 도 한 번 돌려 본다 — 시험 워커에 `worker-abandon` → `terminal close` → 닫힘 확인이 되는지(오르카 판마다 상태 이름이 바뀐다)
  이것이 도는지 보지 않고 루프를 넘기면 첫 phase 에서 사람이 스크립트를 고치게 된다. 결과를 8절 "스모크 테스트"에 적는다
