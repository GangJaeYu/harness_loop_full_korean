# Codex 환경 보조 지침 (plan-generator)

## 세 입력을 읽는 방법

`docs/PRD.md`, `docs/TRD.md`, `docs/ARCHITECTURE/` 아래 마크다운 **전부**를 읽는다.
셸에서 파일 목록을 먼저 뽑고(`ls docs/ARCHITECTURE/`) 하나도 건너뛰지 않는다.
아키텍처 파일 하나를 빠뜨리면 그 영역의 설계 단위가 통째로 태스크 없이 남고, 그 부분은 아무도 만들지 않게 된다.

요약본으로 대체하면 안 되는 곳은 PRD의 4·5·8·**9절(추적표)**, TRD의 각 TD 확정도와 12절,
overview.md의 3절(의존 방향)·4절(핵심 흐름)·**7절(CF 표)**·8절(추적표), 그리고 영역 문서의 번호 절 전부다.
**번호 절 하나가 태스크의 씨앗**이라, 요약하는 순간 잘라야 할 대상이 사라진다.

기존 프로젝트라면 셸에서 현재 파일 구조를 먼저 확인한다. 태스크의 `files` 는 실제 경로여야 한다 —
존재하지 않는 경로를 적으면 루프가 첫 태스크에서 헤맨다.

## 차단과 분할은 번호 목록으로 한 번에

선택지 UI가 없으므로 **표 하나로 모아** 제시하고 한 번에 답을 받는다.
차단 항목을 여러 턴에 흩뿌리면 답이 누락되고, 누락된 차단은 그냥 진행한 것과 구별되지 않는다.

```
플랜을 만들기 전에 정할 것이 있습니다. 앞 문서에 미해소 차단이 3건 남아 있습니다.
("1: A, 2: B" 형태로 답해 주셔도 됩니다.)

1) OQ-007 (계약서 템플릿 법적 검토) — FR-006·FR-011 차단
   A) 지금 해소하고 플랜을 만든다  → 태스크 5개가 정상 생성됩니다
   B) blocked 로 만들고 나머지부터 → phase-03 의 태스크 5개가 blocked. phase-03 전체가 대기합니다

2) CF-006 (P0 뼈대: 예) — 계약서 개체·공유 경로 설계
   A) 앞 문서로 돌아간다          → 권장. 뒤집히면 phase-03 이 통째로 재작업입니다
   B) 잠정 설계대로 blocked 생성  → 태스크는 만들되 실행하지 않습니다
```

각 선택지에 **그 선택으로 태스크 몇 개가 막히는지**를 붙인다.
영향 감각 없이 고르면 사용자는 가장 빨라 보이는 것을 고르고, 실제 비용은 Layer 5에서 청구된다.

phase 분할 방식이 둘 이상 그럴듯하면 같은 목록에 넣어 함께 묻는다. **묻는 것은 한 번이다.**
태스크마다 확인을 구하면 사용자가 플랜을 대신 짜게 된다.

## 파일 작성

`plan_setup/` 아래 디렉터리를 만들고 파일 쓰기 도구나 heredoc 으로 만든다. 순서는 이게 낫다.

1. 태스크 문서 → 2. phase 문서 → 3. `PLAN.md` → 4. `STATE.md`·`LOG.md` → 5. `docs/PRD.md` 9절 갱신

**PRD 는 통째로 다시 쓰지 않는다.** 9절 추적표에서 `담당 태스크` 의 `(Layer 3에서 채움)` 을 태스크 ID 목록으로,
`상태` 를 `계획됨`(차단이면 `계획됨(차단)`)으로 바꾼다. 다른 열과 다른 절은 그대로 둔다 — 사용자가 손으로 고친 문장이 사라진다.

태스크 문서에는 YAML frontmatter 가 있다. heredoc 으로 쓸 때 앞뒤 `---` 이 파일의 첫 줄부터 시작하는지,
목록 항목의 들여쓰기가 무너지지 않았는지 확인한다. **frontmatter 가 깨지면 루프가 `status` 와 `depends_on` 을 못 읽는다.**
`phase` 값은 반드시 따옴표로 묶는다 — `02` 는 YAML에서 정수 `2` 가 되어 파일 이름과 어긋난다.

다 쓴 뒤 셸로 실제 파일 목록을 뽑아 **각 태스크의 `id` 가 확장자를 뗀 자기 파일 이름과 같은지** 확인한다.
어긋나면 STATE.md 가 가리키는 파일을 루프가 찾지 못한다. 태스크가 수십 개면 눈으로 세는 것보다 스크립트가 정확하다.

승인 모드에 따라 쓰기 권한 요청이 필요하니, 작성 직전에 만들 디렉터리와 파일 개수를 알린다.

이미 `plan_setup/` 이 있으면 **10단계(부분 갱신)만 한다.** 바뀌는 태스크 문서와 PLAN.md 색인 행만 고치고 heredoc 으로 전체를 다시 만들지 않는다.
**특히 `STATE.md` 와 `LOG.md`** 는 루프가 진행 상황을 기록해 둔 파일이라, 초기값으로 덮으면 어디까지 했는지가 사라진다.
`Task Status` 에 행을 더하고 `LOG.md` 끝에 한 줄 덧붙이는 것까지가 이 스킬의 몫이다.

## `AGENTS.md` 는 `CLAUDE.md` 를 가리키는 한 줄

Codex 는 프로젝트 루트의 `AGENTS.md` 를 자동으로 읽고 `CLAUDE.md` 는 읽지 않는다. 본문을 두 파일에 두면 곧 어긋나므로
본문은 SKILL.md 의 "`CLAUDE.md` 갱신" 절대로 `CLAUDE.md` 에만 쓰고, `AGENTS.md` 에는 아래 한 줄만 둔다.
없으면 만들고, 이미 다른 내용이 있으면 그 줄을 맨 위에 더한다.

```
CLAUDE.md 를 읽고 따른다.
```

## 다음 스킬 연결

Codex에서는 스킬 자동 호출을 기대하지 말고 다음 단계를 명시적으로 남긴다.
예: `다음 단계: harness-setup 스킬(SKILL.md)을 읽고 plan_setup/PLAN.md 와 phase·task 문서를 입력으로 harness_setup/quality_gates/ 를 구성합니다.`

차단된 태스크가 남아 있으면 그 목록을 함께 남긴다. 하네스가 검증할 수 없는 태스크에 게이트를 세우지 않게 해야 한다.
