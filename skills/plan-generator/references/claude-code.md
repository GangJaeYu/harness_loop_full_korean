# Claude Code 환경 보조 지침 (plan-generator)

## 세 입력을 읽는 방법

`docs/PRD.md`, `docs/TRD.md`, `docs/ARCHITECTURE/*.md` 를 Read 로 읽는다.
아키텍처는 Glob 으로 `docs/ARCHITECTURE/*.md` 목록을 먼저 잡고 **전부** 읽는다.
파일 하나를 건너뛰면 그 영역의 설계 단위가 통째로 태스크 없이 남고, 그건 "그 부분은 아무도 안 만든다"는 뜻이 된다.

특히 아래는 요약하지 말고 그대로 본다.

| 문서 | 절 | 왜 |
|---|---|---|
| PRD | 4·5절(FR·NFR), 8절(미결), **9절(추적표)** | 태스크가 덮어야 할 목록 전체. 9절은 나중에 직접 고칠 표다 |
| TRD | 각 TD의 확정도, 12절(미결) | 잠정 결정 위의 태스크에 '바뀔 수 있는 지점'을 적어야 한다 |
| ARCHITECTURE/overview.md | 3절(의존 방향), 4절(핵심 흐름), **7절(CF 표)**, 8절(추적표) | 태스크 순서와 차단 판정의 재료 |
| ARCHITECTURE 영역 문서 | 번호 절 전부 | 절 하나하나가 태스크의 씨앗이다 |

파일이 길어 한 번에 안 들어오면 offset·limit 으로 나눠 읽되, 건너뛰지 않는다.

Explore 서브에이전트에게 **"아키텍처 문서의 모든 번호 절 목록과 각 절의 근거 FR·NFR·TD를 뽑아라"** 를 시켜
설계 단위 목록을 만드는 데 쓸 수 있다. 다만 그 결과를 그대로 태스크로 옮기지 않는다 —
자르는 판단(파일 하나인가, 검증 가능한가)은 직접 한다.

## 기존 코드베이스가 있으면

Glob·Grep 으로 현재 파일 구조를 먼저 확인한다. 태스크의 `files` 는 실제 경로여야 한다.
**존재하지 않는 파일을 `files` 에 적으면 루프가 첫 태스크에서 헤맨다.** 새로 만드는 파일이면 "새로 만든다"를 본문에 적는다.

기존 프로젝트의 플랜은 "처음부터 만드는 순서"가 아니라 **"지금 상태에서 무엇을 더할 것인가"**다.
이미 구현된 요구사항이 있으면 그 태스크를 만들지 말고, PRD 추적표의 `담당 태스크` 열에 "구현됨"으로 남긴다.

## 차단·범위 판단은 AskUserQuestion 으로

이 스킬은 대화가 필요한 지점이 둘이다.

**차단이 남아 있을 때 (1·2단계).** 차단 미결이나 `P0 뼈대: 예` 미해소 충돌이 있으면 플랜을 만들기 전에 묻는다.

- 선택지 ①앞 문서로 돌아가 해소하고 온다(권장) ②차단 태스크를 `blocked` 로 만들고 나머지부터 진행한다
- `option.description` 에 **그 선택으로 몇 개의 태스크가 막히는지**를 적는다.
  ("OQ-007이 남으면 phase-03 의 태스크 다섯 개가 blocked 로 생성됩니다. phase-03 은 전체가 대기합니다.")

**phase 분할을 고를 때 (4단계).** 나누는 방식이 둘 이상 그럴듯하면 묻는다.
다만 **한 번만 묻는다.** 태스크마다 확인을 구하면 사용자가 플랜을 대신 짜게 된다.

한 호출에 최대 4개까지 묶되, **앞의 답이 뒤 선택지를 바꾸는 것은 묶지 않는다.**
차단 처리 방식의 답이 phase 분할을 바꾸므로 이 둘은 같은 호출에 넣지 않는다.

## 파일 작성

디렉터리를 만들고 Write 로 쓴다. 순서는 이게 낫다.

1. 태스크 문서 (설계 단위에서 자른 것)
2. phase 문서 (그 phase의 태스크 표가 확정된 뒤)
3. `PLAN.md` (색인·추적표가 전부 확정된 뒤)
4. `STATE.md`, `LOG.md`
5. `docs/PRD.md` 9절 갱신

**PRD 갱신은 Edit 으로 두 열만 고친다.** 파일을 Write 로 다시 쓰면 사용자가 손으로 고친 문장이 사라진다.
`담당 태스크` 의 `(Layer 3에서 채움)` 을 태스크 ID 목록으로, `상태` 를 `계획됨`(차단이면 `계획됨(차단)`)으로 바꾸는 것뿐이고,
다른 열·다른 절은 건드리지 않는다.

태스크가 수십 개가 되므로 다 쓴 뒤 Glob 으로 실제 파일 목록을 뽑아 확인한다. 확인할 것은 둘이다 —
**각 태스크의 `id` 가 확장자를 뗀 자기 파일 이름과 같은가**, PLAN.md 색인이 그 목록과 일치하는가.
`id` 가 어긋나면 STATE.md 가 가리키는 파일을 루프가 찾지 못한다. 사람이 눈으로 세는 것보다 스크립트가 정확하다.

이미 `plan_setup/` 이 있으면 **10단계(부분 갱신)만 한다.** Write 가 아니라 Edit 로 바뀌는 태스크 문서와 PLAN.md 색인 행만 고친다.
**STATE.md 와 LOG.md 는 특히 조심한다** — 루프가 진행 상황을 기록해 둔 파일이라, 초기값으로 덮으면 어디까지 했는지가 사라진다.
`Task Status` 에 행을 더하고 `LOG.md` 끝에 한 줄 덧붙이는 것까지가 이 스킬의 몫이다.
