- **버전**: 0.1 (초안)
- **작성일**: 2026-09-08
- **입력 문서**: docs/PRD.md (버전 0.1)
- **상태**: 사람 검토 대기
- **주의 1**: 프로젝트 여건(인원·기간·익숙한 스택·운영 인력·예산·배포 대상·OS)을 사용자에게 확인하지 못한 채 작성했다. 확인했어야 할 질문은 `questions.md` 에 그대로 남겼고, 가정으로 채운 값은 전부 `(가정)` 으로 표기했다.
- **주의 2**: PRD 8절의 **차단 미결이 남은 상태**로 작성했다. PRD의 OQ-001(전자서명), OQ-007(템플릿 법적 검토), OQ-010(개인정보 국내 저장 강제 여부)이 미해소다. 절차상 사용자가 ①PRD로 돌아가 해소 ②기본값으로 진행하되 영향 결정을 '잠정' 처리 중 하나를 골라야 하지만, 대화가 불가능하므로 **②를 가정으로 택했다.** 영향받는 TD-016, TD-009의 확정도를 `잠정` 으로 내렸다. 되돌리기 비용은 각 결정에 적혀 있다.

## 1. 개요

### 1.1 이 문서의 범위

이 문서는 PRD가 약속한 것을 **어떤 기술로 만들 것인가**만 정한다. 스택·데이터 저장소·통신 방식·인증 모델·보안 원칙·테스트 도구·배포 형태를 결정 단위(TD-0xx)로 고정하고, 각 결정에 근거가 된 PRD 요구사항과 검증 방법·되돌리기 비용을 붙인다.

정하지 **않는** 것: 테이블 컬럼과 인덱스, API 엔드포인트 스키마, 모듈·컴포넌트 구조는 Layer 2 아키텍처가 정한다. 개발 순서와 태스크 분할은 Layer 3 마스터 플랜이, 품질 게이트 구성·E2E가 덮을 흐름 목록·task validation 절차는 Layer 4 하네스가 정한다. 테스트에 관해 여기서 정하는 것은 **도구와 반드시 덮어야 할 영역까지**다.

이 문서는 요구사항을 만들지 않는다. 기술을 고르는 중에 필요해 보인 기능이 있으면 TRD 본문에 적지 않고 PRD로 돌려보낸다(이번 작성에서 신설한 기능 요구사항은 없다).

## 3. 스택

#### TD-001. 언어·런타임: TypeScript / Node.js LTS
- **영역**: 스택
- **근거 요구사항**: 여건(개발 인원 1명·기간 3개월), NFR-010(브라우저 3종에서 전 기능 동작), NFR-011(375px 반응형) — 화면이 제품의 대부분이므로, 브라우저에서 도는 언어를 서버에서도 쓰면 1인이 유지할 언어가 하나로 줄어든다
- **결정**: 프론트엔드와 서버 로직을 모두 TypeScript로 쓰고 런타임은 Node.js LTS를 쓴다. 금액·인보이스 상태·과세 방식 같은 값은 타입으로 좁혀 컴파일 시점에 걸리게 한다. 패키지 매니저·포매터·린터는 이 결정에 따라오는 것이므로 별도 결정으로 세우지 않는다
- **검토한 대안**: ①Python + 별도 프론트엔드 — 서버는 편해지지만 화면 코드가 다른 언어가 되어, 1인 3개월에서 문맥 전환 비용이 그대로 일정에서 빠진다. 금액 계산(NFR-008)과 검증 규칙을 두 언어로 각각 구현하게 된다. ②Node.js 외의 JS 런타임 — PDF 생성(TD-017)과 DB 드라이버의 검증된 조합이 적어, 문제가 났을 때 답을 찾는 시간이 길다
- **확정도**: 확정 — 단 1.3절의 '팀이 익숙한 스택'이 가정이다. 틀리면 OQ-016의 답에 따라 다시 정한다
- **되돌리기 비용**: 전 코드베이스 재작성. 사실상 프로젝트 재시작
- **검증 방법**: 타입 검사 명령이 오류 0건으로 끝난다. 화면 코드와 서버 코드가 같은 금액 타입·검증 스키마 정의를 참조한다(중복 정의가 없다)

#### TD-002. 애플리케이션 프레임워크: Next.js 단일 배포 단위
- **영역**: 스택
- **근거 요구사항**: NFR-001(대시보드·프로젝트 상세 P95 1.5초), NFR-011(375px 반응형), NFR-012(로그인 없이 링크 열람), NFR-013(월 99% 가동률), 여건(1인 운영·예산 5만 원)
- **결정**: React 기반 Next.js 하나에 화면과 서버 로직을 함께 둔다. 배포 산출물은 1개다. 데이터가 많은 화면(대시보드·프로젝트 상세·공유 열람)은 서버에서 렌더해 내려보내 왕복을 줄인다. 스타일링은 유틸리티 CSS(Tailwind CSS)로 하고, 접근성이 필요한 소수 요소(모달·드롭다운)만 헤드리스 컴포넌트를 쓴다 — 이는 이 결정에 흡수된 잔가지다
- **검토한 대안**: ①SPA + 별도 API 서버 — 배포 단위가 2개가 되어 NFR-013의 월 7.2시간 다운타임 예산을 두 곳에서 쓰게 되고, 1인 운영에서 배포 실패 지점이 두 배가 된다. 예산도 인스턴스 2개로 늘어난다. ②서버 렌더 없는 SPA — 공유 링크(NFR-012)를 연 클라이언트가 JS 번들을 받은 뒤에야 문서를 보게 되어, "링크 클릭 이상을 요구하면 이탈한다"(PRD 2절)와 충돌한다
- **확정도**: 확정
- **되돌리기 비용**: 높음. 화면 계층 전면 재작성. 서버 로직은 대부분 옮길 수 있으나 라우팅·데이터 로딩 규약이 전부 바뀐다
- **검증 방법**: JavaScript를 끈 브라우저에서 공유 링크를 열면 계약서 본문과 고지 문구가 표시된다(NFR-012, NFR-014). 프로젝트 200건·인보이스 1,000건 상태에서 대시보드 응답이 P95 1.5초 이내다(NFR-001)

## 4. 데이터

#### TD-003. 저장소: 관계형 DB 1개 (PostgreSQL)
- **영역**: 데이터
- **근거 요구사항**: NFR-008(금액 정수 저장, 반올림 오차 없음), NFR-001(200 프로젝트·1,000 인보이스에서 P95 1.5초), FR-005(프로젝트 상세에 계약서·인보이스·집계를 함께 표시), FR-012(프로젝트–인보이스 연결), FR-013(계정 안에서 유일한 인보이스 번호)
- **결정**: 관리형 PostgreSQL 인스턴스 1개를 쓴다. 스키마 변경은 코드와 함께 버전 관리되는 마이그레이션 파일로만 한다. 데이터 접근은 타입이 붙는 단일 접근 계층을 통해서만 하고, 원시 SQL은 집계 질의에 한해 허용한다 — 마이그레이션 도구와 접근 계층 선택은 저장소를 고르면 따라오므로 이 결정에 흡수한다. 시각은 UTC로 저장하고 표시 시점에 KST로 변환한다(FR-010의 열람 시각, FR-019의 기한 판정 기준을 한 곳으로 고정하기 위해서다)
- **검토한 대안**: ①문서형 DB — 클라이언트·프로젝트·계약서·인보이스가 항상 함께 조회되는 것이 FR-005의 존재 이유인데, 이 구조에서는 조인을 애플리케이션이 떠안고 미수금 합계(FR-005·FR-020)의 정합성도 애플리케이션 책임이 된다. FR-013의 계정 내 번호 유일성도 DB가 아니라 코드가 지키게 된다. ②파일 기반 임베디드 DB — 배포마다 파일이 사라지지 않게 볼륨을 직접 관리해야 해서, 운영 인력이 없다는 여건과 정면으로 충돌한다. 백업(NFR-007의 전제)도 직접 만들어야 한다
- **확정도**: 확정
- **되돌리기 비용**: **높음.** 데이터 접근 계층 전면 재작성 + 저장된 데이터 이전이 별도 태스크로 추가된다. 이 문서에서 가장 비싼 결정 중 하나다
- **검증 방법**: 마이그레이션을 빈 DB에 처음부터 적용하면 오류 없이 끝나고 되돌리기도 동작한다. 프로젝트 200건·인보이스 1,000건을 넣은 상태에서 프로젝트 상세와 대시보드 조회가 P95 1.5초 안에 든다(NFR-001). 같은 계정에서 인보이스 2건을 동시에 생성해도 같은 번호가 두 건 만들어지지 않는다(FR-013)

#### TD-004. 금액은 정수로 저장하고, 세액 계산은 서버 한 지점에서만 한다
- **영역**: 데이터
- **근거 요구사항**: NFR-008(원 단위 정수, 표시·PDF·합계 어디서도 반올림 오차 없음), FR-014(부가세 10%·원천징수 3.3%, 원 단위 절사), NFR-016(KRW 단일)
- **결정**: 모든 금액은 원 단위 정수(64비트)로 저장하고, 애플리케이션 안에서도 부동소수점 타입에 담지 않는다. 부가세·원천징수 계산과 절사는 서버의 계산 모듈 하나에서만 수행하고, 화면·PDF·목록 집계는 그 결과값을 받아 표시만 한다. 통화 추상화는 만들지 않는다(NFR-016)
- **검토한 대안**: ①십진 소수 타입으로 원 미만까지 저장 — FR-014가 원 단위 절사를 명시하므로 저장할 소수부가 없고, 표시 지점마다 반올림 규칙이 갈릴 여지만 생긴다. ②화면에서도 계산 — 같은 인보이스의 금액이 화면과 PDF에서 1원 달라지는 사고가 NFR-008 위반으로 직결된다
- **확정도**: 확정
- **되돌리기 비용**: 낮음. 계산 모듈과 컬럼 타입 변경 + 저장된 금액 변환 마이그레이션 1회
- **검증 방법**: 공급가액 1,000,003원에 원천징수 3.3%를 적용하면 원천징수액 33,000원·실수령액 967,003원이 화면·PDF·목록 집계 세 곳에서 동일하게 나온다. 저장한 금액을 조회하면 입력값과 정확히 일치한다

#### TD-005. 삭제는 논리 삭제 + 30일 뒤 물리 파기
- **영역**: 데이터
- **근거 요구사항**: NFR-007(삭제 문서 30일 복구 가능 후 자동 파기, 계정 해지 30일 뒤 개인정보 파기), FR-023(문서·클라이언트 삭제), FR-024(처리방침의 파기 시점과 일치)
- **결정**: 삭제 시 삭제 시각을 기록하고 모든 조회에서 제외한다. 30일이 지난 것은 정기 작업이 물리 삭제한다. 계정 해지도 같은 방식이다. 정기 작업은 별도 서버 없이 배포 환경의 스케줄 실행 기능으로 하루 1회 돌린다 — 실행 위치는 TD-016에 흡수된다. 논리 삭제된 데이터는 목록·검색·대시보드·공유 링크 어디에서도 조회되지 않는다
- **검토한 대안**: ①즉시 물리 삭제 — NFR-007의 "30일간 복구 가능"을 만족할 수 없다. ②별도 아카이브 저장소로 이동 — 저장소가 하나 늘고 파기 시점을 두 곳에서 관리하게 되는데, 데이터 규모(1인·프로젝트 수백 건)가 이를 요구하지 않는다
- **확정도**: 확정
- **되돌리기 비용**: 중간. 모든 조회 경로의 삭제 필터 제거와 정기 작업 폐기. 이미 논리 삭제 상태인 데이터의 처리 방침을 다시 정해야 한다
- **검증 방법**: 문서를 삭제하면 목록·검색·대시보드·공유 링크에서 즉시 사라지고 DB에는 삭제 시각이 기록된 행이 남아 있다. 삭제 시각을 31일 전으로 조작한 뒤 파기 작업을 실행하면 그 행이 DB에서 사라진다

#### TD-006. 생성 문서(PDF)를 저장하지 않는다
- **영역**: 데이터
- **근거 요구사항**: NFR-007(보관·파기 시점이 정해져 있어야 한다), FR-008·FR-015(PDF 내려받기), NFR-015(개인정보 국외 이전 금지), 예산 여건
- **결정**: PDF를 파일로 보관하지 않고 내려받기 요청 시마다 현재 문서 데이터로 생성해 응답 본문으로 돌려준다. 따라서 오브젝트 스토리지·파일 서버·업로드 경로를 두지 않는다. 사용자가 올리는 파일도 이번 버전에는 없다(PRD에 해당 FR 없음)
- **검토한 대안**: 생성한 PDF를 스토리지에 저장하고 재사용 — 저장소가 하나 늘고 NFR-007의 파기 대상이 DB 밖으로 확장된다. 문서 수정 후 옛 PDF가 남는 정합성 문제도 생긴다. 재생성 비용이 NFR-002의 10초 예산 안이라면 얻는 것이 없다
- **확정도**: 확정 — 단 OQ-014의 스파이크 결과 생성 시간이 예산을 넘으면 캐시 형태로 다시 본다
- **되돌리기 비용**: 낮음~중간. 스토리지 도입과 저장·무효화·파기 경로 추가. 새 저장소가 NFR-015의 리전 제약을 함께 받는다
- **검증 방법**: 계약서 본문을 수정한 직후 PDF를 내려받으면 수정 내용이 반영되어 있다. 파일 저장소를 사용하는 코드 경로가 저장소 전체에 존재하지 않는다

#### TD-007. 감사 이력은 같은 DB의 추가 전용 테이블에 1년 보존
- **영역**: 데이터
- **근거 요구사항**: NFR-009(인보이스 상태 변경·공유 링크 발급/폐기·공유 링크 열람을 시각과 함께 최소 1년 보존), FR-010(열람 기록 표시), FR-018(상태 변경 이력)
- **결정**: 위 세 종류의 사건을 같은 DB의 추가 전용(수정·삭제하지 않는) 이력 테이블에 기록한다. 애플리케이션 코드에 이력 수정 경로를 만들지 않는다. 보존 기간은 1년이며 TD-005의 파기와 별개로 관리한다(문서를 삭제해도 이력은 남는다). 로그 파일이 아니라 DB에 두는 이유는 FR-010이 열람 횟수를 화면에 표시해야 하기 때문이다
- **검토한 대안**: 애플리케이션 로그에만 남긴다 — FR-010이 최초·최근 열람 시각과 총 횟수를 화면에 표시하도록 요구하므로 조회 가능한 저장이 필요하다. 로그 1년 보존(NFR-009)도 로그 서비스 비용으로 돌아온다
- **확정도**: 확정
- **되돌리기 비용**: 낮음. 기록 지점과 조회 지점 변경
- **검증 방법**: 인보이스를 발송→입금완료→발송으로 되돌리면 이력 3건이 시각·변경 전후 상태와 함께 남는다(FR-018). 공유 링크를 5회 열면 열람 이력이 5건 쌓이고, 소유자가 로그인 상태로 문서를 연 것은 포함되지 않는다(FR-010)

## 5. API

#### TD-008. 자체 클라이언트 전용 HTTP + JSON, 단일 오류 형식
- **영역**: API
- **근거 요구사항**: FR 전반(화면과 서버 사이의 모든 상호작용), FR-003·FR-004·FR-013·FR-014(다수 수용 기준이 "해당 입력란에 오류가 표시된다"를 요구), NFR-004(권한 위반 시 404), 여건(1인·3개월)
- **결정**: 통신은 HTTP + JSON으로 하고 소비자는 이 제품의 웹 클라이언트뿐이다. 공개 API가 아니므로 URL 버전 정책을 두지 않는다(외부에 열게 되는 시점에 다시 정한다). 오류 응답은 전 경로가 하나의 형식을 쓴다 — 기계가 읽는 코드, 사람이 읽는 한국어 메시지, 입력 오류일 때 어느 입력란인지. 화면의 인라인 오류 표시가 이 필드를 그대로 쓴다. 권한 없음과 부재는 구분하지 않고 404로 통일한다(TD-012). GraphQL·RPC 계층을 두지 않는다
- **검토한 대안**: ①GraphQL — 클라이언트가 하나뿐이라 질의 유연성이 필요 없고, 스키마·리졸버·N+1 대응이 1인 3개월 일정에서 순비용이다. ②경로마다 자유 형식 오류 — 형식이 갈리면 화면마다 오류 파싱 코드를 다시 쓰게 되고, FR-003·FR-004의 "해당 입력란" 요구가 화면마다 다르게 구현된다
- **확정도**: 확정
- **되돌리기 비용**: 낮음~중간. 오류 형식 변경은 서버 응답 생성부와 화면 오류 표시부 양쪽 수정
- **검증 방법**: 사업자등록번호를 9자리로 보내면 오류 응답에 해당 입력란 식별자가 포함되고 화면의 그 칸에 메시지가 뜬다(FR-003). 인증·권한·검증·서버 오류 네 가지 상황의 응답이 모두 같은 키 구조를 갖는다

#### TD-009. 외부 연동은 트랜잭션 메일 발송 서비스 1개
- **영역**: API
- **근거 요구사항**: FR-002(비밀번호 재설정 메일), FR-017(인보이스 메일 발송), NFR-015(개인정보 국외 이전 금지)
- **결정**: 이번 버전이 붙는 외부 서비스는 트랜잭션 메일 발송 하나뿐이다. 결제·전자서명·오픈뱅킹·세금계산서 연동은 PRD 6절이 범위 밖으로 두었으므로 연동 지점을 만들지 않는다. 메일 발송은 인터페이스 하나를 두고 그 뒤에서 제공자를 교체할 수 있게 한다 — PRD OQ-011(도달률 실험)의 결과로 제공자를 바꿔야 할 수 있기 때문이다. 발송 실패는 사용자에게 그대로 표시하고 인보이스 상태를 바꾸지 않는다(FR-017)
- **검토한 대안**: 서버에서 직접 SMTP로 발송 — 발신 도메인 평판을 직접 관리해야 하고, 운영 인력이 없다는 여건에서 스팸 분류(OQ-011)를 해결할 수단이 없다
- **확정도**: **잠정 (PRD OQ-011·OQ-010 대기)** — 도달률 실험 결과가 제공자를 가르고, 수신자 이메일은 개인정보이므로 국외 이전 금지(NFR-015)가 유지되면 국내에서 처리하는 제공자만 후보가 된다
- **되돌리기 비용**: 낮음. 인터페이스 뒤 구현체 교체. 다만 발신 도메인 인증 설정을 다시 하게 되어 OQ-011의 실험도 다시 돌려야 한다
- **검증 방법**: 메일을 가로채는 로컬 환경에서 비밀번호 재설정을 요청하면 재설정 링크가 담긴 메일 1건이 잡힌다(FR-002). 발송 실패를 강제하면 화면에 사유가 표시되고 인보이스 상태가 그대로다(FR-017)

## 6. 인증·권한

#### TD-010. 서버 세션 + HttpOnly 쿠키, 비밀번호 Argon2id, 역할은 '소유자' 단일
- **영역**: 인증·권한
- **근거 요구사항**: FR-001(이메일 가입·로그인, 비로그인 시 로그인 화면으로 이동), FR-002(재설정 링크 24시간 만료, 재설정 후 기존 비밀번호 무효), NFR-006(비밀번호 평문 저장·전송 금지), NFR-004(타인 데이터 접근 불가), PRD 비목표(팀 협업·권한 분리 없음)
- **결정**: 로그인 상태는 서버가 관리하는 세션으로 유지하고, 식별자는 HttpOnly·Secure·SameSite 속성을 건 쿠키로 전달한다. 비밀번호는 Argon2id로 해시해 저장한다. 역할 모델을 만들지 않는다 — 계정은 자기 데이터의 소유자이고 그것이 유일한 권한이다. 세션 수명, 쿠키 속성, 재설정 토큰 수명(FR-002의 24시간), 재설정 완료 시 기존 세션 무효화는 이 결정에 흡수된 잔가지다
- **검토한 대안**: ①JWT 무상태 토큰 — FR-002가 "재설정을 완료하면 기존 비밀번호로는 로그인되지 않는다"를 요구하고 링크 폐기(TD-011)도 즉시 반영되어야 하는데, 무상태 토큰은 즉시 무효화를 위해 결국 서버 상태를 다시 들여온다. ②외부 인증 서비스 위탁 — 계정 정보가 국외로 나갈 여지가 생겨 NFR-015와 충돌하고, 무료 베타에서 비용 항목이 하나 늘어난다. ③소셜 로그인 — PRD에 요구가 없다
- **확정도**: 확정
- **되돌리기 비용**: **높음.** 인증 경로 전면 재작성 + 기존 계정의 비밀번호 재설정 강제. 계정 모델 자체가 바뀌면(PRD OQ-003이 '스튜디오'로 뒤집히는 경우) FR-001·FR-003·NFR-004가 함께 재작성된다
- **검증 방법**: 가입 후 DB의 비밀번호 컬럼에서 입력한 문자열이 검색되지 않는다(NFR-006). 로그인하지 않고 대시보드 주소를 열면 로그인 화면으로 이동한다(FR-001). 비밀번호 재설정 후 이전 비밀번호로 로그인하면 실패한다. 재설정 링크를 25시간 뒤 열면 만료 안내가 표시된다(FR-002)

#### TD-011. 비인증 경로는 공유 토큰 하나뿐 — 128비트 CSPRNG, 해시 저장, 즉시 폐기
- **영역**: 인증·권한
- **근거 요구사항**: NFR-005(128비트 이상 난수, 순차·예측 불가, 폐기 즉시 접근 불가), NFR-012(로그인·가입·설치 없이 열람), FR-009·FR-016(공유 링크 발급·폐기, 존재 여부 비노출), FR-023(삭제된 문서의 링크 접근 불가)
- **결정**: 로그인 없이 접근할 수 있는 경로는 공유 링크 열람과 그 PDF 내려받기뿐이며, 그 외의 비인증 경로를 만들지 않는다. 토큰은 암호학적 난수 생성기로 128비트 이상을 만들어 URL 안전 문자열로 인코딩한다. DB에는 토큰 자체가 아니라 해시를 저장한다(DB 유출 시 링크가 그대로 열리지 않게). 폐기는 상태로 표현하고 조회 시점에 확인하므로 즉시 반영된다. 공유 화면은 소유자의 다른 문서·클라이언트를 조회할 수 있는 어떤 경로도 갖지 않는다. 존재하지 않는 토큰과 폐기된 토큰의 응답에서 문서 존재 여부를 알 수 있는 차이를 만들지 않는다
- **검토한 대안**: ①서명된 만료 토큰(URL 서명) — 폐기(FR-009)를 즉시 반영할 수 없어 서버 상태가 결국 필요하다. ②비밀번호를 건 공유 — NFR-012의 "아무 준비 없이 본다"와 충돌한다
- **확정도**: 확정
- **되돌리기 비용**: 중간. 토큰 발급·검증 경로 재작성과 이미 배포된 링크의 무효화(사용자가 클라이언트에게 다시 보내야 한다)
- **검증 방법**: 발급된 토큰 1,000개에서 순차적 규칙이 발견되지 않고 길이가 128비트 이상이다(NFR-005). 링크를 폐기한 직후 같은 주소를 열면 무효 안내가 표시된다. 로그인하지 않은 브라우저에서 공유 링크를 열면 문서와 고지가 표시되고, 그 화면에서 소유자의 다른 프로젝트로 이동할 수 있는 링크가 없다

## 7. 보안

#### TD-012. 모든 데이터 접근에 소유자 조건을 강제하고 위반은 404로 응답
- **영역**: 보안
- **근거 요구사항**: NFR-004(다른 계정의 클라이언트·프로젝트·계약서·인보이스 상세 및 PDF 생성 주소 접근 시 404, 본문·파일 미생성), FR-003·FR-008·FR-015(각각의 404 수용 기준), FR-022(검색 결과에 타 계정 문서 미포함)
- **결정**: 로그인 사용자가 접근하는 모든 조회·수정·삭제는 현재 세션의 계정 조건을 반드시 포함한다. 조건 없이 기본키만으로 조회하는 경로를 만들지 않는다. 권한 없음과 존재하지 않음을 구분하지 않고 둘 다 404로 응답한다 — 403을 주면 그 자원이 존재한다는 사실이 새기 때문이다. PDF 생성 경로도 예외가 아니며 권한 검사가 통과한 뒤에만 생성을 시작한다. 이 조건이 어느 계층에서 강제되는지(미들웨어·접근 계층·DB 정책 중 어디인지)는 Layer 2 아키텍처가 정한다
- **검토한 대안**: 화면 계층에서만 필터링 — 주소를 직접 치는 경로(NFR-004가 명시적으로 요구하는 상황)를 막지 못한다
- **되돌리기 비용**: 되돌리는 것이 아니라 **빠뜨리는 것이 문제인 결정**이다. 한 경로라도 빠지면 NFR-004 위반이 그 경로에서만 조용히 발생하고, 발견 시점에는 이미 배포되어 있다. 그래서 8.1의 필수 커버 영역에 넣는다
- **확정도**: 확정
- **검증 방법**: 계정 A와 B를 만들고, B의 클라이언트·프로젝트·계약서·인보이스 상세 주소와 PDF 생성 주소 전부에 A 세션으로 접근하면 모두 404가 반환되고 PDF 파일이 생성되지 않는다. A의 검색 결과에 B의 문서가 나오지 않는다

#### TD-013. 입력 검증은 서버 경계에서 스키마로 단일 수행, 비밀값은 환경으로만 주입
- **영역**: 보안
- **근거 요구사항**: FR-003(사업자등록번호 10자리), FR-004(대금 조건 합계·날짜 순서·음수 금지), FR-014(수량·단가 음수 금지), FR-013(번호 중복 금지), NFR-006(비밀번호·전송 보호), NFR-008(금액 정수)
- **결정**: 모든 서버 진입점에서 요청 본문을 스키마로 검증하고, 통과한 값만 도메인 로직에 들어간다. 화면 쪽 검증은 사용자 편의용이며 서버 검증을 대체하지 않는다(TD-001이 언어를 하나로 정했으므로 같은 스키마 정의를 공유한다). DB가 지킬 수 있는 무결성(인보이스 번호 유일성 등)은 DB 제약으로 이중으로 건다. 비밀값(DB 접속 정보, 메일 서비스 키, 세션 서명 키)은 환경변수와 호스팅 시크릿 저장소로만 주입하고 저장소에 커밋하지 않는다. 전송 구간은 전부 TLS이며 평문 HTTP 접근은 리다이렉트한다(NFR-006). 감사 로그는 TD-007이 담당한다
- **검토한 대안**: 화면에서만 검증 — API를 직접 호출하면 음수 금액·잘못된 사업자번호가 그대로 저장된다. FR-004·FR-014의 수용 기준이 "저장되지 않는다"이므로 저장 직전에 막아야 한다
- **확정도**: 확정
- **되돌리기 비용**: 낮음. 검증 라이브러리 교체는 진입점 단위 수정
- **검증 방법**: 화면을 거치지 않고 서버에 음수 단가를 보내면 저장되지 않고 검증 오류가 반환된다(FR-014). 대금 조건 비율 합이 90%인 요청이 거부된다(FR-004). 저장소 전체 검색에서 비밀값 문자열이 발견되지 않는다. HTTP로 접근하면 HTTPS로 이동한다

## 8. 테스트

#### TD-014. 단위·통합 테스트 도구: Vitest
- **영역**: 테스트
- **근거 요구사항**: NFR-008(금액 오차 없음), NFR-004(타인 데이터 접근 불가), FR-013(번호 유일성), FR-014(세액 계산), FR-018(상태 전이), FR-019(연체 판정)
- **결정**: 단위·통합 테스트는 Vitest로 작성한다. TD-001이 TypeScript로 정해졌으므로 별도 변환 설정 없이 같은 타입 정의를 그대로 쓴다. 서버 로직 통합 테스트는 실제 PostgreSQL(9.3절의 로컬 컨테이너)에 붙여 돌린다 — 인보이스 번호 유일성(FR-013)과 소유자 조건(NFR-004)은 DB 제약과 질의가 함께 걸린 상태여야 의미 있게 검증된다
- **검토한 대안**: ①다른 JS 테스트 러너 — 동작하지만 TypeScript·번들 설정을 따로 맞춰야 해서 1인 일정에서 손해다. ②DB를 흉내 낸 가짜 저장소로만 테스트 — 유일 제약과 소유자 조건이 검증되지 않아, 정작 틀리면 안 되는 것이 안 덮인다
- **확정도**: 확정
- **되돌리기 비용**: 낮음. 러너 교체는 테스트 파일 문법 수정 수준
- **검증 방법**: 명령 한 줄로 전체 스위트가 실행되고 종료 코드로 성패를 알 수 있다. 8.1의 각 영역에 실제로 실행되는 테스트가 최소 1건씩 존재한다

#### TD-015. 브라우저 자동화 도구: Playwright
- **영역**: 테스트
- **근거 요구사항**: NFR-010(Chromium 계열 2종·WebKit 계열 1종 최신 2개 버전에서 전 기능 동작), NFR-011(폭 375px에서 가로 스크롤 없이 동작), NFR-012(로그인 없이 공유 링크 열람), FR-005(뷰포트 높이 900px에서 스크롤 없이 표시)
- **결정**: 브라우저 자동화는 Playwright로 한다. 선택을 실제로 가른 조건은 하나다 — NFR-010이 WebKit 계열을 요구하므로, 한 도구로 Chromium과 WebKit을 모두 실행할 수 있어야 한다. 뷰포트 크기를 지정한 검증(375px 폭, 900px 높이)과 로그인 상태를 비운 세션 검증도 같은 도구로 한다. TD-017의 PDF 생성이 같은 계열 엔진을 쓰므로 로컬·CI에 설치할 브라우저 런타임이 하나로 줄어든다
- **검토한 대안**: Chromium 전용 자동화 도구 — NFR-010의 WebKit 계열 1종을 검증할 수 없다. 지원 브라우저를 줄이려면 PRD의 NFR-010을 바꿔야 하고, 그건 사용자의 결정이다
- **확정도**: 확정
- **되돌리기 비용**: 중간. 브라우저 테스트 전량 재작성. NFR-010을 유지하는 한 대체 후보가 사실상 없다
- **검증 방법**: 같은 테스트 스위트가 Chromium 2종과 WebKit 1종에서 실행되어 결과가 나온다. 뷰포트 375px로 대시보드를 열었을 때 문서 폭이 뷰포트 폭을 넘지 않는다(NFR-011)

## 9. 배포·운영

### 9.1 실행 환경과 환경 구분

#### TD-016. 국내 리전 관리형 호스팅에 컨테이너 단일 인스턴스 + 관리형 PostgreSQL
- **영역**: 배포·운영
- **근거 요구사항**: NFR-015(개인정보 국외 이전 금지 — 잠정), NFR-013(월 99% 가동률, 계획 점검 1회 30분 이내), NFR-006(전 구간 TLS), NFR-001(성능 목표), 여건(운영 인력 없음, 월 예산 5만 원)
- **결정**: 애플리케이션은 컨테이너 이미지 1개로 만들어 **국내 리전을 제공하는 관리형 컨테이너 호스팅**에 인스턴스 1개로 배포한다. DB는 같은 리전의 관리형 PostgreSQL을 쓰고 자동 백업을 켠다. OS 패치·백업 스크립트·모니터링 에이전트를 사람이 돌보는 형태의 인프라를 고르지 않는다 — 운영 인력이 없다. 환경은 로컬 / 스테이징 / 운영 셋으로 나누고 DB를 각각 따로 둔다. TLS는 호스팅이 제공하는 인증서를 쓴다. TD-005의 정기 파기와 FR-019의 연체 판정 갱신은 이 환경의 스케줄 실행 기능으로 하루 1회 돌린다. 구조화 JSON 로그를 표준 출력으로 내보내 호스팅의 로그 수집에 맡기는 것도 이 결정에 흡수된다.
  **구체 제공자는 이 문서에서 확정하지 않는다(OQ-013).** 확정 조건은 셋이다 — ①국내 리전 제공 ②TD-017의 헤드리스 브라우저가 도는 컨테이너 실행 ③월 5만 원 이내
- **검토한 대안**: ①국외 리전의 일반적인 PaaS — 운영 편의와 비용이 가장 좋지만 NFR-015가 잠정 제약으로 금지하고 있다. PRD OQ-010이 "국내 저장이 강제가 아니다"로 풀리면 이 대안이 1순위가 된다. ②직접 관리하는 가상 서버 — 비용은 가장 싸지만 백업·패치·TLS 갱신·모니터링을 1인이 떠안고, NFR-013의 가동률을 지킬 사람이 없다. ③서버리스 함수 — PDF 생성(TD-017)이 헤드리스 브라우저를 띄우므로 실행 시간·이미지 크기 제약과 정면으로 부딪힌다
- **확정도**: **잠정 (PRD OQ-010 대기)** — 개인정보 국내 저장이 법적으로 강제되는지에 따라 후보 집합이 달라진다. 강제가 아니면 선택지가 넓어지고 비용이 내려간다
- **되돌리기 비용**: **높음.** 호스팅 이전은 배포 파이프라인 재구성 + DB 데이터 이전 + 도메인·TLS 재설정. 운영 중이면 점검 시간이 NFR-013의 월 예산(7.2시간)을 쓴다. 리전이 바뀌면 개인정보 처리방침(FR-024)의 문구도 함께 고쳐야 한다
- **검증 방법**: 배포된 서비스와 DB의 리전이 국내로 표시된다. 배포 1회에서 요청이 실패하는 구간이 NFR-013의 월 예산 안에 든다. HTTP로 접근하면 HTTPS로 이동한다. 정기 작업이 하루 1회 실행된 기록이 로그에 남는다. 월 청구액이 5만 원 이내다

#### TD-017. PDF는 서버의 헤드리스 Chromium이 HTML을 렌더해 생성한다
- **영역**: 배포·운영
- **근거 요구사항**: FR-008(계약서 PDF, 페이지 나눔, "n / m" 쪽 번호), FR-015(인보이스 PDF, 항목 20개 초과 시 페이지 나눔, 합계는 마지막 페이지), NFR-002(조항 30개·항목 20개 기준 10초 이내, 3초 초과 시 진행 표시), NFR-014(모든 페이지에 고지), NFR-016(한국어)
- **결정**: PDF는 화면과 같은 HTML/CSS 템플릿을 서버의 헤드리스 Chromium이 렌더해 만든다. 쪽 번호·페이지 나눔·반복되는 머리말과 꼬리말(고지 문구)은 인쇄 CSS로 처리한다. 한글 폰트는 컨테이너 이미지에 함께 넣어 실행 환경의 폰트 유무에 의존하지 않게 한다. 3초를 넘는 경우를 대비해 요청은 진행 표시가 가능한 형태로 처리한다
- **검토한 대안**: ①PDF 작성 라이브러리로 좌표를 직접 그리기 — 조항 길이에 따라 달라지는 페이지 나눔(FR-008)과 20개 초과 항목 분할(FR-015)을 직접 구현해야 하고 한글 줄바꿈까지 떠안는다. 생성은 빠르지만 "PDF에 화면과 동일하게 포함된다"(FR-008·FR-015 수용 기준)를 두 벌의 코드로 유지하게 된다. ②외부 PDF 변환 서비스 — 계약서 본문과 클라이언트 개인정보가 외부로 나가 NFR-015와 충돌한다
- **확정도**: **스파이크 필요 (OQ-014)** — NFR-002의 10초 안에 드는지, 그리고 TD-016의 호스팅 컨테이너에서 헤드리스 브라우저가 실행되는지를 실제로 재기 전에는 확정할 수 없다
- **되돌리기 비용**: 중간~높음. 대안 ①로 가면 두 문서의 PDF 레이아웃을 처음부터 다시 만들고 화면–PDF 일치 검증도 새로 짠다. 실행 환경 제약 때문에 바꾸는 경우 TD-016도 함께 흔들린다
- **검증 방법**: 조항 30개 계약서와 항목 20개 인보이스의 PDF 생성 시간을 각 5회 측정해 중앙값이 10초 이내다(NFR-002). 생성된 PDF의 모든 페이지에 고지 문구와 "n / m" 쪽 번호가 있다(FR-008, NFR-014). PDF의 조항 본문·금액·기간이 화면 표시와 문자열 단위로 일치한다

### 9.2 배포 방식

기본 브랜치에 병합되면 컨테이너 이미지를 만들어 스테이징에 자동 배포하고, 운영 배포는 수동 승인으로 **같은 이미지**를 올린다(같은 이미지를 쓰므로 "스테이징에서는 됐는데 운영에서 안 되는" 차이가 줄어든다). DB 마이그레이션은 배포 전에 적용하며, **되돌릴 수 있는 마이그레이션만 운영에 올린다.** 롤백은 직전 이미지로 되돌리는 것이므로, 되돌릴 수 없는 마이그레이션이 하나라도 올라가면 롤백이 불가능해진다 — 이 규칙이 NFR-013의 가동률을 지키는 실질적 수단이다.

### 9.3 로컬 개발 환경

#### TD-018. 로컬 개발 환경: 컨테이너로 뜨는 의존 서비스 + 호스트에서 실행하는 앱
- **영역**: 배포·운영
- **근거 요구사항**: 여건(개발자 OS 미확인 — 가정), FR-002·FR-017(메일 발송을 실제 발송 없이 확인해야 한다), TD-014(통합 테스트가 실제 PostgreSQL에 붙는다), NFR-001(성능 검증에 대량 시드가 필요하다)
- **결정**: 명령 하나(`local-dev`)로 DB와 메일 캡처를 컨테이너로 띄우고, 마이그레이션과 시드를 적용한 뒤, 앱 개발 서버는 호스트에서 실행한다. 앱을 컨테이너에 넣지 않는 이유는 개발자 OS가 미확인(가정)이라 파일 감시·핫 리로드가 OS별로 가장 자주 깨지는 지점이기 때문이다. 구성 요소는 아래 표와 같다
- **검토한 대안**: ①앱까지 전부 컨테이너로 — 환경 재현성은 가장 좋지만 파일 감시와 핫 리로드가 OS·볼륨 방식에 따라 느려지거나 깨져서, 확인되지 않은 OS에서 첫날부터 막힐 위험이 있다. ②전부 호스트에 직접 설치 — 운영과 같은 종류의 DB 버전을 맞추기 어렵고, 마이그레이션·유일 제약 검증(TD-014)의 신뢰도가 떨어진다
- **확정도**: 확정 — OQ-017(개발자 OS)의 답에 따라 컨테이너 실행 방식만 조정한다
- **되돌리기 비용**: 낮음. local-dev 스크립트 수정으로 끝난다. 운영 코드에 영향이 없다
- **검증 방법**: 새 컴퓨터에서 저장소를 받아 명령 한 줄을 실행하면 로그인 가능한 계정과 예시 프로젝트가 있는 상태로 앱이 뜬다. 그 상태에서 비밀번호 재설정을 요청하면 메일 캡처 화면에서 재설정 메일을 볼 수 있다. 시드 옵션으로 프로젝트 200건·인보이스 1,000건을 만들 수 있다

Layer 4는 아래 목록을 그대로 구현한다.

| 구성 요소 | 형태 | 왜 필요한가 |
|---|---|---|
| PostgreSQL | 컨테이너 | TD-003. 운영과 같은 종류의 DB에서 마이그레이션과 유일 제약을 검증하기 위해 |
| 스키마 마이그레이션 적용 + 시드 데이터 | 스크립트 | 빈 DB에서 시작해도 로그인 가능한 계정과 예시 프로젝트가 있어야 화면 개발이 된다 |
| 애플리케이션 개발 서버 | 호스트에서 실행 (핫 리로드) | TD-002. 개발자 OS가 미확인(가정)이므로 앱 자체는 호스트에서 돌려 OS 차이를 줄인다 |
| 메일 수신함 캡처 | 컨테이너 | TD-009. FR-002·FR-017을 실제 메일 발송 없이 확인하기 위해. 브라우저에서 받은 메일을 본다 |
| 헤드리스 브라우저 런타임 | 로컬 설치 | TD-015(테스트)와 TD-017(PDF)이 같은 런타임을 공유한다 |
| 예시 환경변수 파일 | 파일 | TD-013. 필요한 비밀값 목록이 파일 하나로 보여야 한다 |

성능 검증(NFR-001, OQ-015)을 위해 프로젝트 200건·인보이스 1,000건을 만드는 시드 옵션을 함께 둔다.

### 9.4 로그·모니터링

구조화된 JSON 로그를 표준 출력으로 내보내고 호스팅의 로그 수집에 맡긴다(TD-016에 흡수). 로그에는 요청 식별자·계정 식별자·소요 시간을 남기고 **비밀번호·토큰 원문·클라이언트 개인정보는 남기지 않는다**(NFR-006, NFR-015). 감사 이력은 로그가 아니라 DB에 있다(TD-007). 외부 가동 확인 서비스로 1분 간격 상태 확인을 두어 NFR-013의 가동률을 실제로 측정한다 — 측정하지 않는 가동률 목표는 지켜졌는지 알 수 없다.
