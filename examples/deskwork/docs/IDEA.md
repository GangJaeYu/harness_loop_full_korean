# 아이디어 정의서: (가칭) Deskwork — 프리랜서 디자이너용 계약·인보이스 통합 관리

> 이 문서는 사용자와의 문답 없이, 초기 한 문장("프리랜서 디자이너용으로 계약서랑 인보이스를 한 곳에서 관리하는 웹서비스 / 1인 개발 / 3개월")에서
> 출발해 합리적 가정을 채워 작성했습니다. **`(가정)` 표시가 붙은 문장은 사용자가 직접 말한 것이 아닙니다.**
> 실제로 물었어야 할 질문은 `questions.md`에 있고, 답에 따라 이 문서는 바뀝니다. 특히 '미결 사항' 1번은 문서 전체의 결론을 바꿉니다.

## 한 줄 정의

국내에서 혼자 일하는 프리랜서 디자이너가, 한 클라이언트와의 계약서와 그 일에서 나온 인보이스를
**프로젝트 하나 아래 묶어서** 작성·발송·입금 확인까지 추적할 수 있게 하는 웹서비스.

## 문제

- **현재 상황:** 프리랜서 디자이너 한 명이 동시에 3~6개 프로젝트를 진행하고, 클라이언트마다 계약서(한글/워드 파일)와
  인보이스(엑셀 또는 손으로 만든 PDF)가 따로 존재한다. 둘 사이에 연결이 없다. (가정)
- **불편의 구체적인 장면:** 두 달 전 끝난 프로젝트의 잔금이 안 들어왔다. 계약서에 잔금 조건을 뭐라고 썼는지 확인하려고
  메일함과 카톡과 바탕화면 폴더를 뒤진다. 인보이스는 몇 번 보냈는지, 언제 보냈는지 기억나지 않는다.
  독촉 메일을 쓰려면 계약 조항과 인보이스 번호를 둘 다 찾아야 하는데, 그 둘은 서로 다른 곳에 있다. (가정)
- **지금의 대안과 그 한계:**
  - 한글/워드 템플릿 + 엑셀 + 메일/카톡 (가정, 가장 유력한 현재 대안)
    → 무료이고 익숙하지만, 계약↔인보이스↔입금 상태가 사람 머릿속에만 있다. 미수금을 놓친다.
  - 전자계약 서비스(모두싸인 등) → 서명은 잘 되지만 돈 흐름을 모른다. 1인에게는 비싸다.
  - 세무/정산 서비스(삼쩜삼 등) → 세금은 처리하지만 계약 문서를 다루지 않는다.
  - **빈틈:** "이 계약에서 나온 이 청구서가 아직 안 들어왔다"를 한 화면에서 보여주는 것이 없다.

## 타깃 사용자

- **1순위 사용자:** 국내에서 개인 자격 또는 개인사업자로 일하는 프리랜서 디자이너. 경력 2~7년.
  동시 진행 프로젝트 3~6개, 클라이언트는 대부분 국내 중소기업/에이전시.
  연 매출 3~8천만 원 규모로 세무사를 쓰지 않고 스스로 정산한다. (가정)
- **2순위 사용자:** 같은 방식으로 일하는 다른 1인 프리랜서 — 개발자, 영상 편집자, 마케터.
  디자이너로 검증되면 계약서 템플릿 문구만 바꿔서 확장 가능. (가정)
- **쓰지 않을 사람 / 노리지 않는 시장:**
  - 5인 이상 스튜디오/에이전시 (멤버 권한, 승인 흐름이 필요 — MVP 범위 밖)
  - 해외 클라이언트 중심 디자이너 (다국어·환율·해외 송금 — 범위 밖) (가정)
  - 클라이언트(발주사) 쪽. 발주사는 계정 없이 링크로만 문서를 본다.

## 핵심 가치 제안

1. **계약과 청구가 같은 프로젝트에 묶여 있다.** 잔금 조건을 확인하려고 폴더를 뒤지지 않는다. 이것이 이 제품의 유일한 진짜 차별점이다.
2. **미수금이 저절로 보인다.** 발송했는데 입금 안 된 인보이스가 대시보드 첫 화면에 뜬다. 프리랜서가 실제로 잃고 있는 돈이 여기 있다.
3. **디자이너용 계약서 기본형이 이미 들어 있다.** 수정 횟수, 저작권 귀속, 시안 반려, 추가 요청 비용 — 백지에서 쓰지 않는다. (가정)

## 핵심 사용자 흐름

1. 가입 후 **클라이언트를 하나 만들고, 그 아래 프로젝트를 하나 만든다.** (금액, 기간, 대금 조건)
2. 프로젝트에서 **계약서를 만든다.** 디자이너용 템플릿을 고르고 프로젝트 정보가 자동으로 채워진 것을 확인, 조항 몇 개를 수정.
3. 계약서를 **PDF로 만들어 클라이언트에게 공유 링크로 보낸다.** 열람 여부가 기록된다.
4. 착수금 시점이 되면 **같은 프로젝트에서 인보이스를 만든다.** 계약의 금액·대금 조건이 그대로 넘어온다. 번호는 자동 채번.
5. 인보이스를 보내고, 입금되면 **'입금 완료'로 표시한다.**
6. 대시보드에서 **아직 안 들어온 돈과 그 계약서를 한 화면에서 본다.**

이 흐름을 처음부터 끝까지 도는 데 첫 사용 기준 10분 이내여야 한다. (가정)

## MVP 범위

### 포함
- 이메일 기반 회원가입/로그인 (1인 계정, 팀 없음)
- 클라이언트 관리 (상호, 담당자, 연락처, 사업자번호)
- **프로젝트** — 모든 것이 매달리는 중심 개체. 금액, 기간, 대금 조건(착수금/중도금/잔금), 상태
- 계약서: 디자이너용 기본 템플릿 1~2종, 변수 자동 채움, 조항 편집, PDF 생성
- 계약서 공유 링크 (수신자 로그인 불필요) + 열람 시각 기록
- 인보이스: 프로젝트에서 생성, 자동 채번, 항목·부가세·원천징수 3.3% 계산, PDF 생성
- 인보이스 상태: 초안 → 발송 → 입금완료 / 연체
- 대시보드: 미수금 합계, 연체 인보이스 목록, 진행 중 프로젝트
- 문서 검색 (클라이언트명, 프로젝트명 기준)

### 제외 (다음 버전 이후)
- **법적 효력을 주장하는 전자서명** — MVP에서는 서명하지 않는다. PDF를 만들고 보내는 데까지만. (가정 — 3개월 제약상 가장 먼저 잘라낸 것)
- 팀/멤버 초대, 권한 분리
- 결제 연동, 유료 구독 (무료 베타로 시작) (가정)
- 세금계산서 국세청 연동, 회계 프로그램 연동
- 은행 계좌 연동을 통한 입금 자동 확인 (수동 체크로 시작)
- 자동 독촉 메일 발송 (알림은 앱 내 표시까지만)
- 해외 클라이언트: 다국어, 다통화, 환율
- 모바일 앱 (반응형 웹으로 대응)
- 견적서, 작업지시서, 타임트래킹, 경비 관리

**범위 판단 기준 한 줄:** "이 기능이 없으면 계약→청구→입금 확인 한 바퀴를 못 도는가?" 아니면 제외.

## 제약 조건

- **기간:** 3개월 (사용자 명시)
- **인원:** 1명, 개발자 본인 (사용자 명시). 디자이너·기획자 없음 → UI는 기성 컴포넌트 조합으로 간다.
- **실질 가용 시간:** 3개월 전체를 개발에만 쓸 수 없다. 배포·버그·사용자 피드백 대응을 빼면 순수 기능 개발은 8~9주 수준. (가정)
- **기술적 제약 / 선호:** 미확인. 스택은 이 문서에서 정하지 않는다 — TRD(Layer 1)에서 결정.
  다만 **PDF 생성**과 **메일 발송**이 필수 기술 요소라는 점은 기록해 둔다.
- **예산·운영:** 미확인. 1인 개발이므로 초기 인프라 비용은 월 5만 원 이내를 전제. (가정)
- **법·규정:** 계약서와 인보이스는 개인정보(성명, 연락처, 사업자번호)와 금액 정보를 담는다.
  개인정보 처리방침이 필요하고, 문서 보관 기간 정책을 정해야 한다.

## 성공 기준

- **정량 (3개월 시점):** (전부 가정 — 사용자 확인 필요)
  - 본인 외 실사용자 10명이 가입
  - 그중 5명이 **인보이스를 실제 클라이언트에게 1건 이상 발송**
  - 그중 3명이 **2주 뒤에도 재방문**
  - 계약서 1건 + 인보이스 1건을 만드는 데 걸리는 시간 15분 이내
- **정성:**
  - 사용자가 "이제 계약서 찾으러 폴더 안 뒤진다"고 말한다
  - 사용자가 요청하지 않았는데 두 번째 프로젝트를 스스로 등록한다
  - 최소 1명이 "이거 얼마면 쓰겠다"고 먼저 묻는다

## 검토된 대안 방향

세 방향을 놓고 비교했고, **C안을 채택**했습니다. (사용자 선택이 아니라 이 문서의 제안입니다 — questions.md Q4로 확인 필요)

### A안. 인보이스 우선 — "돈 받는 것"부터
- 형태: 웹앱 / 첫 사용자: 미수금을 자주 놓치는 프리랜서 / 핵심 기능: 인보이스 발행·발송·입금 체크·미수금 대시보드. 계약서는 파일 업로드 보관만
- 강점: 4~5주면 나온다. 통증이 가장 직접적(돈). 3개월 중 절반을 사용자 피드백에 쓸 수 있다
- 약점: 인보이스 생성기는 이미 많다. "한 곳에서"라는 원래 차별점을 검증하지 못한다
- 규모: 4~5주, 화면 5개

### B안. 계약서 우선 — "일 시작"부터
- 형태: 웹앱 / 첫 사용자: 계약서를 매번 백지에서 쓰는 디자이너 / 핵심 기능: 템플릿 계약서 작성·PDF·공유 링크·보관
- 강점: 디자이너용 계약 문구라는 콘텐츠 자산이 남는다. 진입 시점이 프로젝트 시작이라 자연스럽다
- 약점: 서명이 없으면 반쪽. 계약서는 프로젝트당 1회라 재방문 빈도가 낮다. **돈이 안 걸려 있어 아쉬움이 약하다**
- 규모: 5~6주, 화면 6개

### C안 (채택). 프로젝트 축으로 둘 다 얇게
- 형태: 웹앱 / 첫 사용자: 프로젝트 3~6개를 동시에 굴리는 국내 프리랜서 디자이너
- 핵심 기능: ①클라이언트·프로젝트 관리 ②템플릿 계약서 → PDF·공유 ③프로젝트에서 인보이스 생성 → 발송·입금 체크
- 강점: **이 제품이 존재하는 유일한 이유(연결)를 처음부터 검증한다.** 계약(1회)의 진입성과 인보이스(반복)의 재방문성을 둘 다 얻는다
- 약점/리스크: 8~10주로 3개월을 거의 다 쓴다. 각 기능이 A안·B안보다 얇아서 단독 비교에서는 열세
- 규모: 8~10주, 화면 8~10개

**채택 이유:** A와 B는 각각 이미 있는 제품의 열화판이 되기 쉽다. 이 아이디어의 유일한 방어선은 '연결'이고,
그것을 3개월 뒤에 검증한다면 3개월을 버리는 셈이다. 다만 4주차에 '프로젝트+인보이스'가 도는지 점검하고,
안 되면 그 시점에 A안으로 축소한다.
