# 게이트 4 — task_validation

## 무엇을 판정하는가

그 태스크의 수용 기준이 **실행 중인 애플리케이션에서 실제로 관찰되는가.**
앞의 세 게이트는 도구가 판정하지만 이것은 **에이전트가** 판정한다.

## 분리 원칙

이 검증은 **그 태스크를 구현한 세션이 아닌 세션**에서 돈다.

구현한 세션은 자기가 무엇을 **의도했는지** 알고 있다. 그래서 화면이 실제로 그렇게 동작하지 않아도
그렇게 보이고, 수용 기준의 애매한 문장을 자기 구현에 맞는 쪽으로 읽는다.
나쁜 의도가 아니라 **정보의 문제**다 — 구현 중에 형성된 판단이 관찰을 덮어쓴다.

검증자에게는 **태스크 문서에 적힌 문장이 정보의 전부**이고, 그건 사용자가 나중에 그 기능을
처음 써 볼 때와 같은 조건이다.

### 이 환경(Claude Code)에서의 분리 수단

**서브에이전트로 돌린다.** 서브에이전트는 새 컨텍스트로 시작하므로 구현 세션이 무엇을 했는지 모른다.

**한 세션 안에서 구현하고 같은 세션이 판정하는 것은 이 게이트를 돌린 것이 아니다.**
그렇게 돌 수밖에 없는 상황이면 **통과로 기록하지 말고 사용자에게 알린다.**
분리된 척하는 검증은 안 하느니만 못하다 — 통과했다는 기록만 남고 실제로는 구현자가 자기 코드를 승인한 것이다.

### 검증자가 받는 것

1. 태스크 문서 경로 — `plan_setup/phase-NN/phase-NN-tasks/phase-NN-task-MM.md`
2. 실행 중인 애플리케이션 (`scripts/local-dev.ps1` 로 준비) 과 접속 주소
3. 이 문서 (`harness_setup/quality_gates/task_validation.md`)
4. (필요 시) 태스크의 `architecture` 가 가리키는 설계 절

### 검증자가 받지 않는 것

**이 목록이 이 게이트의 실질이다. 하나라도 새면 분리한 의미가 없어진다.**

- 구현 세션의 대화·요약·"무엇을 했는지" 설명
- 구현자가 쓴 통과 보고나 자체 점검 결과
- "이 부분은 이렇게 동작하도록 만들었다" 류의 안내
- 구현이 건드린 파일 목록·diff·커밋 메시지
- 앞 게이트(lint·unit·e2e)가 통과했다는 사실 이상의 실행 로그
- 원인 추정, 확인 요청, "여기를 특히 봐 달라"

> **"참고하라고 요약만 붙이는 것"이 가장 흔한 누수다.** 그 한 줄 요약이 바로 구현 중에 형성된 판단이다.

### 호출 형식 (매번 이대로 쓴다)

매번 다르게 쓰면 매번 다른 것이 새어 나간다. 서브에이전트 프롬프트에 넣는 것은 아래 네 가지뿐이다.

```
아래 태스크 문서의 수용 기준을 실행 중인 애플리케이션에서 직접 관찰해 판정한다.

1. 태스크 문서: plan_setup/phase-NN/phase-NN-tasks/phase-NN-task-MM.md
2. 판정 절차와 출력 형식: harness_setup/quality_gates/task_validation.md
3. 애플리케이션이 실행 중이다: http://localhost:<APP_PORT>
   (이상하면 `pwsh harness_setup/scripts/local-dev.ps1 -Status` 로 무엇이 안 떴는지 먼저 본다)
4. task_validation.md 의 '판정 형식' 블록을 그대로 출력한다.

이 태스크 문서와 실행 중인 앱 외의 정보를 찾지 마라.
구현 과정·대화 기록·커밋·diff 를 조회하지 마라. 코드를 고치지 마라.
```

## 절차

1. `pwsh harness_setup/scripts/local-dev.ps1` 로 환경을 준비한다 (앞 검증이 남긴 데이터가 결과를 바꿀 수 있으면 `-Reset`).
   뭔가 이상하면 `-Status` 로 무엇이 안 떴는지 **먼저** 본다 — **환경 문제를 구현 실패로 보고하지 않기 위해서다**
2. 태스크 문서의 `acceptance_criteria` 를 번호대로 읽는다
3. 기준마다 애플리케이션을 실제로 조작해 결과를 관찰한다
4. **수용 기준이 코드를 대상으로 할 때만** 코드를 검사한다
5. 아래 형식으로 판정을 출력한다

### 관찰이 기본이고 코드 검사는 예외인 이유

**코드가 그렇게 쓰여 있는 것과 그렇게 동작하는 것은 다르고**, 그 차이를 잡으라고 이 게이트가 있다.
코드를 근거로 PASS 를 주면 앞의 세 게이트가 이미 한 일을 반복하는 것에 불과하다.

이 프로젝트에서 **코드 검사가 정당한 기준**은 이런 모양이다 —
"`route` 파일에 SQL 문자열이 없다"(`phase-01-task-01`), "data 계층 함수 중 첫 인자가 `accountId` 가
아닌 것은 `findByShareToken*`·`sweep*` 뿐이다"(`phase-02-task-02`), "이력 UPDATE 구문이
정기 작업 한 곳 외에 없다"(`phase-04-task-03`). 이런 기준은 관찰로 판정되지 않으므로 검색이 수단이다.
**그 외에는 코드를 근거로 PASS 를 주지 않는다.**

## 판정 형식

```
TASK: phase-NN-task-MM
GATE: task_validation
RESULT: PASS | FAIL | 판정 불가
- [1] PASS — (무엇을 했고 무엇이 보였는가)
- [2] FAIL — (관찰한 것. 원인 추정 없이)
- [3] 판정 불가 — (기준의 어느 부분이 관찰 가능하게 쓰이지 않았는가)
```

- 기준 하나라도 FAIL 이면 `RESULT: FAIL`
- FAIL 이 없고 `판정 불가` 가 있으면 `RESULT: 판정 불가`
- 전부 PASS 여야 `RESULT: PASS`

## 판정 규칙

- **수용 기준 한 줄마다 PASS / FAIL 과 관찰한 증거를 적는다.** 무엇을 했고 무엇이 보였는지.
  **증거 없는 PASS 는 PASS 가 아니다** — 그건 구현 문서를 읽고 동의한 것에 불과하다
- **검증자는 고치지 않는다.** 고치는 순간 검증자가 구현자가 되고, 다음 기준부터는 자기 코드를 검증한다.
  실패는 실패로 돌려보내고 수정은 구현 쪽에서 한다
- **원인 분석이나 수정 제안을 하지 않는다.** 관찰한 것만 적는다. 원인 추정이 붙으면 구현 세션이
  그것을 따라가고, 틀린 추정이면 엉뚱한 곳을 고친 뒤 다시 실패한다
- **판정할 수 없으면 PASS 도 FAIL 도 아니다.** 기준이 관찰 가능하게 쓰이지 않았으면 `판정 불가` 로 돌려보낸다.
  그건 구현의 문제가 아니라 태스크 문서의 문제이고, Layer 3 으로 돌아갈 일이다
- **환경이 이상하면 판정하지 않는다.** `-Status` 에서 안 뜬 구성 요소가 있으면 그 사실을 출력하고
  판정을 멈춘다. 안 뜬 앱을 보고 "화면이 안 보인다 → FAIL" 로 적으면 멀쩡한 코드를 세 번 고치게 된다

### 증거의 모양

관찰은 **재현 가능한 문장**으로 쓴다.

- 나쁨: "정상 동작함", "요구대로 구현됨", "코드에 처리가 있음"
- 좋음: "계정 B 로 로그인한 상태에서 계정 A 의 인보이스 상세 URL `/invoices/<id>` 를 열었더니
  404 화면이 떴고, 존재하지 않는 id 로 연 화면과 본문이 같았다"
- 좋음: "항목을 0개로 두고 '발송' 버튼을 눌렀더니 상태가 '초안' 그대로였고
  '항목이 없어 발송할 수 없습니다' 가 입력란 아래에 표시됐다"

## 결과 기록

**새 상태 파일도 증거 디렉터리도 만들지 않는다.** 진행 상태는 `STATE.md`, 이력은 `LOG.md` 가 이미 갖고 있고,
세 번째 기록처가 생기면 셋이 서로 어긋난다. 증거는 텍스트로 `LOG.md` 에 남는다.

검증자는 판정 블록을 출력하고, 루프가 그것을 두 곳으로 옮긴다.

- `plan_setup/STATE.md` 의 `Last Verification` — **지금 상태 한 줄.** 태스크 / 결과 / 실패면 사유
- `plan_setup/LOG.md` — **관찰한 증거.** 통과는 한 줄이면 되지만 **실패는 관찰을 남긴다** —
  그게 없으면 다음 세션이 같은 것을 처음부터 다시 확인한다

## 대상이 아닌 것

`status: blocked` 인 태스크(현재 `phase-06-task-01` ~ `phase-06-task-12`, 12건)는 이 게이트의 대상이 아니다.
아직 정해지지 않은 것 위에 있어 수용 기준이 확정되지 않았다.

## 전제

- `scripts/local-dev.ps1` 로 앱과 의존 서비스가 떠 있어야 한다
- 검증 세션은 **구현 세션과 다른 세션**이어야 한다. 아니면 이 게이트는 돌지 않은 것이다
