# 게이트 3 — e2e

## 무엇을 판정하는가

사용자가 브라우저에서 실제로 하는 흐름이 **끝까지 동작하는가.**
단위 테스트가 전부 통과해도 화면과 서버를 이어 붙이면 안 되는 일이 흔하고, 그것만 잡는 게이트다.

도구는 TD-015 가 정한 **Playwright** 다. NFR-010 이 WebKit 계열을 요구하므로 한 도구로
Chromium 과 WebKit 을 모두 실행할 수 있어야 했고, 그 조건이 선택을 갈랐다. 하네스는 이 선택을 바꾸지 않는다.

## 명령

```
npm run gate:e2e
```

`package.json` 의 `scripts.gate:e2e` 는 아래와 정확히 같아야 한다.

```
playwright test --project=chromium --grep-invert @phase-complete
```

- 매 태스크마다 도는 **빠른 묶음**이다. `@phase-complete` 태그가 붙은 느린 측정은 제외한다
- 브라우저 1종(Chromium)만 돈다. 3종 실행은 아래 'phase 완료 묶음'에 있다
- `--update-snapshots` 를 붙이지 않는다 — 자동 수정이다

### phase 완료 묶음 (게이트 명령이 아니다)

phase 하나가 완료될 때 한 번 돈다. 태스크마다 돌리면 느려지고, **느려지면 사람이 게이트를 끄고,
꺼진 게이트는 없는 것과 같다.**

```
npm run gate:e2e:phase
```

= `playwright test`  (전 프로젝트: `chromium`, `chromium-edge`, `webkit` / 태그 제외 없음)

## 통과 조건

- 종료 코드 0
- 실패·시간초과 0건. **재시도(`retries`)로 살아난 통과는 통과가 아니라 흔들림이다** —
  Playwright 의 `flaky` 로 보고된 항목이 1건이라도 있으면 아래 '실패 분류'로 넘긴다
- 활성 흐름이 0개여서 "no tests found" 로 끝난 것은 **통과가 아니라 `미활성`** 이다

## 활성 시점

- **`phase-02-task-07`(로그인·가입 화면) 완료 시부터.** 그전에는 조작할 화면이 없다
- 그전 phase 에서도 이 게이트를 **빼지 않는다.** 그때는 `미활성` 로 기록되고, 조용한 통과가 되면 안 된다
- 흐름별 활성 phase 는 아래 표에 있다. 활성화된 흐름은 그 뒤 모든 태스크에서 **회귀로** 계속 돈다
- 설정 파일: 프로젝트 루트의 `playwright.config.ts` (프로젝트 3종·태그·`baseURL` 정의). 흐름 파일은 `tests/e2e/`

## 흔들림을 줄이는 규칙

같은 코드로 두 번 돌렸는데 한 번은 통과하고 한 번은 실패하면, 사람은 곧 **실패를 무시하기 시작한다.**
느려서 꺼지는 것과 결과가 같고, 오히려 나쁘다 — 꺼진 게이트는 꺼진 줄이라도 안다.

- **선택자는 역할과 이름으로 잡는다** — `getByRole('button', { name: '인보이스 만들기' })`, `getByLabel('상호')`.
  그것으로 안 되는 곳에만 최소한의 표식(`data-testid`)을 붙인다. 화면 구조를 따라가는 선택자
  (`div > div:nth-child(3)`)는 관계없는 수정에서 깨진다
- **실행마다 고유한 테스트 데이터를 만든다** — 이메일·인보이스 번호·상호에 실행 고유값을 붙인다.
  이 프로젝트는 계정 내 인보이스 번호 유일 제약(FR-013)과 이메일 유일 제약이 걸려 있어,
  고정값을 쓰면 두 번째 실행이 첫 번째가 남긴 것과 부딪힌다
- **인증 상태는 한 번 만들어 재사용한다** — Playwright 의 저장된 인증 상태(storage state)를 쓴다.
  **진짜로 로그인 화면을 거치는 흐름은 FLOW-01 하나뿐이다.** 흐름마다 로그인하면 그만큼 느려지고,
  로그인 화면이 바뀔 때 모든 흐름이 함께 깨진다. FLOW-05 는 계정 A·B 두 개의 상태를 준비해 쓴다
- **외부에서 와야 하는 값은 실제 경로에서 가져온다** — FLOW-08 의 재설정 링크는
  **로컬 메일 캡처의 API 에서 읽는다**(`scripts/local-dev.ps1` 이 띄운다). 링크를 하드코딩하거나
  DB 에서 토큰을 꺼내 조립하면 그 흐름은 "메일이 실제로 발송되어 링크가 들어 있다"를 검증하지 않는다
- **`page.waitForTimeout` 을 쓰지 않는다** — 기다림은 항상 관찰 가능한 조건(요소·응답·URL)에 건다
- **retries 는 0 이다** — 재시도로 가려진 흔들림은 아무도 고치지 않는다

## 단언 세 층

화면만 보면 **"성공 메시지는 떴는데 저장은 안 된"** 상태를 통과시킨다. 흐름마다 세 층을 확인한다.

1. **화면 상태** — 사용자가 보는 것 (메시지, 이동한 화면, 목록에 나타남)
2. **서버 상태** — 실제로 남았는가 (DB 행, 발급된 세션·토큰, `audit_events` 이력).
   예: FLOW-03 의 '입금 완료' 는 화면 배지만이 아니라 `invoices.paid_at` 과 상태 변경 이력 1건까지 본다(FR-018)
3. **사용자에게 보이는 결과** — 다시 조회했을 때·다른 계정에서 볼 때 기대대로인가.
   예: FLOW-03 의 입금 완료 뒤 대시보드 미수금 합계에서 그 금액이 빠져 있다(FR-018·FR-020).
   FLOW-05 는 이 층 자체가 흐름이다

## 실패 분류 (고치기 전에 정한다)

E2E 실패를 없애는 가장 빠른 길은 **단언을 느슨하게 만드는 것**이고, 그렇게 하면 게이트가 조용히 죽는다.
그래서 실패를 만나면 먼저 셋 중 무엇인지 정한다.

| 분류 | 어떻게 알아보는가 | 무엇을 고치는가 |
|---|---|---|
| **진짜 결함** | 수동으로 같은 순서를 밟아도 같은 결과 | 코드. 태스크 수정으로 돌아간다 |
| **낡은 스펙** | 화면이나 규약이 의도적으로 바뀌었고 흐름이 옛 모습을 기대한다 | 흐름 정의. `harness-update` 의 일이다 |
| **환경 문제** | `local-dev.ps1 -Status` 에서 DB·메일 캡처·앱 중 안 뜬 것이 있다. 남은 데이터가 있다 | `local-dev.ps1 -Reset` 으로 환경을 다시 준비한다. **코드도 스펙도 고치지 않는다** |

> **분류를 `plan_setup/LOG.md` 에 남긴다.** 루프는 실패를 3회까지만 재시도하는데,
> 세 번이 전부 환경 문제였다면 고칠 것은 코드가 아니라 하네스다. 그 구별이 기록에 없으면 아무도 하네스를 고치지 않는다.

## 전제

- `scripts/local-dev.ps1` 로 DB·메일 캡처·앱 개발 서버가 떠 있어야 한다
- Playwright 브라우저 런타임이 설치되어 있어야 한다 (`local-dev.ps1` 이 전제 확인 단계에서 검사한다)

## 하지 않는 것

- 자동 수정 — 스냅샷 갱신 포함
- 기능 전수 나열 — 기능 단위 검증은 unit 의 일이다
