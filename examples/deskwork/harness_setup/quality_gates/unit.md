# 게이트 2 — unit

## 무엇을 판정하는가

수정된 단위가 의도대로 동작하고, **이미 되던 것이 깨지지 않았는가.**
판정 대상은 그 태스크에 딸린 테스트가 아니라 **전체 스위트(회귀)** 다.
딸린 테스트만 돌려 통과시키면 다른 곳이 깨진 채로 태스크가 완료된다.

TD-014 에 따라 러너는 **Vitest** 이고, 서버 로직 통합 테스트는 **실제 PostgreSQL** 에 붙어 돈다.
인보이스 번호 유일성(FR-013)과 소유자 조건(NFR-004)은 DB 제약과 질의가 함께 걸린 상태여야 의미가 있다.

## 명령

```
npm run gate:unit
```

`package.json` 의 `scripts.gate:unit` 은 아래와 정확히 같아야 한다.

```
vitest run
```

- **전체 스위트**를 돈다. 경로·패턴으로 좁히지 않는다
- `--passWithNoTests` 를 **붙이지 않는다.** 테스트가 0건이면 Vitest 는 실패로 끝나야 하고,
  그 실패를 루프가 `미활성` 로 읽는다. 이 플래그를 붙이는 순간 0건 실행이 초록불이 된다
- `-u` / `--update` (스냅샷 갱신)를 붙이지 않는다 — 자동 수정이다

## 통과 조건

- 종료 코드 0
- 실패 테스트 0건, 건너뛴(skipped) 테스트가 있으면 그 목록이 출력에 남는다
- **커버리지 숫자는 통과 조건이 아니다.** 아래 '커버리지' 절을 보라

## 활성 시점

- **`phase-01-task-01` 완료 시부터.** 그전에는 `미활성`
  (`phase-01-task-01` 이 `tests/architecture/layering.test.ts` 로 첫 테스트를 만든다)
- **통합 테스트(실제 DB에 붙는 것)는 `phase-01-task-02` 완료 시부터.**
  마이그레이션 러너가 있어야 빈 DB에 스키마를 올릴 수 있다. 그전까지 통합 테스트는 존재하지 않는다
- 테스트 0건으로 명령이 실패하는 것은 `실패` 가 아니라 `미활성` 이다

## 두 묶음

| 묶음 | 무엇인가 | 게이트 판정 대상인가 |
|---|---|---|
| 태스크에 딸린 테스트 | 그 태스크의 `files` 에 적힌 테스트 파일 | 아니다 (구현 중에 돌리는 것) |
| **전체 스위트** | `vitest run` 이 수집하는 전부 | **그렇다** |

## 필수 커버 영역 (TRD 8.1)

TRD 가 "반드시 덮어야 할 영역"까지 정했고, **각 영역에 실제로 실행되는 테스트가 최소 1건씩 있는지**가
이 게이트가 성숙했다는 뜻이다. 상태는 `harness-update` 가 갱신한다.

## 커버리지

**커버리지 숫자를 게이트로 두지 않는다.** 숫자를 맞추라고 하면 숫자를 맞추는 테스트가 생기고,
그건 정작 틀리면 안 되는 것을 덮지 않는다. 판정 기준은 위 표의 **필수 커버 영역이 실제로 덮였는가**다.

커버리지는 **보고 값으로만** 남긴다 — 별도 명령이며 게이트가 아니다. **(하네스 결정: 보고 형식 `text` + `lcov`)**

```
npm run report:coverage
```

## 전제

- **통합 테스트가 실제 PostgreSQL 에 붙는다(TD-014).** `scripts/local-dev.ps1` 로 DB 가 떠 있어야 이 게이트가 돈다
- 전제가 안 지켜졌을 때의 실패는 **환경 문제**다. `local-dev.ps1 -Status` 로 먼저 확인하고,
  코드에서 원인을 찾기 전에 `LOG.md` 에 환경 문제로 분류해 남긴다
- 통합 테스트는 `.env.local` 의 `DATABASE_URL` 이 가리키는 **로컬 DB** 에만 붙는다. 운영·스테이징 DB 를 가리키지 않는다

## 하지 않는 것

- 자동 수정 — 스냅샷 갱신(`-u`) 포함. 게이트는 판정만 한다
- 브라우저를 띄우는 검증 — e2e 의 몫이다
- 커버리지 임계 실패
